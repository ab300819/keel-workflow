# Markdown 标记与排版审查

审查 Markdown 文档的**标记**与**排版**三组问题：M 组（markdownlint 标记）、T 组（中文排版）、L 组（LLM 输出毛病）。输出结构化报告；修改一律经用户确认后进行。

**与 DevDocs 独立**：不读 `docs/prd/` `docs/devdocs/`，不写 F/US/AC 编号，不接入 ms- 流程，对现有协议零改动。

## Language

- 接受中英文提问，统一中文回复

## 触发条件与路由出口

**何时用本 skill**：

- 审查一篇（或一批）Markdown 文档的标记与排版是否规范，尤其是 LLM 生成的文档
- 想知道本仓的 markdownlint 配置为何这样调、某条 `MDxxx` 该不该开
- 写作前想要一份「怎么写才合规」的清单（见下文「生成时清单」，不必读 references）

**何时不用——路由出口**：

| 需求 | 去处 |
|---|---|
| 文风与语言润色（长句、被动语态、的地得、套话） | 不在本 skill 范围内，属语意改写（见「边界原则」）；需要时另做 `writing-review` |
| 代码规范、命名、注释、日志 | `code-quality` |
| 提交信息格式 | `commit-convention` |
| DevDocs 文档的结构与编号治理、死链、过大文件 | `/ms-pipeline realign --scope=health` |
| AGENTS.md / CLAUDE.md 记忆文件维护 | `agent-memory` |
| 自动格式化（一键改好全文） | 本 skill **不提供**，首版无自动修复路径（见「身份与边界」） |

## 身份与边界

**这是一个 Markdown 审查策略 skill，不是 Markdown 自动格式化 skill。** 首版完全不实现自动修复：`markdownlint-cli2` 只做只读扫描，全部检出走报告。

价值内核按重要性排序：

1. 本仓统一的 markdownlint 配置与分歧决策（含为何偏离 Google docguide）
2. 中文排版规则的**出处、冲突与反例**——包括与国标冲突之处的裁决
3. M / T / L 三组的边界与默认状态
4. 保护区、语意承载豁免与降级策略
5. 稳定的报告结构
6. 生成时清单与事后审查共用同一 SSOT

**存废判据**：若删去 T / L 的规则知识、豁免与出处，只剩一份配置加一句「AI 通读」，则不配单独做 skill——此时一份 `.markdownlint.jsonc` 加通用审查 prompt 即可。

### 边界原则

**本 skill 只碰排版与标记，不碰原文语意。** 任何会改变文字表达、删除内容、重写句子的操作都在边界之外，**本原则无例外**——原方案曾以「越界模式」名义保留文风审查组，已删除。违反本原则的规则一律不实现，或降为只报告。

以下两个自欺点最容易复发，判定检出项时须逐条对照：

1. **「只改 Markdown 标记」不等于「不改语意」**——标记、强调、emoji、结构本身都可能承载语意。删掉 `🔒 仅管理员可见` 的 emoji 会丢信息；把独占一行的加粗改成标题会改变目录与锚点；删掉 `**必须**` 的加粗会削弱规范强度
2. **「需要人确认的 assist」不等于「在边界内」**——生成一个可直接应用的语意改写 diff，仍是在做语意改写，不因最终由人点确认而回到边界内

## 三组概览

| 组 | 内容 | 权威出处 | 判定者 | 默认 | 规则参考 |
|---|---|---|---|---|---|
| M | Markdown 标记 | markdownlint `MD001`–`MD060`（53 条）+ Google Markdown style guide | `markdownlint-cli2` | 开 | [references/markdown-rules.md](references/markdown-rules.md) |
| T | 中文排版 | GB/T 15834—2011、中文文案排版指北 | AI 通读 | 中文文档开 | [references/cjk-typography.md](references/cjk-typography.md) |
| L | LLM 输出毛病 | 新增（无外部权威源，靠判据可量化保证一致） | AI 通读 | 开 | [references/llm-artifacts.md](references/llm-artifacts.md) |

- **M 组配置**：[assets/markdownlint.jsonc](assets/markdownlint.jsonc)，13 条默认值调整。出厂默认在本仓实测百余条告警（82% 是噪音），本配置降至 22 条且逐条核对为真问题。基线是活的（实测 138 → 复测 139，绝对值随文档修订漂移），须保持的是量级差与「本配置下 100% 真问题」这一判断，逐次实测值与漂移来源见 [references/markdown-rules.md](references/markdown-rules.md) §2
- **T 组规则 ID 为 `T1`–`T4`、`T6`、`T7`、`T9`**，`T5` 与 `T8` 是**故意空缺**，不补也不重排：`T5`（半角标点转全角）**已否决**，`T8`（英文整句内用半角标点）**已并入 `T7`** 的「带条件」档。两者原因不同，记录在 [references/cjk-typography.md](references/cjk-typography.md) §2
- **L 组三条**：`L1` emoji 装饰滥用、`L2` 加粗滥用、`L3` 结构滥用。承载语意的 emoji（状态 🟢🟡🔴 / 权限 🔒 / 级别 ⛔⚠️ℹ️✅）**不限位置一律豁免**，`L1` 只针对装饰性用法
- **组间去重靠职责划分，不靠运行时仲裁**：唯一边界是「加粗代替标题」这一形态归 `MD036` 独占、`L2` 不覆盖。除此之外三组判据不重叠，**同一行上的两个不同缺陷各报各的**（`## 🎉 快速开始！` 应同时报 L1 与 MD026，不得互相压制）

## 工具获取

**检测顺序**（先用现成的，不重复安装）：

1. 目标仓库的 `node_modules/.bin/markdownlint-cli2`——存在则用，尊重项目自带版本
2. `PATH` 上的 `markdownlint-cli2`
3. 都没有 → **询问用户**，四个选项：

| 选项 | 命令 | 适用 |
|---|---|---|
| Homebrew 安装 | `brew install markdownlint-cli2` | macOS 首选。依赖 node，但不随 node 版本切换而失效 |
| npm 全局安装 | `npm i -g markdownlint-cli2` | 跨平台。⚠️ 若 node 由 mise / nvm / asdf 管理，包装在当前 node 版本目录下，**切换 node 版本后失效** |
| 本次临时运行 | `npx --yes markdownlint-cli2` | 不想装。首次需网络、较慢 |
| 跳过 M 组 | —— | 降级为 AI 按 [references/markdown-rules.md](references/markdown-rules.md) 扫描，只报告 |

**不得静默安装。** 安装修改用户系统环境，必须先问。

**版本处理**：不强制特定版本，本地已装什么就用什么；但**报告头部须记录 `markdownlint-cli2 --version` 的实际输出**。「报告可复现」的实质是知道某份报告出自哪个规则集，而非固定某一版本。只在「帮用户安装」与「npx 兜底」两种情况下建议具体版本。

⚠️ **安全提示（对只读扫描同样成立）**：CLI2 会沿目标路径发现 `.markdownlint-cli2.*` 与 `.markdownlint.*` 配置，其中 `.cjs` / `.mjs` 形式**会执行代码**，且没有关闭配置发现的命令行参数。对**不受信任的第三方仓库**运行扫描存在代码执行风险，扫描前须向用户明示。

**配置路径必须用绝对路径。** `--config` 的值须解析为**本 skill 目录下 `assets/markdownlint.jsonc` 的绝对路径**，不得写裸相对路径：

```bash
# 正确：先取 skill 目录绝对路径，再拼配置
CFG="<本 SKILL.md 所在目录的绝对路径>/assets/markdownlint.jsonc"
markdownlint-cli2 --config "$CFG" <目标文件或目录>
```

本 skill 的**主场景是审别的仓库的文档**，此时 cwd 在目标仓库而非本仓，`--config assets/markdownlint.jsonc` 与 `--config skills/markdown-style/assets/markdownlint.jsonc` 两种写法都不解析。文档里出现的相对路径命令示例一律只在本仓 cwd 下成立，跨仓使用前须换成绝对路径。

**配置策略**：`--config` 只是 base configuration，可被目标路径上的子目录配置与文档内 `markdownlint-*` 注释覆盖。因只读扫描不改文件、误报成本低，**允许项目配置生效**——目标仓库自有的 markdownlint 约定优先于本 skill 默认值是合理行为。

## 执行流程

```text
0  前置检查:目标文件是否在 git 版控下、该文件自身是否有未提交改动
   (逐文件判,不看整仓 git status;判据见下文「确认时机」)
   → 不满足则 ⚠️ 警告并请求确认(不硬阻塞:目标可能是刚生成的新文件)
   → 目标为不受信任的第三方仓库:先提示配置发现的代码执行风险
1  语言判定:CJK 字符占比 → 中文 / 英文 / 混合
   → 英文文档跳过 T 组
2  M 组扫描(只读):按检测顺序取得 markdownlint-cli2
   → --config <skill 目录绝对路径>/assets/markdownlint.jsonc(不得用相对路径)
   → 未安装:询问用户(brew / npm -g / npx 临时 / 跳过),不得静默安装
   → 用户选跳过或工具不可用:降级为 AI 按 references/markdown-rules.md 扫描,
     报告标题须追加「AI 兜底扫描,非工具判定」
   → 报告头部记录工具实际版本
3  T 组 + L 组:AI 通读,跳过保护区,产出报告条目
4  报告输出:按组分节,每条含 行号 · 规则 ID · 严重级 · 权威出处
   → 结构不确定项单列一节,标注「结构不确定,未处理」
5  询问是否应用 → 用户确认后按下文事务流程修改
6  二次验证:重跑步骤 2,确认无新增问题
```

报告结构见 [templates/report.md](templates/report.md)。判据回归用的陷阱样例集见 [references/fixtures.md](references/fixtures.md)——保护区三反例、T 组误检样例、L 组豁免对照，每条带期望结果；改动任何判据后须按其「两趟跑法」重核。

**保护区**：围栏代码块（含 blockquote 与列表内嵌套）、缩进代码块、行内 code span（含跨行与多反引号）、YAML frontmatter、HTML 块、链接与图片的 URL 与 title、autolink。通读判定与改前确认一律跳过，清单见 [references/cjk-typography.md](references/cjk-typography.md)。

**批量与输出落点**：支持传入目录，逐文件处理并汇总。文件数 ≤ 5 时报告输出到终端；> 5 时写入系统临时目录 md 文件并给出路径（**不入库**）。

## 严重级别

| 级别 | 判据 |
|---|---|
| ⛔ 错误 | 确定破坏渲染 / 违反国标强制条款（如 `T9` 省略号形式） |
| ⚠️ 警告 | 风格不一致 / LLM 排版毛病 / **M 组全部检出** |
| ℹ️ 提示 | 可选项与争议项（如链接两侧是否加空格、是否用直角引号「」），仅在文档内写法不统一时提示，不给强制主张 |

**M 组一律 ⚠️。** 原判据含「markdownlint error」一项，已删除——`markdownlint-cli2` 对**每条**违规都输出字面量 `error`，没有 severity 字段（实测对 `docs/workflows.md` 的 10 条检出，`error` 出现 10 次，无其他取值）。照字面执行会把 M 组全部判为 ⛔，与报告模板里 `MD040` / `MD036` 标 ⚠️ 直接冲突；而「工具说 error 就是 ⛔」既无判别力，又让 M 组的严重级实际由 AI 每次自由裁量，与 T / L 两组坚持「判据可量化」的立场矛盾。**⛔ 只留给国标强制条款与确定破坏渲染的情形。**

**处置方式**：**全部检出一律只报告，不存在自动修改路径。** 用户确认后的修改统一走下文事务流程。原方案的 `auto` / `assist` / `report` 三级处置分级已取消——分级本身是「某些项可以安全自动改」这一错误假设的产物。

同理，`fixable` 只表示工具能修，**不表示语意安全**。自动修复白名单经两轮审查从 27 条收缩至 9 条、再至 4 条后整体放弃；十类破坏模式记录在 [references/markdown-rules.md](references/markdown-rules.md)，是将来若有人提议启用 `--fix` 时必须先逐条回答的清单。

## 事务流程

**本节不提供结构安全保证。** 这是人工确认后的**尽力修改流程**；可验证的部分只有「落盘内容与已确认内容逐字节相等」这一条不变量。以下三点是被驳回的「纪律即安全」表述，须记录，因为这是最容易复发的自欺：

- 「一次一处 Edit」保证的是**定位唯一**，不保证**判断正确**——AI 可以精确地改错地方
- 「改前确认不在保护区」仍然要求 AI 正确解析 CommonMark。跨行 code span、容器内 HTML、围栏长度、lazy continuation 不因改用逐点 Edit 而变简单
- 「重跑 lint 零 error」只证明结果更符合 lint 规则，不证明没有语意、AST 或渲染变化。`MD009` 与 `MD029` 正是能修得干净却改坏含义的例子

**唯一硬不变量**：实际落盘结果 `A` 与推导出的预期结果 `E` **逐字节相等**（哈希比对），不等则回滚。行号子集断言不成立——确认条目的行号属于冻结前文件，而 diff 的删除行用旧侧坐标、新增行用新侧坐标，前面的编辑还会让后续行号整体漂移。

### 确认时机

按回滚成本分两种情况。目标文件在 git 版控下且自身无未提交改动时，「改完看 diff，不满意 `git checkout -- <file>` 回滚」与「先看 diff 再改」**安全性等价**——两者都能完整回滚、信息量相同，只是顺序不同，而前者流畅得多。

**判据按目标文件逐个判，不看整个工作区。** 回滚成本只取决于目标文件自身：`git checkout -- <file>` 只回滚该文件，仓库里其他文件脏不脏与它无关。机械判据是 `git diff --quiet -- <file>`（并确认文件已被跟踪）。

| 情况 | 确认时机 |
|---|---|
| 目标文件已被 git 跟踪，且 `git diff --quiet -- <file>` 通过 | **后置**：直接改，改完展示 diff，不阻塞 |
| 目标文件自身有未提交改动，或不在 git 中 | **前置**：先展示 diff 并等待确认（回滚成本高） |

⚠️ **「后置」指的只是 diff 的展示时机，不是跳过授权。** 修改授权始终在执行流程**第 5 步**取得（「询问是否应用」）——那是唯一的授权点，与本文开头「修改一律经用户确认后进行」一致。用户在第 5 步同意应用之后，本表才决定是「先给 diff 再落盘」还是「落盘后给 diff」。未经第 5 步同意，两种时机都不得动文件。

⚠️ 不得按「整仓 `git status` 是否为空」判定。活跃开发中的仓库几乎总有无关的未跟踪或已修改文件——本仓在编写本节时就是这个状态——按整仓判会让后置分支永不生效，前置确认退化为无条件阻塞，与「可完整回滚时前置确认纯属摩擦」的结论正相反。

### 八步

```text
1  冻结:记录事务开始时的原始字节串 B 与 hash(B)
2  生成:所有编辑基于 B 推导出确定性候选结果 E
3  前置确认(仅回滚成本高的情况):展示 B → E 完整 diff 并等待确认
4  防竞态:落盘前再次断言当前文件哈希仍为 hash(B)
   → 不等则中止并重新生成(文件在此期间被其他进程改动)
5  应用:写入 E
6  校验:断言 hash(A) == hash(E)
   → 不等则事务失败,恢复 B
7  展示:完整 diff(后置确认情况下这是使用者的审查点,
   须明确告知可用 git checkout 回滚)
8  复核:重跑 M 组只读扫描
```

哈希不变量在两种确认时机下都保留——它防的是并发写入，与确认时机无关。

## 修改纪律

以下纪律降低误改概率，但不构成保证：

1. **禁止正则全文替换。** 不得用 `sed` / `perl -pi` / 全局 `replace_all` 处理排版问题——这是把已排除的正则风险重新引入的捷径。候选结果 `E` 须逐点推导后整体写入，而非全文正则变换
2. 每处改动须有唯一定位的上下文依据
3. 改前确认不在保护区（清单见上文「执行流程」）
4. 行内标记外侧落点：`中文**abc**` 改为 `中文 **abc**`，空格加在标记符外侧，不改标记符内部
5. 行尾空白一律不动——行尾两个空格是硬换行，删掉会改变渲染结构
6. 结构不确定时跳过，并在报告中标注「结构不确定，未处理」
7. 数量门：单文件待改 > 30 处时汇总确认，不逐条询问

## 生成时清单

**本节内嵌不读 references**，供会话或其他 skill 直接引用——写作约束与事后审查共用同一 SSOT。以下是最高频的 16 条，覆盖实测告警的绝大多数：

1. 围栏代码块必须声明语言（`MD040`，实测告警第一名）
2. 标题逐级递增不跳级，统一用 ATX `#` 形式（`MD001` / `MD003`）
3. 标题、围栏代码块、列表、表格上下各留一个空行（`MD022` / `MD031` / `MD032` / `MD058`）
4. 无序列表统一用 `-`，嵌套缩进 2 空格（`MD004` / `MD007`）
5. 行尾不留空格；确需硬换行时保留**恰好**两个（`MD009`）
6. 不出现连续多个空行；文件以单个换行结尾（`MD012` / `MD047`）
7. 强调标记用 `*` 不用 `_`——下划线紧邻 CJK 时部分渲染器不生效（`MD049` / `MD050`）
8. 不用加粗或斜体充当标题（`MD036`）
9. 标题末尾不带标点（`MD026`）
10. 图片须有 alt 文本；链接不裸写 URL（`MD045` / `MD034`）
11. 表格内容行两侧各留一个空格，分隔行写 `|---|---|`（`MD060`）
12. 中文与半角英文之间加一个半角空格（`T1`）
13. 全角标点两侧不留**行内横向**空格（`T4`）——**两个例外：行尾空白（硬换行）与表格单元格边界的 padding 空格一律不动**。后者正是第 11 条要求的那个空格，两条不矛盾：`| 逐步确认（默认） |` 合规
14. 数字与英文单位之间加空格（`°` `%` 例外）；中文与数字的空格风格在同一文档内保持统一（`T3` / `T2`）
15. 中文省略号写六连点 `……`（`T9`）；全角**数字**改半角，全角字母同理（类推），全角符号仅在英文整句 / 特殊名词内适用，**中文标点保持全角不动**（`T7`）
16. 不用装饰性 emoji 做标题（`L1`）、不用加粗代替标题（`MD036`，同第 8 条；**这一形态不由 `L2` 管**）、一段内加粗不超过两组、列表嵌套不超过 3 层（`L2` / `L3`）

第 16 条只约束**装饰性**用法：承载语意的状态、权限、级别标记不限位置一律豁免。

## 权威规格

设计定稿：[docs/superpowers/specs/2026-07-31-markdown-style-skill-design.md](../../docs/superpowers/specs/2026-07-31-markdown-style-skill-design.md)（Codex 三轮对抗审查 + 首次真实运行验证）。

**precedence 分两类，不是一句「以规格为准」：**

| 类别 | 权威 | 例 |
|---|---|---|
| **规则知识**：判据、出处、证伪记录、盲区分类、边界原则 | **以规格为准** | T4 闭集范围、为何不用 `--fix`、L 组豁免 |
| **执行口径**：流程步骤、判据的机械形式、命令与路径、报告字段 | **以本文为准** | git 状态判据、`--config` 路径、严重级归档 |

分开的理由：实施期的真实运行会先修正执行口径（本文与 references 是落地面），规格随后同步；若一律「以规格为准」，任何回读规格的人都可能把已被实测推翻的口径读回来——`git status` 整仓判据就是这样一处，实测证伪后本文已改逐文件，而规格里一度残留整仓写法。规则知识则相反：它是审查沉淀的资产，本文只是浓缩摘要，冲突时必须回规格。
