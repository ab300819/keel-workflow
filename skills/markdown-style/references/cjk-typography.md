# T 组中文排版参考

> 配合 [SKILL.md](../SKILL.md) 使用。本文件是 T 组（中英混排 / 数字 / 标点等中文排版规则）的知识底座，覆盖 T1–T4、T6、T7、T9 七条规则的判定依据与出处，并保留六条证伪记录——它们记录了「为什么这条规则不能自动修复」，防止将来有人以为是遗漏而重新引入已排除的错误。
>
> 本仓配置文件：[`assets/markdownlint.jsonc`](../assets/markdownlint.jsonc)（M 组用）。T 组无对应配置文件，全部由 AI 通读判定。

## 1. 权威源与降级说明

T 组以 **Node 版 markdownlint 与国标 / 排版指北为准**。用户最初提供的两个本地参考项目均降为二手参考，仅作落地示例，不作为规则出处：

- `~/Projects/markdownlint`（Ruby `mdl`）——原始实现但规则集停留在 `MD047` 附近，已被 Node 版取代。
- `~/Projects/document-style-guide`——规则可溯源至 GB/T 15834 与《中文文案排版指北》，且存在与国标冲突之处（见 T9 证伪记录）。

**GB/T 15835—2011《出版物上数字用法》不纳入本组权威源。** 该标准规定的是「何时用汉字数字、何时用阿拉伯数字」，即计量、编号、概数的用字选择，与 T 组关心的空格排版无关；且 2011 版相比旧版不再强调优先使用阿拉伯数字，允许两种形式在简洁性无显著差异时并存——标准本身不给强制主张，机械检查必然误报。

因此 **T2、T3 的依据一律是《中文文案排版指北》，不得引用 GB/T 15835 的条款号**作为出处。

### 1.1 「排版指北 §N」的编号口径

排版指北原文用的是分组标题加扁平条目，同一份内容按「是否把例外条并入主条」可以数出两套编号，相差一位。**本文件全部 `排版指北 §N` 采用扁平叶子编号——例外条自成一条**，映射如下（这几条是本组实际引用到的）：

| §N | 条目 | 本组引用者 |
|---|---|---|
| §1 | 中英文之间需要增加空格 | T1 |
| §2 | 中文与数字之间需要增加空格 | T2（**主动分歧**，见 §2） |
| §3 | 数字与单位之间需要增加空格 | T3 |
| §4 | 例外：度、百分比与数字之间不加空格 | T3 |
| §5 | 全角标点与其他字符之间不加空格 | T4 |
| §6 | 不重复使用标点符号 | T6（**明文推翻**，与国标冲突，见 §3） |
| §7 | 使用全角中文标点 | T7 排除中文标点的一手依据 |
| §8 | 数字使用半角字符 | T7 |
| §9 | 遇到完整的英文整句、特殊名词，其内容使用半角标点 | T7 |

记录这套口径是因为 §3 / §4 与 §5 的归并方式直接决定 T3、T4 的条号：把「度与百分比例外」并入 §3 会让后续全部前移一位，T4 就变成 §4。**本文件不采用并入读法**——T3 同时引 `§3/§4`（主条 + 例外条）本身就是这套数法的自证。改动任何 `§N` 前须先核对本表，不得凭 off-by-one 直觉调整。

表中列出了本组**引用到与明文偏离**的全部条目，包括 §2、§6、§7 三条——它们此前被省掉，恰好是最该在场的三条：§2 是 T2 的一手出处（原先错引已被本文件自己降级的二手项目）、§6 是 T6 明文推翻的那条、§7 是 T7 排除中文标点的一手权威。

## 2. 七条规则

全部为**只报告**，无自动修复项。

**规则 ID 为 `T1`–`T4`、`T6`、`T7`、`T9`，`T5` 与 `T8` 是故意空缺，不补也不重排。** 两者空缺的原因不同，须分别记录——这也是这段说明必须落在本文件（T 组 SSOT）而非仅落在 SKILL.md 的理由：本文件才是「保留证伪记录、防止后人当作遗漏而重新引入」的载体。

| ID | 原规则 | 处置 | 去向 |
|---|---|---|---|
| `T5` | 半角标点转全角 | **已否决** | 不实现。中英混排下「此处该用半角还是全角标点」的判定边界模糊（英文整句、代码标识符、混排短语各有惯例），机械检查必然误报 |
| `T8` | 英文整句 / 特殊名词内部使用半角标点 | **已并入 T7** | 不是被证伪，而是被吸收——T7 三档表的「带条件」档引的排版指北 §9 就是原 T8 的规则本身。空缺是合并的痕迹，不是删除 |

重排编号会让这两段记录失去锚点，故 ID 一律不动。

| ID | 规则 | 出处 |
|---|---|---|
| T1 | 中文与半角英文之间加一个半角空格 | 排版指北 §1 |
| T2 | 中文与数字之间的空格风格须统一（判据：同一文档内同时出现`5 台`与`5台`） | 排版指北 §2（**主动分歧**，见下） |
| T3 | 数字与英文单位之间加空格（`°` `%` 例外） | 排版指北 §3/§4 |
| T4 | 全角标点两侧不留**行内横向**空格（全角标点各占一至两个字位置，位置本身已含间距） | 排版指北 §5；GB/T 15834 §5.1.1（句号 / 逗号 / 顿号 / 分号 / 冒号占一个字位置）、§5.1.3（引号 / 括号 / 书名号各占一个字位置）、§5.1.4（破折号占两个字位置）、§5.1.5（省略号占两个字位置） |
| T6 | 问号 / 叹号叠用超过三个 | GB/T 15834 §4.2.3.3、§4.3.3.3（推翻排版指北 §6，见 §3） |
| T7 | 全角数字宜用半角；全角字母同理（类推）；全角 ASCII 符号仅在英文整句 / 特殊名词内适用。**中文标点不在此列** | 排版指北 §8（数字）、§9（英文整句内的半角标点） |
| T9 | 中文省略号须为六连点`……` | GB/T 15834 前言、§4.11.2 |

四条判定范围的收敛，均来自首次真实运行暴露的误报或漏检（对照样例见 [fixtures.md](fixtures.md) T-03、T-04、T-10、T-11、T-12）：

**T2 与排版指北 §2 的主动分歧**（与 [markdown-rules.md](markdown-rules.md) §3 记录的两处 Google 分歧同等待遇，须显式记录以免后续被当作遗漏「修正」）：指北 §2「中文与数字之间需要增加空格」是**硬规则**，要求一律加空格；本 skill 把 T2 降为「**风格须统一，只报告**」。理由即 §3 T1 证伪记录的第 1 条——硬规则会强制 `2026年7月31日`、`第3章`、`3个节点` 加空格，而这类日期与编号场景加空格反而不合中文习惯。降级的代价是放弃了一条明确主张，换来的是不误报。

**T2 的出处已更正。** 原先写作 `document-style-guide text.md（2）`，而本文件 §1 两次立规「本地参考项目降为二手参考，不作为规则出处」「T2、T3 的依据一律是《中文文案排版指北》」——引一个自己刚降级的项目当出处，是自我违规。现改引一手的排版指北 §2。

- **T2 不统计「数字属于英文术语」的边界**：`iPhone 12 上`、`markdownlint-cli2 扫描`、`HTTP/2 协议` 中的数字是英文术语的组成部分，其与中文之间的空格由 **T1** 管辖。若把这类空格计入 T2 的风格统计，任何同时出现 `iPhone 12 上` 与 `第3章` 的文档都会被误判为「中数空格风格不统一」。T2 只统计**裸数字**与中文相邻的情形（`5 台` / `5台`）
- **T4 的「全角标点」是一个闭集**：`，。、；：？！（）【】《》「」『』` 与六连点省略号 `……`、双破折号 `——`。**排除项按同一条理由处理——East Asian Width 归类为 Ambiguous 者一律不计入**：
  - 单个 `—`（U+2014）与单个 `…`（U+2026）——在中文正文里既可能是半个破折号 / 省略号，也可能是照英文习惯用的 em dash / ellipsis
  - **弯引号 `“”`（U+201C/201D）与 `‘’`（U+2018/2019）**——同为 Ambiguous，在中英混排里常常就是英文引号本身，`the “foo” option` 不该被判 T4。且本文件 §5 已把「是否使用直角引号「」」列为**争议项**（只在同文档写法不统一时以 ℹ️ 提示），把弯引号放进 T4 闭集等于一边说「引号形式不给强制主张」一边强制它的空格规则

  **判定 T4 时必须数码点、查 EAW 归类，不能凭字形。** 闭集是 T4 唯一的判定依据，不得凭「看上去是中文标点」扩展
- **T4 不管表格单元格的 padding 空格**：`| 逐步确认（默认） |` 中 `）` 后的那个空格是 `MD060` 配置为 `padded` 时**强制要求**的结构 padding。报 T4 会与 M 组配置直接冲突，按 T4 修改会立刻造成 MD060 违规。该空格与行尾硬换行空格同类——属结构而非排版空白，一律不动
- **T7 的范围逐类给出处，中文标点排除在外**：规则文字原写作「全角字母数字」，与其证伪记录举的全角 `＠`（符号而非字母数字）不一致；而一度改写成的「全角 ASCII 符号宜用半角」又走过了头——**排版指北 §7 明文要求「使用全角中文标点」**——建议把中文标点转半角是直接违反指北自己的条款。这是排除中文标点的一手权威依据。**辅证**：`，` = U+FF0C 是 `,` 的全角形式、`（` = U+FF08 是 `(` 的全角形式，同属 U+FF01–FF5E 全角区，所以「全角 ASCII 符号宜用半角」这句话在字面上就覆盖了它们；但该论证只覆盖到 U+FF01–FF5E 区内的字符，闭集里的 `。、【】《》「」『』` 并不在该区（分别属 U+3000 CJK 符号与标点区等），**故 Unicode 论证不足以单独支撑排除，须以 §7 为准**。无条件建议转半角还会与 T4 闭集「这些字符应保持全角」结论直接相反。范围按可溯源程度分三档：

  | 档 | 范围 | 出处 | 处置 |
  |---|---|---|---|
  | 出处充分 | 全角**数字** `０-９` | 排版指北 §8「数字使用半角字符」 | 检出 |
  | **类推**，出处不覆盖 | 全角**字母** `Ａ-Ｚ` `ａ-ｚ` | 由 §8 类推——**§8 原文只讲数字，字母无直接出处** | 检出，但报告须标注「出处仅覆盖数字，字母为类推」 |
  | **带条件** | 全角 ASCII 符号中**不属于中文标点**者：`＠＃％＆＝＋＄＾＿｜～` 等 | 排版指北 §9「遇到完整的英文整句、特殊名词，其内容使用半角标点」 | **仅当该符号处于英文整句或特殊名词内部时**检出；中文语境下单独出现不检出 |
  | 排除 | **中文标点**：`，。、；：？！（）【】《》「」『』` 等 | 排版指北 §7「使用全角中文标点」 | **一律不检出**，空格问题归 T4 闭集（见上一条）。T7 与 T4 在这批字符上不重叠 |

  三档均同等附带「可能是数据本身」的风险提示（见 §3 T7 证伪记录）。判定顺序：先看字符是否落在 T4 闭集，落在即退出 T7。

  **弯引号 `“”` `‘’` 既不归 T4 也不归 T7。** 它们不是全角 ASCII 符号（全角引号是 `＂` U+FF02，与 U+201C/201D 是不同字符），故不入 T7；又因 EAW Ambiguous 被排除在 T4 闭集之外。引号形式的唯一落点是 §5 的**争议项** ℹ️——只在同一文档内写法不统一时提示，不给强制主张。

## 3. 逐条证伪记录

以下六条记录了「原方案为什么把这条定为可自动修复，以及审查如何证伪」。每条都是将来最容易被「优化」重新引入的错误，须完整保留。

- **T1 原含「与数字」，与 T2 直接矛盾**——若 T1 管辖中文与数字之间的空格，`2026年7月31日`、`第3章`、`3个节点` 会被强制加空格；而 T2 正是因为日期、编号这类场景不应强制统一才定为只报告。同一件事得出两个结论。**修正：中数关系全部归 T2，T1 只管中文与英文**。
- **T3 白名单答不了「此处是不是单位」**——若白名单含 `s`，`iPhone 5s` 会被误改为 `iPhone 5 s`；裸写的 CSS `margin: 2em` 被误改为 `margin: 2 em` 后变成无效值。白名单仅用于**降低误报**，不构成自动修复依据。
- **T4 会删除 Markdown 硬换行**——行尾两个空格是 hard break，若把"标点两侧空格"理解为包含行尾空格，删掉会改变渲染结构。**故限定为「同一行内部」的横向空格，行尾空白一律不动**。表格单元格边界的 padding 空格同属结构空白，见 §2 判定范围收敛第 3 条。
- **T6 改语气强度，属语意**——`危险！！！` 与 `危险！` 语气不同，删减属于改写内容而非排版。国标允许叠用最多三个（§4.3.3.3 原文示例「我要揭露！我要控诉！！我要以死抗争！！！」），§4.3.3.4 允许 `？！` 连用，§5.1.2 还为二叠、三叠、问叹连用规定了占位宽度；排版指北「不要重复使用标点符号」仅为文案风格主张，与国标冲突。**故仅报告「超过三叠」这一越界情形，二至三叠不提示**。
- **T7 全角字符可能是数据本身**——测试文档中`系统必须拒绝用户名 ａｄｍｉｎ`若转半角，测试对象本身就变了；全角`＠`可能被刻意用于避免触发 mention。**检出时须附带此风险提示，不得直接建议转换**。注意本条举的 `＠` 属 §2 三档表的「带条件」档（英文整句 / 特殊名词内适用），不是把 T7 扩展到全部全角符号的依据——中文标点由 T4 管，见 §2 收敛条目「T4 的『全角标点』是一个闭集」。
- **T9 与本地参考项目冲突**——document-style-guide 主张`⋯⋯`（U+22EF），但 GB/T 15834 前言明确规定省略号的形式统一为六连点，即`……`（U+2026 × 2）。**以国标为准，`⋯⋯` 判为不合规**。`...` → `……` 仅在紧邻 CJK 字符时报告；英文语境的`...`、`foo(...)`、`a...b` 范围语法一律不报。

## 4. 保护区清单

来源设计方案第 6.2 节修改纪律第 3 条。以下八项在通读判定与改前确认时一律跳过，不作为 T 组检出对象：

1. 围栏代码块（含 blockquote 与列表内嵌套的围栏）
2. 缩进代码块
3. 行内 code span（含跨行与多反引号形式）
4. YAML frontmatter
5. HTML 块
6. 链接与图片的 URL
7. 链接与图片的 title
8. autolink

另有两条配套纪律：

- **行内标记外侧落点**：涉及行内标记（加粗、斜体、code span 等）时，空格加在标记符外侧，不改标记符内部。例如`中文**abc**`改为`中文 **abc**`，而不是`中文** abc**`。
- **结构不确定时跳过**：无法确认某段落是否落在保护区内时，跳过该处并在报告中标注「结构不确定，未处理」，不得凭推测处理。

## 5. 争议项

排版指北标注为争议项的以下两条，检出级别为 ℹ️ 提示，**仅在同一文档内写法不统一时提示**，不给强制主张：

- 链接文字与前后中文之间是否加空格
- 是否使用直角引号「」
