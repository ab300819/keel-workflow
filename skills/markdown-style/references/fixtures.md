# 验证样例集

> 配合 [SKILL.md](../SKILL.md) 使用。本文件收录[设计方案 §9](../../../docs/superpowers/specs/2026-07-31-markdown-style-skill-design.md) 项 3（保护区零误伤）与项 4（T 组检出准确性）所需的陷阱样例，每条给出**期望结果**与**理由**，供首次验证与后续回归逐条核对。
>
> **所有样例一律包在围栏代码块内**——围栏代码块本身就是保护区第 1 项，因此本文件自身应零告警。这既是样例的载体，也顺带把「保护区不被检出」变成一条自检：若对本文件的扫描报出任何**落在代码块内部**的条目，说明保护区识别有误。

## 1. 使用方式

自检命令（期望输出 `0`）：

```bash
npx --yes markdownlint-cli2 --config skills/markdown-style/assets/markdownlint.jsonc \
  skills/markdown-style/references/fixtures.md 2>&1 | grep -cE "\.md:[0-9]+"
```

T / L 两组无工具可跑，核对方式见下。**样例集同时含「应检出」与「不应检出」两类**——只有负例的样例集无法区分「保护区正确」与「什么都没扫」，故正例是必需的对照。

**两趟跑法**（缺一不可）：

1. **原样跑**——直接对本文件执行完整审查流程。因全部样例都在围栏内，正确结果是**零条落在代码块内部的检出**。这一趟验的是保护区识别
2. **解包跑**——把下文各样例的围栏内容复制到临时目录的一个 `.md` 文件里（**不入库**）作为正文，再执行一次审查，把报告与每条样例的「期望」逐条比对。这一趟验的是判据本身

只跑第一趟是无效验证：所有样例都落在保护区内，「零检出」既可能说明判据正确，也可能说明判据根本没跑。

## 2. 保护区反例

三条来自设计方案第三轮审查，是最容易被误伤的三种结构。

### P-01 blockquote 内的围栏代码块

```text
> ```yaml
> name: 中文abc
> size: 10GB
> ```
```

- **期望**：不应检出
- **理由**：`中文abc` 缺空格（形似 T1）、`10GB` 数字紧贴单位（形似 T3），但它们在 blockquote 嵌套的围栏代码块内，属保护区第 1 项。判定保护区时须先解析 blockquote 的 `>` 前缀再判围栏，只按行首 `` ``` `` 匹配会漏掉这种嵌套形式

### P-02 跨行的多反引号 code span

```text
配置项写作 ``中文abc
size: 10GB`` 这一整段。
```

- **期望**：不应检出
- **理由**：CommonMark 的 code span 可在同一段落内跨行，且反引号可为多个。此处 `中文abc` 与 `10GB` 都落在同一个 code span 内部，属保护区第 3 项。逐行扫描并假定 code span 不跨行会把它们误判为正文

### P-03 含平衡括号与查询串的链接

```text
详见 [中文API](https://example.com/a_(b)?q=中文ABC "版本v2") 一节。
```

- **期望**：不应检出（URL 与 title 部分）
- **理由**：URL 中的 `a_(b)` 含平衡括号，朴素的「匹配到第一个 `)` 即结束」会把 URL 截断在 `a_(b` 处，从而把 `?q=中文ABC` 当成正文并按 T1 报告；title `"版本v2"` 同理属保护区第 7 项。URL 里的 `_` 也不得按 MD049 改写
- **补充**：链接**文字** `中文API` 不在保护区内——它是可见正文，T1 对它成立。但「链接文字与前后中文之间是否加空格」是争议项，只在同文档写法不统一时以 ℹ️ 提示（cjk-typography.md §5）

## 3. T 组样例

### T-01 机型后缀不是单位

```text
本机在 iPhone 5s 与 iPhone 12 上实测通过。
```

- **期望**：不应检出
- **理由**：`5s` 的 `s` 是机型后缀，不是「秒」。T3 白名单若含 `s` 会误改为 `iPhone 5 s`（cjk-typography.md §3 T3 证伪记录）

### T-02 裸写的 CSS 值

```text
把外边距设为 margin: 2em 即可。
```

- **期望**：不应检出
- **理由**：`2em` 是 CSS 长度值，改成 `2 em` 后是**无效值**。同上条：白名单只用于降低误报，不构成自动修复依据

### T-03 日期不走 T1

```text
定稿日期为 2026年7月31日，第3章同步更新。
```

- **期望**：不应检出（T1 不成立；T2 视全文而定）
- **理由**：中文与数字的关系全部归 T2，T1 只管中文与半角英文。若 T1 含数字，日期与「第3章」会被强制加空格——这正是 T1 原判据与 T2 直接矛盾之处（cjk-typography.md §3 第 1 条）
- **T2 触发条件**：仅当同一文档内**同时**出现 `5 台` 与 `5台` 两种写法时报风格不统一，且只报不改。单独出现 `2026年7月31日` 不构成检出

### T-04 全角字符可能是数据本身

```text
系统必须拒绝用户名 ａｄｍｉｎ，也须拒绝含全角＠的地址。
```

- **期望**：应检出 T7 **两处**（`ａｄｍｉｎ`、`＠`），均**须附数据风险提示，不得直接建议转换**；`ａｄｍｉｎ` 还须标注「出处仅覆盖数字，字母为类推」。**行内两个全角逗号 `，` 不检出**（见 T-11）
- **理由**：这是一条测试断言，`ａｄｍｉｎ` 转半角后测试对象本身就变了；全角 `＠` 可能被刻意用于避免触发 mention。报告须写明「此处全角字符可能是数据，转换前请确认」（cjk-typography.md §3 第 5 条）。`＠` 落在 T7 三档表的「带条件」档——此处 `含全角＠的地址` 指的正是邮箱地址这一特殊名词内部，故成立

### T-11 中文标点不是 T7 的检出对象

```text
拒绝用户名 ａｄｍｉｎ，并记录日志（含时间戳）。
```

- **期望**：不应检出 T7 于 `，` 与 `（）`；仅 `ａｄｍｉｎ` 检出 T7
- **理由**：`，`(U+FF0C)、`（`(U+FF08) 都在 U+FF01–FF5E 全角区内，**中文标点本身就是 ASCII 符号的全角形式**。若 T7 无条件写作「全角 ASCII 符号宜用半角」，这些字符会被建议转半角，与 T4 闭集「这些字符应保持全角、两侧不留空格」结论直接相反——同一批字符两条规则打架。故 T7 明确排除中文标点，判定归 T4（cjk-typography.md §2 T7 三档表末行）。判定顺序：先查 T4 闭集，落在闭集内即退出 T7

### T-05 三叠叹号在国标允许范围内

```text
我要揭露！我要控诉！！我要以死抗争！！！
```

- **期望**：不应检出
- **理由**：GB/T 15834 §4.3.3.3 的原文示例即为此句，允许叠用最多三个。排版指北「不要重复使用标点符号」与国标冲突，以国标为准。删减叠号改变语气强度，属语意（cjk-typography.md §3 第 4 条）

### T-06 四叠叹号越界

```text
危险！！！！请立即停止操作。
```

- **期望**：应检出 T6
- **理由**：四叠超出国标允许的最多三叠，是 T6 唯一的检出情形。**仍只报告不改**——收敛叠号属语意操作

### T-07 英文语境的三点省略

```text
Usage: foo(...) — see also a...b for ranges.
```

- **期望**：不应检出
- **理由**：T9 的 `...` → `……` 只在紧邻 CJK 字符时报告。英文语境的 `...`、函数签名 `foo(...)`、范围语法 `a...b` 一律不报（cjk-typography.md §3 第 6 条）

### T-08 中文语境的省略号形式

```text
这些细节...暂且不论，其余部分⋯⋯照旧。
```

- **期望**：应检出 T9 两处
- **理由**：`...` 紧邻 CJK 须为六连点 `……`；`⋯⋯`（U+22EF）是本地参考项目的主张，与 GB/T 15834 前言「省略号的形式统一为六连点」冲突，以国标为准判为不合规

### T-09 中英之间缺空格

```text
调用markdownlint-cli2扫描后生成report文件。
```

- **期望**：应检出 T1 **四处**（`用|m`、`2|扫`、`成|r`、`t|文` 四个边界）
- **理由**：正例对照组。中文与半角英文之间须加一个半角空格（排版指北 §1）。`markdownlint-cli2` 末尾的 `2` 是英文术语的组成部分，其与中文的边界归 T1 不归 T2（见 T-03）。空格加在行内标记**外侧**：`中文**abc**` 改为 `中文 **abc**`，不写成 `中文** abc**`

### T-10 表格单元格的 padding 空格

```markdown
| 命令 | 用途 |
|---|---|
| `/ms-prd` | 自动检测输入（短想法 → 头脑风暴） |
```

- **期望**：不应检出
- **理由**：第 3 行的 `）` 后紧跟一个空格再接 `|`，形似 T4「全角标点两侧留了空格」，但该空格是 `MD060` 配置为 `padded` 时**强制要求**的表格结构 padding——报 T4 就与 M 组配置直接冲突，且按 T4 修改会立刻造成 MD060 违规。表格单元格边界的 padding 空格与行尾硬换行空格同类：属结构而非排版空白，一律不动（cjk-typography.md §2 T4 注）

### T-12 破碎号与 em dash：T4 闭集的边界

```text
末步）清理 —— 代码才是事实源。
第 1 项 — 需求探索阶段。
```

- **期望**：第 1 行**应检出 T4**；第 2 行**不应检出**
- **理由**：这是 T4 闭集唯一的判别样例，两行只差一个字符。第 1 行是 `——`（U+2014 **× 2**，双破折号），**在闭集内**，两侧各有空格 → T4 成立。第 2 行是单个 `—`（U+2014 × 1），East Asian Width 为 Ambiguous，既可能是半个破折号也可能是照英文习惯用的 em dash，**不在闭集内** → 不报
- **来源**：本样例取自首次真实运行的实际失守点。`docs/workflows.md:63`（`清理 —— 代码`）与 `:206` / `:207`（`** — 需求探索阶段`）三行肉眼几乎一样，当时被一并判为「落在未定义区间、不检出」，逐码点核对后才发现 `:63` 是双破折号、属真检出。**判定 T4 时必须数码点个数，不能凭字形**

## 4. L 组样例

四条分两组。L-01 / L-02 区分 L1 的「装饰性」与「承载语意」，落点在标题行——豁免是否适用于标题位置曾是歧义点，现已裁决为**不限位置一律豁免**。L-03 / L-04 针对 L2 的阈值与「段」的定义，两条都是实测误报的固化。

### L-01 标题位置的语意承载 emoji

```markdown
## 🟢 正常状态

## ⛔ 错误级别
```

- **期望**：不应检出
- **理由**：状态标记 🟢 与级别标记 ⛔ 承载事实（状态 / 级别），删除即丢信息。豁免**不限位置**，标题位置同样豁免（llm-artifacts.md §3）

### L-02 标题位置的装饰性 emoji

```markdown
## 🎉 快速开始

## 🚀 部署上线
```

- **期望**：应检出 L1
- **理由**：🎉 🚀 不承载任何事实，删除后读者不丢失信息，属装饰性用法——L1 只针对这一类。判据落点是「删除后是否有信息丢失」，不是「是否好看」

### L-03 一段内两处并列加粗

```markdown
适用于**模糊想法**或**已有 PRD 文档**，独立于 DevDocs。
```

- **期望**：不应检出
- **理由**：两个并列强调的词语是正常技术写作，不是滥用。L2 的阈值是**一段内 ≥ 3 组完整加粗标记**（≥ 6 个 `**`），两组不到线（llm-artifacts.md §2.2）

### L-04 列表各项分别计数

```markdown
- **期望**：不应检出
- **理由**：列表不按一段合并计数
```

- **期望**：不应检出
- **理由**：整个列表共 4 个 `**`，但 L2 的「段」指 CommonMark 段落，**列表的每一项各自成段**，逐项计数各为 1 组，均不到线。若把列表按一段合并，本仓几乎所有文档都会命中 L2
