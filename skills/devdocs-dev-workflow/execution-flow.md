# 任务执行流程详解

各层级任务的详细执行流程。**所有模式（含单任务）均通过 Task tool 子 Agent 执行开发流程（步骤 1→5 + Commit 1）**，文档同步（/devdocs-sync + Commit 2）及后续步骤由编排器调度。

## 步骤状态追踪

11 步执行流程中，每步完成后记录状态标记，用于断点恢复时精确定位：

| 步骤 | 对应流程 | 状态标记 |
|------|----------|----------|
| S1 | 读取任务定义 | `task_loaded` |
| S2 | 生成接口骨架 | `skeleton_interface` |
| S3 | 生成测试骨架 | `skeleton_test` |
| S4 | 红：编写测试断言（来自 AC） | `red_assertions` |
| S5 | 绿：实现代码 | `green_impl` |
| S6 | 重构优化 | `refactored` |
| S7 | 验证 AC 满足度 | `ac_verified` |
| S8 | 对抗式验证 | `review_done` |
| S9 | 更新自描述 | `self_describe_done` |
| S10 | 提交代码 | `committed` |
| S11 | 追溯同步 + 知识沉淀 | `synced` |

**断点恢复**：检测到中断时，从上一个已完成步骤的下一步继续。比原有 5 步检查点（骨架/红/绿/验证/提交）更精确，减少重复工作。

**记录方式**：通过 TodoWrite 跟踪当前步骤状态。批量模式下，编排器维护每个任务的步骤状态。

## 批量编排流程

批量模式（含依赖扩展后 >1 任务的单任务请求）的外层编排流程。纯单任务（队列长度=1）跳过拓扑排序、检查点文件和全量测试，其余步骤相同：

```
┌─ 外层编排（编排器，轻量上下文）─────────────────────┐
│                                                    │
│  1. 批量指定符解析                                  │
│     └── T-XX~T-YY / F-XXX / US-XXX / --all        │
│                    │                                │
│                    ▼                                │
│  2. 依赖解析 + 拓扑排序                             │
│     └── 递归收集依赖 → 已完成跳过 → DAG → 排序     │
│                    │                                │
│                    ▼                                │
│  3. 逐任务循环                                      │
│     ┌──────────────────────────────────────┐       │
│     │  a. 断点检测（编排器轻量执行）        │       │
│     │  b. 启动子 Agent 执行单任务（Task）   │       │
│     │     └── 骨架→TDD→验证→Commit 1       │       │
│     │  c. 编排器处理子 Agent 结果           │       │
│     │  d. 更新任务状态 + /devdocs-sync          │    │
│     │  e. Commit 2: 文档+追踪提交          │       │
│     │  f. 写检查点文件                     │       │
│     └──────────────────────────────────────┘       │
│                    │                                │
│                    ▼                                │
│  4. 全量测试验证（/devdocs-test-run --trace）       │
│     └── 触发条件：至少 1 个任务成功完成             │
│                    │                                │
│                    ▼                                │
│  5. 批量执行报告                                    │
│                                                    │
└────────────────────────────────────────────────────┘
```

> 详见 [task-orchestration.md](task-orchestration.md)

## 统一任务执行流程

所有任务遵循相同步骤，层级标记决定各步骤的强制程度：

| 符号 | 含义 |
|------|------|
| ■ | 必须执行 |
| □ | 推荐执行（跳过时记录原因） |
| ○ | 可选 |

### 强制程度矩阵

| 步骤 | 🔴 核心逻辑 | 🟡 接口层 | 🟢 UI 层 | ⚪ 基础设施 |
|------|------------|----------|---------|-----------|
| 1. 生成骨架（接口/组件） | ■ | ■ | ■ | ■ |
| 2. 生成测试骨架 | ■ | ■ | ■ | □ |
| 3. 编写测试断言 | ■ | □ | □ | ○ |
| 4. 运行测试→确认失败（红） | ■ | □ | ○ | ○ |
| 5. 实现代码 | ■ | ■ | ■ | ■ |
| 6. 运行测试→确认通过（绿） | ■ | ■ | ■ | ■ |
| 7. 重构优化（保持测试通过） | ■ | □ | ○ | ○ |
| 8. 检查验收标准 | ■ | ■ | ■ | ■ |
| 9. 对抗式验证 | ■ 自动 | □ --review | □ --review | ○ --review |
| 10. 更新自描述 | ■ | ■ | ■ | ■ |
| 11. 提交决策+原子提交 | ■ | ■ | ■ | ■ |

### 执行流程图

```
1. 开始任务
   │
   ▼
2. 生成骨架（Step 1）                              ← ■ 全层级必须
   ├── 接口/组件签名 + @requirement/@satisfies 标注
   └── 方法体: throw new Error('Not implemented')
   │
   ▼
3. 生成测试骨架（Step 2）                           ← ■/■/■/□
   ├── 测试结构和预期行为来自 03-test-*.md
   ├── @verifies/@testcase 标注
   └── 测试体: test.skip() 或 test.todo()
   │
   ▼
4. 编写测试断言（移除 skip，断言来自 AC 对应的测试用例） ← ■/□/□/○
   │
   ▼
5. 运行测试 → 确认失败（红）                        ← ■/□/○/○
   │
   ▼
6. 实现代码（遵循 /code-quality）                   ← ■ 全层级必须
   │
   ▼
7. 运行测试 → 确认通过（绿）                        ← ■ 全层级必须
   ├── 失败 → 修复实现 → 重新测试（最多 N 次，默认 3；超限标记任务失败）
   │
   ▼
8. 重构优化（保持测试通过）                         ← ■/□/○/○
   │
   ▼
9. 检查验收标准（AC-XXX）                           ← ■ 全层级必须
   ├── 全部满足 ─────────────┐
   └── 未满足 → 补充测试+实现 │
                             ▼
10. 对抗式验证                                      ← ■自动/□--review/□--review/○--review
   ├── Phase 1: 代码质量审查（/code-quality）
   ├── Phase 2: 测试完备性审查（/testing-guide）
   ├── Phase 3: 综合报告
   ├── Blocker → 修复 → 重新验证
   └── 通过 ────────────────┐
                             ▼
11. 更新自描述（/code-self-describe --update）      ← ■ 全层级必须
   │
   ▼
12. 提交决策（--headless 自动提交 / 交互模式询问用户）← ■ 全层级必须
   │
   ▼
13. Commit 1: 代码提交
   │
   ▼
14. 更新任务状态 + /devdocs-sync → Commit 2: 文档提交
```

> **跳过记录**：□ 或 ○ 步骤被跳过时，在提交信息中记录 `跳过: 步骤X（原因）`。

## 任务完成流程

所有层级遵循统一完成流程，对抗式验证的触发方式因层级而异：

1. **确认测试状态**：检查测试是否通过（步骤 6-7 结果）
2. **确认 TDD 循环**（■🔴 □🟡 ○🟢⚪）：测试从失败到通过的红-绿循环
3. **检查重构**（■🔴 □🟡 ○🟢⚪）：代码是否经过优化
4. **验证验收标准**：检查所有 AC 是否满足
5. **对抗式验证**（■🔴自动 / □🟡🟢--review / ○⚪--review）：
   - Phase 1: 代码质量审查（/code-quality 视角）
   - Phase 2: 测试完备性审查（/testing-guide 视角）
   - Phase 3: 综合报告，处理 Blocker
6. **更新自描述**：运行 /code-self-describe --update
7. **提交决策**：
   - `--headless` 模式：自动提交（安全不变量已在前置步骤保证）
   - `--auto-commit` 模式：测试通过 + 无 Blocker 时自动提交
   - 交互模式：AskUserQuestion："任务 T-XX 已完成，是否提交代码？"
     - 选项："提交" / "继续修改" / "跳过"
8. **如提交**（原子提交）：
   - Commit 1: `git add [代码文件] && git commit -m "<type>(T-XX): <名称>"`
   - 更新 04-dev-tasks*.md 状态为 `已完成`
   - 运行 /devdocs-sync
   - Commit 2: `git add [文档文件] && git commit -m "docs(T-XX): 更新任务状态并同步 trace"`
9. **更新 TodoWrite**：将任务标记为已完成

## 提交信息格式

遵循 `/commit-convention` 规范，格式如下：

```
<type>(T-XX): <任务名称>

- <完成内容1>
- <完成内容2>

关联: F-XXX, AC-XXX
测试: UT-XXX, IT-XXX 通过
```

**type 类型**：feat | fix | refactor | test | docs | chore

## TodoWrite 集成

用户确认开始开发时：

```
使用 TodoWrite 添加任务：
- 每个任务成为一个 todo 项
- 保持定义的任务顺序
- todo 内容包含任务编号
- 提交后更新状态
```

### 批量模式下 TodoWrite

```
1. 初始化：将执行队列中所有任务添加为 todo 项
2. 执行中：当前任务标记为 in_progress
3. 完成时：任务标记为 completed
4. 断点续做：读取 TodoWrite 状态辅助判断进度
```
