# 追溯维护 (--trace)

> 维护追溯矩阵的「变更来源」列。⛔ **不扫描代码**——代码里没有 DevDocs 编号。
>
> 连接方向是**文档 → commit**（反向依赖）：私有上下文可以依赖代码，代码不得依赖私有上下文。

## 为什么不扫代码

`@satisfies AC-001` 这类标注对一个没有 DevDocs 上下文的维护者是纯噪音——不知道 AC-001 是什么、去哪查、还在不在；DevDocs 一旦丢失或过期，它就是指向虚空的指针。⛔ 本流程不再产生、不再消费任何代码内编号标注。

## 数据来源

`ms-dev-workflow` 的两段式提交里，**Commit 2（文档）** 写 Commit 1（代码）的 `<repository>@<full-sha>` 到追溯矩阵——写 Commit 2 时 Commit 1 的 hash 已经是已知的。`--trace` 只做**校验与补齐**，不做发现。

## 执行流程

```
1. 读取 03-test-cases.md 追溯矩阵
   ├── 03 不存在且 AC 标 `来源: inline` → 跳过该 AC，提示"inline 条目待回填"
   │      （见 dev-workflow references/inline-entry.md）
   ▼
2. 逐条校验「变更来源」
   ├── 空 → ⚠️ 该 AC 无变更来源，提示补齐
   └── 有值 → 解析 <repository>@<sha>，在对应代码根执行 git cat-file -e <sha>
   ▼
3. 失效处理（三级降级，全程不阻塞）
   ├── sha 可解析            → ✅
   ├── sha 不可解析 + 有 patch_id → 在当前历史中找等价提交，找到则更新并标注 "已重新定位"
   └── 都找不到              → ⚠️ 列入报告，回到当前代码事实重建；⛔ 不为此建机制
   ▼
4. 输出报告（只读；写回需 --apply）
```

## 校验规则

| 检查 | 结果 |
|------|------|
| AC 有测试编号但「变更来源」为空 | ⚠️ 待补齐 |
| 「变更来源」的 sha 在对应代码根不存在 | ⚠️ 失效，附旁边那句描述供人工找回 |
| `repository` 不在 `workspace_context.code_roots` 中 | ⚠️ 仓库名未知 |
| 同一 AC 有多条变更来源 | ✅ 正常——一条 AC 可跨多个 commit |

⛔ **「变更来源有值」不等于「AC 已满足」。** commit 是变更事件锚点，不是当前实现定位符；后续重构、移动、revert 之后它仍在，但已不代表现状。判定 AC 是否满足属 `/ms-verify --impl`，须从当前代码重算。

## 输出格式

```markdown
## 追溯校验报告

| AC | 变更来源 | 状态 |
|----|----------|------|
| AC-001 | `api@a3f9c21` 邮箱格式校验 | ✅ |
| AC-002 | `api@7b2e104` 密码强度 | ⚠️ sha 失效（上游 rebase），描述："密码强度" |
| AC-003 | - | ⚠️ 待补齐 |

**失效条目需人工找回**：按描述在当前历史中搜索，或回到当前代码事实确认该行为是否仍存在。
```

## shell / linked 拓扑

`repository` 取 `workspace_context.code_roots` 的名字，逐代码根执行 `git cat-file`。三种 mode 下形状与取值规则一致，⛔ 调用方不分支。
