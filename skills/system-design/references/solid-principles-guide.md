# SOLID + 迪米特六大原则指南

> 配合 `/ms-system-design` 使用。本文把 SOLID+LoD 六大原则映射到设计文档的具体章节，给出启发式阈值和可验证特征，作为 MTE rubric 的**设计证据**（MTE 是上位目标，SOLID 是证据支撑）。
>
> 代码级/diff 级判定特征见 [`/code-quality` 设计原则（代码级）](../../code-quality/SKILL.md#设计原则代码级)；本文件聚焦设计文档级判定，两层各管一层。

## 核心关系

| 上位目标（`mte-rubric.md`） | 支撑的 SOLID+LoD 原则 |
|--------------------------|-----------------------|
| **Maintainability 可维护性** | SRP、DIP、LoD |
| **Testability 可测试性** | ISP、DIP |
| **Extensibility 可演进性** | OCP、LSP、DIP |

两套不合并；`mte-rubric.md` 评估上位目标时可引用本文件作为证据支撑。

## 六原则映射表

| 原则 | 落地章节 | 启发式告警阈值（超阈值需理由+ADR） |
|------|---------|-------------------------------|
| **SRP 单一职责** | §4 模块表"职责"列 | 职责描述含"和/并且"等多职责连接词；模块变化原因 >1 |
| **OCP 开闭原则** | §5 核心接口 + §6 设计模式 | 新增功能要求修改已有接口签名；§6 无可扩展模式支撑明显的变化点 |
| **LSP 里氏替换** | §5 行为契约表 | 同接口多实现出现"前置强化/后置弱化/新增错误契约" |
| **LoD 迪米特法则** | §4 依赖图 + "依赖接口引用"列 | 依赖层级 >2；单模块"依赖接口引用"数 >5 |
| **ISP 接口隔离** | §5 核心接口 | 单接口方法数 >7；消费方引用的接口中 >50% 方法未使用 |
| **DIP 依赖倒置** | §4 "依赖接口引用"列 | **硬 ⛔**：跨模块依赖列出现具体实现类名或裸模块名 |

阈值为**启发式告警**，非硬判据。超阈值时必须在对应章节或 ADR 中说明理由。

## 复杂度分级触发（对抗性审查）

| 复杂度 | 触发原则 | 理由 |
|-------|---------|------|
| **单模块项目** | SRP / LoD / DIP | LSP/OCP/ISP 在无多实现/无扩展场景下"不适用" |
| **低-中复杂度**（2~5 模块） | SRP / LoD / DIP / ISP | 加 ISP 因接口粒度变重要 |
| **高复杂度**（>5 模块或含多实现） | 全部 6 原则 | 所有原则都有明确可验证场景 |

## 审查结论表（强制填写三态）

```markdown
## 原则校验

| 原则 | 状态 | 理由（违反时必填） |
|------|------|----------------|
| SRP | ✅ 适用 | — |
| OCP | ⚠️ 违反 | ADR-003: 为兼容遗留 API 暂不走 Strategy |
| LSP | ✅ 适用 | — |
| LoD | — 不适用 | 单模块项目无跨模块调用 |
| ISP | ✅ 适用 | — |
| DIP | ✅ 适用 | — |
```

- **三态强制填写**：每条原则必须填 `✅ 适用 / — 不适用 / ⚠️ 违反+理由` 之一，**禁止空着**
- **⚠️ 违反**必须在设计文档的"设计变更记录（ADR）"中有对应决策条目说明"为何违反"
- **— 不适用**需一句话说明场景（如"单模块"、"无多实现"）
- **"不适用"防滥用**（吸收 codex T-076 风险）：按复杂度分级设有**适用下限**——
  - 单模块项目：SRP/LoD/DIP 中**至少 2 项为 ✅ 适用**（全 3 项"不适用"视为原则未考虑，需补说明）
  - 低-中复杂度：4 原则中**至少 3 项为 ✅ 适用**
  - 高复杂度：6 原则中**至少 5 项为 ✅ 适用**
  - 未达适用下限时，审查结论为"待修正"，不允许放行

## 分层自查清单（建议性）

**L2 模块层确认时**（决策 3 四层推进）：

- [ ] 每个模块的职责描述 ≤ 1 句话且不含多职责连接词（SRP）
- [ ] §4 依赖图层级 ≤ 2，无跨多层调用（LoD）
- [ ] "依赖接口引用"列均为 `I*(§5.x)` 形式，无裸实现类名（DIP，硬约束）

**L3 接口层确认时**：

- [ ] §5 每接口方法数 ≤ 7（ISP）
- [ ] §5 每接口的消费方使用比例 > 50%（ISP——没有"胖接口"）
- [ ] 新增功能可通过新接口/实现扩展，无需修改已有签名（OCP）
- [ ] 同接口所有实现在契约表中无冲突（LSP）

清单非 ⛔ 阻断——用户可选"不适用"或"违反+理由"，但必须显式选择。

## 反例对照（常见违反模式）

**SRP 违反**：
- ❌ "用户服务：管理用户**并**处理支付" → 两个变化原因
- ✅ 拆为 `UserService` + `PaymentService`

**OCP 违反**：
- ❌ 新增支付方式需修改 `PaymentService.pay(type)` 的 switch 分支
- ✅ `IPaymentStrategy` 接口 + 多实现，新增支付方式只加实现

**LSP 违反**：
- ❌ `FreeUser` 的 `withdraw()` 抛 `NotSupportedError` 而父类 `User.withdraw()` 无此错误
- ✅ 契约中声明 `withdraw()` 可能抛 `QuotaExceededError`，所有子类遵循

**LoD 违反**：
- ❌ `OrderController` 调用 `user.getAddress().getCity().getZipCode()`（跨 3 层）
- ✅ `user.getShippingZip()` 封装内部结构

**ISP 违反**：
- ❌ `IMultiPurpose` 接口含 50 个方法，客户端只用其中 3 个
- ✅ 拆为 `IReader` / `IWriter` / `ISubscriber` 等单一目的接口

**DIP 违反**：
- ❌ `AuthService` 依赖 `PostgresUserRepository` 具体类
- ✅ `AuthService` 依赖 `IUserRepository` 接口（DI 注入）
