# 对抗性设计审查 — 视角问题清单

## 产品视角
- 核心用户场景是否被架构支撑？
- 用户价值与技术复杂度是否匹配？
- 是否存在过度设计（功能用户不需要）？

## 工程视角

**常规挑战**：
- 技术债是否可控？关键依赖是否稳定？
- 性能瓶颈在哪？是否有扩展空间？
- 与现有架构的兼容性？迁移成本？
- 重构 / 命名变更 / 接口拆分涉及"老名→新名"过渡时，是否合理判定了桥接策略边界？（是否已发布？调用方是否内部 / 单 PR 可改齐？默认 `@Deprecated` 在未发布场景是否产生纯粹中间状态成本？详见 [`incremental-design.md` § 桥接策略边界判定](incremental-design.md#桥接策略边界判定重构--命名变更--接口拆分类-adr)）

**SOLID + LoD 六原则校验**（按项目复杂度分级强制触发，详见 [`solid-principles-guide.md`](solid-principles-guide.md)）：

| 复杂度 | 触发原则 |
|-------|---------|
| 单模块项目 | SRP / LoD / DIP |
| 低-中复杂度（2~5 模块） | SRP / LoD / DIP / ISP |
| 高复杂度（>5 模块或含多实现） | 全部 6 原则（SRP / OCP / LSP / LoD / ISP / DIP） |

每条触发的原则必须至少 1 个挑战问题（参考 `solid-principles-guide.md` 中的反例对照）。

## 测试视角
- 关键业务路径是否可自动化测试？
- 边界条件和异常路径是否明确？
- 模块间依赖是否可 mock/隔离？

> 每个视角至少选 1 个问题提出挑战并自行回应。回应格式：接受（理由）/ 驳回（替代方案）。

## 审查结论表

展示草案时必须输出此表，`原则校验`字段**强制三态填写**（禁止空着）：

```markdown
## 设计审查结论

| 视角 | 挑战问题 | 回应 | 结论 |
|------|---------|------|------|
| 产品 | | | 接受/驳回 |
| 工程 | | | 接受/驳回 |
| 测试 | | | 接受/驳回 |

## 原则校验（强制填写）

| 原则 | 状态 | 理由（违反时必填） |
|------|------|----------------|
| SRP | ✅ 适用 / — 不适用 / ⚠️ 违反 | — 或 <ADR 编号与理由> |
| OCP | ... | ... |
| LSP | ... | ... |
| LoD | ... | ... |
| ISP | ... | ... |
| DIP | ... | ... |
```

- `⚠️ 违反`的原则必须在"设计变更记录（ADR）"中有对应决策条目
- `— 不适用`需一句话说明场景（如"单模块"、"无多实现"）
- **禁止**空着任何一行
- **不设适用下限**（凑数激励，已删除）。防"全填不适用"靠的是每条 `— 不适用` 必须说明场景；DIP 仍为硬 `⛔`，其余为启发式告警。详见 `solid-principles-guide.md`
