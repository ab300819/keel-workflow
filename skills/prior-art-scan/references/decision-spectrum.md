# 决策谱系：6 条路径

```
use-as-is → 插件/扩展 → 上游贡献 → vendor+patch → 硬 fork → 自建
                                    ↑ 默认优先考虑      成本递增 →
```

三选一（fork / 贡献 / 自建）会漏掉中间路径，而中间路径往往才是对的。

---

## 决策程序

### 第 1 步：过硬闸（不过即淘汰该路径，不参与后续比较）

| 硬闸 | 淘汰哪些路径 |
|------|------------|
| license 与用户硬约束冲突 | 全部（该候选整体出局）|
| 外部 PR 受纳度 🔴 | 上游贡献 |
| 无扩展机制 | 插件/扩展 |
| `allow_forking: false` / 实操无法独立构建 | 硬 fork、vendor+patch |
| 架构与 must-have 根本冲突 | use-as-is、插件、贡献、vendor+patch |

⛔ 硬闸不可用"加权打分"绕过。许可证不兼容不是扣分项，是出局项。

### 第 2 步：按缺口类型映射

| 缺口类型 | 路径 |
|---------|------|
| 无实质缺口 | use-as-is |
| help-wanted 型（维护者想要） | 上游贡献 |
| wontfix 型 + 有扩展点 | 插件/扩展 |
| wontfix 型 + 无扩展点 | 硬 fork |
| 需要立刻可用，但缺口有上游收敛可能 | vendor + patch |
| 架构根本不匹配 | 自建 |
| 只是没人维护但东西好 | 接手维护 / co-maintain（先问）|

一个候选可能有多个不同类型的缺口 → 组合路径是合法结论（如"主体 use-as-is + 一个缺口走上游贡献"）。

### 第 3 步：写出反方理由（强制）

**每个推荐必须同时写出「反对本决策的最强理由」。** 写不出来说明还没想清楚，回去重做深评。

不是免责声明，是检验：如果最强反方理由你无法回应，这个决策就是错的。

### 第 4 步：给出先问上游的最小实验

见文末。

## 六条路径详解

### 1. use-as-is

**何时**：缺口是伪需求，或能用配置 / 组合现有能力解决。

**别忽略**：这经常是正确答案，但很少被认真考虑——人倾向于高估自己需求的独特性。在判定"有缺口"之前，先确认那真的是缺口而不是"我还没读完文档"。

**成本**：最低。**风险**：依赖上游的存活性（维度 a/b）。

### 2. 插件 / 扩展点

**何时**：上游提供扩展机制（plugin API、hook、middleware、driver 接口），缺口能在机制内实现。

**前置**：扩展机制**真的够用**——必须实际读过扩展 API 才能下结论，不能因为"它有 plugin 系统"就假设。

**失败模式**：扩展点覆盖不到你的需求，最后靠 monkey-patch 硬撑，实质变成了最糟糕版本的 fork。

**成本**：低。**红利**：升级上游不受影响。

### 3. 上游贡献

**何时**：缺口是 help-wanted 型，且**外部 PR 受纳度已验证为 🟢**（维度 d）。

⛔ 受纳度 🔴 时不得选此路径——不是"试试看"，是已经有数据表明外部 PR 进不去。

**成本**：中，且**不完全由你控制**（review 周期、维护者口味、可能被要求大改或直接拒绝）。

**关键**：先问再写。⛔ 不要先写完 PR 再去问要不要——这是最常见的浪费。

### 4. vendor + patch（边用边上游）★ 默认优先考虑

**何时**：需要立刻可用，同时希望保留上游收敛路径。

**做法**：把上游作为依赖引入（或 vendor 一份），把你的改动维持为**一组最小的、可重放的补丁**，同时把这些改动向上游提。上游接了就删掉对应补丁。

**为什么常常是对的**：它同时解决了"我现在就要"和"我不想永久自负维护"这对矛盾。三分法完全看不见它。

**成本**：中。**关键纪律**：补丁必须保持最小且有记录，否则会悄悄退化成硬 fork。定期核对上游变更。

### 5. 硬 fork

**何时**：缺口是 wontfix 型，无扩展点可用，且你确实需要这个能力。

⚠️ **fork 成本被系统性低估**。fork 意味着：

- 从此**永久**自负全部维护成本（安全补丁、依赖升级、生态适配）
- 与上游持续发散，回合并窗口逐月关闭
- 上游的新功能你不会自动得到，得手动挑
- 社区、文档、生态位都留在上游那边

→ **决策默认反对 fork。** 选它需要额外理由，而不是"选它需要没有反对理由"。

**先自问**：为什么这个能力上游不做？——如果理由是"维护者认为它会伤害产品"，你 fork 出来大概率会撞上同一堵墙。

**变体**：若原项目只是没人维护但质量好，这不是 fork 而是**接手维护**——先联系原作者，很多人乐意交出或加你为 maintainer，这比 fork 好得多（继承 star、issue、生态位、包名）。

### 6. 自建

**何时**：架构与需求根本冲突，或有明确的差异化理由。

**门槛**：必须给出**差异化**理由，且是具体的。

| 不算理由 | 算理由 |
|---------|-------|
| "我不喜欢他们的代码" | 核心数据模型与需求根本冲突，改造量 > 重写 |
| "用的技术栈不是我熟悉的" | 硬约束要求特定运行环境，现有方案无法适配 |
| "感觉自己写更快" | 现有方案全部押注某个已被证伪的设计前提 |
| "想学习" | 学习是**真理由**，但要如实标注为学习项目，不要伪装成技术选型结论 |

**成本**：最高，且成本在**上线之后**才真正开始（维护、文档、生态）。

⚠️ "fork 后大规模重写"实质就是自建，但背着一份不匹配的历史包袱。如果改造量接近重写，如实选自建。

## 先问上游的最小实验

很多决策**不问就是不可知的**：维护者愿不愿意接？是否已有人在做？是不是有意不做？

开一个 issue / discussion 提方案，成本约一天，能消除最大的不确定性。这是**行动项**，不是分析瘫痪的借口。

报告里必须写清三件事：

1. **问什么** —— 具体的 issue/discussion 措辞要点（描述用例 → 提出方案 → 问是否愿意接受 PR）
2. **在哪问** —— issue / discussion / 社区频道，遵守 CONTRIBUTING 的指引
3. **什么回答对应什么路径**：

| 上游回答 | 路径 |
|---------|------|
| "欢迎，提 PR 吧" | 上游贡献 |
| "有意思但我们没时间 review" | vendor + patch |
| "这不在我们的范围内" | 有扩展点 → 插件；否则 fork |
| "我们正在做" | 等待 + use-as-is |
| 长期无回应 | 印证维度 c/d 🔴 → vendor+patch 或 fork |

⚠️ 这一步由**用户**执行——本 skill 只读，不代为发帖（纪律 2）。
