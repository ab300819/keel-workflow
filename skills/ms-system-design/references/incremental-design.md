# 增量设计详解

本文档包含增量设计的详细规范，包括影响分析、兼容性评估、变更记录格式和检查清单。

## 目录

- 影响分析
- 兼容性评估
- 桥接策略边界判定（重构 / 命名变更 / 接口拆分类 ADR）
- 修订清单（嵌入方案确认步骤，强制）
- 设计变更记录（ADR 格式）
- 增量设计检查清单

## 影响分析

增量设计前必须进行影响分析：

### 变更范围分类

首先对变更进行范围分类，决定后续分析深度：

| 范围 | 特征 | 分析深度 | 文档要求 |
|------|------|----------|----------|
| **仅内部实现** | 不影响模块接口，仅修改内部逻辑 | 轻量：确认不影响接口即可 | 无需 ADR |
| **涉及模块接口** | 修改/新增 API 签名、参数、返回值 | 标准：完整影响分析 + 兼容性评估 | 更新 API 文档 |
| **涉及架构** | 新增模块、改变模块间依赖、数据模型变更 | 完整：全量影响分析 + ADR | 必须 ADR 记录 |

### 受影响文档自动识别

扫描变更涉及的 F-XXX/AC-XXX，自动列出需同步更新的文档：

1. 从变更来源提取关联的 F-XXX、AC-XXX 编号
2. 在以下文档中搜索这些编号的引用：
   - `01-requirements.md`（AC 定义）
   - `03-test-cases*.md`（测试用例引用）
   - `04-dev-tasks*.md`（任务引用）
3. 输出受影响文档清单 + 具体章节位置

```markdown
### 受影响文档

| 文档 | 受影响章节 | 需更新内容 |
|------|-----------|-----------|
| 03-test-cases.md | IT-003 | 接口参数变更，需更新测试输入 |
| 04-dev-tasks.md | T-05 | 依赖的接口签名已变更 |
```

### 影响分析示例

```markdown
## 影响分析：<变更名称>

**变更来源**：F-XXX / INS-XXX / 技术改进
**变更日期**：YYYY-MM-DD

### 受影响的模块

| 模块 | 影响类型 | 说明 |
|------|----------|------|
| UserService | 修改 | 新增方法 `resetPassword()` |
| AuthModule | 新增 | 新增密码重置模块 |
| EmailService | 无变化 | 复用现有邮件服务 |

### 受影响的接口

| 接口 | 变更类型 | 向后兼容 | 说明 |
|------|----------|----------|------|
| POST /api/auth/reset-password | 新增 | ✅ | 新接口 |
| GET /api/user/:id | 修改 | ✅ | 返回值新增字段 |
| POST /api/auth/login | 修改 | ❌ | 参数结构变更 |

### 受影响的数据模型

| 实体 | 变更类型 | 需要迁移 | 说明 |
|------|----------|----------|------|
| User | 修改 | ✅ | 新增 `resetToken` 字段 |
| PasswordResetLog | 新增 | ✅ | 新表 |
```

### 变更对比格式

对每个受影响的接口/模块/数据模型，使用统一的变更对比格式：

```markdown
**变更项**：<接口/模块/数据模型名称>
**变更前**：<原设计>
**变更后**：<新设计>
**原因**：<变更理由>
**影响范围**：<受影响的文档/任务/测试>
```

示例：

```markdown
**变更项**：POST /api/user/:id
**变更前**：返回 `{ id, name, email }`
**变更后**：返回 `{ id, name, email, avatar, preferences }`
**原因**：F-004 用户偏好功能需要返回新字段
**影响范围**：
- `03-test-cases.md` IT-003 需更新响应断言
- `04-dev-tasks.md` T-05 前端需适配新字段
- `01-requirements.md` AC-016 定义了 preferences 格式
```

## 兼容性评估

| 变更类型 | 向后兼容判断 | 处理方式 |
|----------|--------------|----------|
| 新增接口 | ✅ 兼容 | 直接添加 |
| 新增字段（可选） | ✅ 兼容 | 直接添加 |
| 新增字段（必填） | ❌ 不兼容 | 需要迁移计划 |
| 修改字段类型 | ❌ 不兼容 | 需要迁移计划 |
| 删除字段/接口 | ❌ 不兼容 | 需要废弃周期 |
| 修改接口参数 | ⚠️ 视情况 | 评估影响范围 |

**破坏性变更处理**：
1. 标注废弃（Deprecated）
2. 设置废弃周期（如 2 个版本）
3. 提供迁移指南
4. 在变更记录中说明

## 桥接策略边界判定（重构 / 命名变更 / 接口拆分类 ADR）

**问题背景**：默认采用 `@Deprecated` + 桥接 + 版本周期是已发布产品演进的常规模式；在**未发布产品**或**内部可控调用方**场景下，桥接策略会产生纯粹的中间状态成本（桥接方法 + 桥接 UT + 批次窗口监控 + 后续移除节点），违反"不为假设需求设计"。

**前置判定**（重构 / 命名变更 / 接口拆分类 ADR 必填）：

| 判定项 | 取值 | 影响 |
|--------|------|------|
| 当前 PRD / 产品是否已发布上线？ | ❌ 未发布 / ✅ 已发布 | 决定是否需要桥接策略 |
| 重构涉及的方法 / 类是否对外暴露？ | ❌ 仅内部 / ✅ 对外（HTTP API / RPC / SDK） | 决定向后兼容性约束范围 |
| 调用点能否在单 PR 内 grep 全仓改齐？ | ✅ 可控 / ❌ 视野超载 | 决定单 commit 硬切 vs 分批渐进 |

**决策树**：

```text
重命名 / 接口拆分 候选
    │
    ▼
1. 是否已发布上线？
    │
    ├── ❌ 未发布 ──────────→ 【直接硬切】单 commit grep 全仓改齐 + 老名残留 = 0
    │                          不引入 @Deprecated / 桥接 UT / 批次窗口
    │
    └── ✅ 已发布 ──→ 2. 调用方类型？
                       │
                       ├── 内部同 jar ─────→ 【直接硬切】（同发版周期内）
                       ├── 跨服务 RPC ─────→ 【@Deprecated 桥接 + 一个版本周期】
                       └── 公开 SDK / API ─→ 【@Deprecated 多版本周期 + 公开 timeline + changelog】
```

**规则**：
- ⛔ **禁止默认采用桥接策略**——必须显式回答上述判定项后再决定
- 决策结果须写入 ADR"决策"或"替代方案"段落（不必新增章节）
- 与"避免过度设计"约束（SKILL.md § 避免过度设计）配套：桥接策略本身可能就是"为假设需求设计"

## 修订清单（嵌入方案确认步骤，强制）

在 `/ms-system-design` 增量设计流程第 5 步"呈现变更方案 + 对抗性审查"中，**方案草案必须包含修订清单表格**，用户确认方案时一并确认清单：

```markdown
## 修订清单 (YYYY-MM-DD, 来源 F-XXX / INS-XXX)

| § | 章节 | 修改方式 | 一句话描述 |
|---|------|---------|----------|
| §4 | 模块设计：AuthModule | 改写 | 新增 resetPassword 组件 |
| §5.1 | IUserService.createUser | 局部调整 | 错误契约补充 RATE_LIMITED |
| §8 | 数据模型：User | 新增字段 | 新增 resetToken |
```

**规则**：
- "修改方式"枚举：`新增` / `改写` / `局部调整` / `重构`
- **最多 10 行**——超出说明变更范围过大，应拆成多次增量设计
- 清单**仅列章节+动作**，禁止拆细到子字段或子方法层级（避免形式主义）
- **⛔ 豁免路径**：如确无正文修改（仅决策补记），清单内需登记"仅追加 ADR 的理由"，否则不得进入"追加 ADR"步骤

## 设计变更记录（ADR 格式）

> ⚠️ **ADR 仅记录决策理由（WHY）**：为什么这样选。具体改了哪里（WHAT）由正文 diff 体现。**追加 ADR 不等于完成修订**，正文必须按修订清单同步更新。

增量设计完成后，在设计文档末尾追加结构化变更记录：

```markdown
### ADR-001: <决策标题>

- **状态**：已采纳 | 已废弃 | 已取代
- **背景**：<为什么需要做这个决策>
- **决策**：<选择了什么>
- **替代方案**：<考虑过但未采用>
- **下游影响**：<影响描述，非变更清单>
- **关联**：F-XXX / CON-XXX / INS-XXX
```

### 推翻 / 取代类 ADR 的强制影响回扫

> ⛔ **仅适用于推翻或取代既有决策的 ADR。** 普通选型 ADR 不填本表——这是防止它变成必填仪式的唯一闸门。

决策被推翻后，最贵的不是文档漂移，而是**留在旧世界的守卫脚本会主动阻塞正确的改动**：规约说不再需要某项配置，守卫脚本却仍把它当必需项，删配置就构建失败。现场表现是「构建失败」，极易被误判成自己改错了。

必填两字段：

```markdown
- **取代**：ADR-006（同时把 ADR-006 的状态改为「已取代」）
- **已知受影响制品**：

  | 类别 | 编号 / 路径 | 复查结论 |
  |------|------------|---------|
  | 约束 | CON-004 | 已改：授权级别 .readWrite → 整条删除 |
  | AC | AC-002 | 无需改 |
  | 任务 | T-01（✅ 已完成）| 已标 superseded_by: ADR-015 |
  | 守卫 | Scripts/verify-bundle.sh:14,18 | 已改：移除两项必需检查 |
```

**范围怎么来——三跳检索**（⛔ 不靠人凭记忆想）：

```sh
# 跳 1：直接引用点
grep -rn "ADR-006" docs/

# 跳 2：被取代 ADR 的「关联」字段列出的每个编号 → 查其定义处与全部引用处
#   （这一跳找到 01 §6 的 CON-004 规约，以及 04 里关联到它的 T-01）
grep -rn "CON-004" docs/

# 跳 3：走出 docs/ —— 上一跳得到的 CON 其「验证方式」指向的脚本
#   + 其关联任务卡的「涉及文件」
#   （这一跳才能找到 verify-bundle.sh，它内部并不含 "ADR-006" 字样）
grep -rn "# verifies:.*CON-004" .
```

> ⛔ **只能声称「已知引用」，不得声称「完整影响范围」。** 检索找不到从未登记、已改名、间接依赖或生成产物。表名就叫「已知受影响制品」，不叫「全部受影响制品」。
>
> ⛔ **不建 ADR→产物 反查索引文件。** 表就在 ADR 正文里，`grep -A20 "ADR-015" docs/devdocs/adr/` 即得反查。再建一张要手工同步的索引表，只会重演「编号状态表最大值漂移」那类失效——手工反向索引必然衰败。

详细 ADR 模板参见 [templates/design-template.md](../templates/design-template.md)

## 增量设计检查清单

- [ ] 已识别所有受影响的模块
- [ ] 已评估向后兼容性
- [ ] 破坏性变更已标注处理方式
- [ ] 已生成变更记录
- [ ] 新增内容已标注关联需求（F-XXX / INS-XXX）
- [ ] 已分类变更范围（内部实现/模块接口/架构）
- [ ] **已自动扫描受影响文档并列出更新清单**（跨文档偏差最易在此漏掉）
- [ ] 每个变更项使用统一的变更对比格式
- [ ] **已生成修订清单并逐条对应正文章节**
- [ ] **正文章节已按修订清单执行更新**（非仅 ADR 追加）
- [ ] **ADR 仅记录决策 WHY，不充当变更日志**
- [ ] **推翻 / 取代类 ADR 已填「已知受影响制品」表，且三跳检索留证**（普通选型 ADR 不适用）
- [ ] **被取代 ADR 的状态已改为「已取代」**
- [ ] **回扫命中的已完成任务卡已标 `superseded_by` + `⚠️ 已失效`**（⛔ 不删改其历史步骤）

> ⛔ "已生成变更记录" ∧ "已更新正文章节" **必须同时为真**，仅其一视为未完成。恢复方式：按修订清单执行正文更新，或登记"仅追加 ADR 的理由"。
