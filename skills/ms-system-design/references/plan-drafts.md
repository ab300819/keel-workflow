# 设计方案草案模板（初始 + 增量）

> 配合 `/ms-system-design` 使用。
>
> ⚠️ **两类内容不要混**：
> - **拍板界面**（下方「方向选择草案」）—— 只在**有岔路**时展示，只放需要人定方向的东西
> - **落盘内容**（边界自查块、模块/接口/数据表、原则校验、对抗审查）—— **恒定产出，直接写进 02 文档**，不进拍板界面
>
> 混在一起的后果是确认退化成走过场：人验不准结构与自查表，只会一路「行」，却留下「已确认」的记录。

## 边界自查块（恒定必答，写入文档，**不进拍板界面**）

L1~L4 逐层推进完成后，**以下块必须完整填写**（不允许空着或整体"跳过"），否则视为质量门退化：

```markdown
## 边界自查

### L1~L4 边界校验

| 层级 | 产出章节 | 边界检查 | 结果 |
|------|---------|---------|------|
| L1 架构 | §2 + §1 | 无模块级细节泄漏到架构图 | ✅/⚠️ |
| L2 模块 | §4 | 职责单一；"依赖接口引用"列格式合规 | ✅/⚠️ |
| L3 接口行为 | §5 | 无越界反例（7 类，见 design-boundary-guide.md） | ✅/⚠️ |

### 越界反例自查（决策 4 清单，L3 完成时强制）

七类越界反例的完整判据见 [design-boundary-guide.md](design-boundary-guide.md)，L3 完成时逐条自查。
```

## 初始设计 · 方向选择草案（仅在有岔路时展示）

一条岔路一块，通常 1~3 块。**没有岔路就不要展示这份草案**——直接产出文档。

```markdown
## 需要你定的方向

### 岔路 1：<一句话说清在选什么>

| | 走法 A：<名称> | 走法 B：<名称> |
|---|---|---|
| 怎么做 | <一两句> | <一两句> |
| 代价 | <慢在哪 / 贵在哪 / 以后难改在哪> | <同> |
| 什么时候会后悔 | <具体场景> | <具体场景> |

**我建议 A**，因为 <理由>。**如果 <条件> 成立，应该选 B。**

### 岔路 2：<...>
（同上格式）

---

### 我已经替你定了的（不用看，出问题我负责）

- <决策>：<一句话理由>
- <决策>：<一句话理由>

> 方向定了我就写文档。模块划分、接口契约、数据模型、原则校验和对抗审查都会做，
> 但那些直接进文档——它们的对错由 `/ms-verify --docs` 查，不用你在这儿判。
```

**写这份草案的三条纪律**：

1. **岔路必须是真岔路** —— 两条路都得站得住。凑不出第二条合理走法，就说明没有岔路，不该展示这份草案。
2. **代价要具体** —— 「性能较差」不是代价，「单机 QPS 上不去 2000，到时得拆」才是。
3. **必须给建议和理由** —— 把 N 个选项摊开让人自己挑，是把决策成本转嫁回去，不是外包。
