# 交叉验证（两个外部审查方）

两个外部审查方各自独立完成同一件事，协调方把意见对齐后给出一个结论。本文件是询问、调度、对齐、一方失败与摘要字段的**唯一出处**；审查方的具体命令见 [external-reviewer-integration.md](external-reviewer-integration.md)。

| 审查方 | 通道 | 备用 |
|---|---|---|
| codex | hcom 窗口实例 → T1（CLI）| T1b（备用计费后端）、T2（codex-mcp），规则不变 |
| agy | hcom 窗口实例 → `agy` CLI 非交互模式 | 无 |

窗口实例是首选送达方式（同一实例里连续对话，审查方能自己跑命令），不可用或中途卡住才落回命令行；启动、发消息、落回与事后检查见 [hcom-instances.md](hcom-instances.md)。

T3（同模型子 Agent）的触发条件以本文件 § 一方失败为准：**所选的外部审查方全部未成功**且用户同意时才用，折损标注规则不变。集成文档与 SKILL.md 里「T1/T2 失败 → T3」描述的是 codex 一侧通道用尽——此时 codex 记 `failed`，⛔ 不直接落到 T3。

⛔ 两票一致只提高可信度，不代替证据。⛔ 一方失败不得被静默吞掉。⛔ 轮次上限与熔断不放宽：一轮 = 一次并行调度。

## 询问审查方式

**先探测再问**：S2.5 开头先探测两方是否可用——窗口实例的前置条件按 [hcom-instances.md § 通道顺序与探测](hcom-instances.md)；命令行一层 codex 按集成文档 § 首选通道探测只测 T1、T2（⛔ 探测阶段不落到 T3），agy 按集成文档 § agy CLI 的检测。两层任一可用，该方就算可用。然后用 AskUserQuestion 问一次，三个选项各带后果：

| 选项 | 后果 |
|---|---|
| 双方共同审查 | 两方独立审、意见对齐后出结论；外部调用量约翻倍，耗时取较慢一方 |
| 只用 codex | 没有第二方参照 |
| 只用 agy | 单方；codex 额度紧张时可用 |

- 每次审查会话只问一次，复审轮次沿用首轮的选择（每轮口径一致，健康分才跨轮可比）。
- 用户在请求里已说明的不再问：「交叉验证」「两边都审」→ 双方；「让 codex 审」「只用 agy」→ 对应单方。
- 探测发现某一方本机不可用 → 不列含该方的选项并说明原因；只剩一方可用 → 不问，直接单方并告知。
- 选单方 → 走单方流程，跳过对齐；摘要 `single_reviewer: true`，另一方记 `status: skipped`、`reason: user_choice`。
- 无法提问（作为子 Agent 被调度）→ 按调用方传入的选择执行；未传入用单方 codex，且 codex 通道用尽时沿用改造前行为：降 T3 并标折损（额度耗尽仍报告并停下）。

## 并行调度

- 选双方时，**同一份 brief** 并行发给两方，互相不可见。并行的写法按宿主能力选（后台任务或并发工具调用）。结构化代码审查两方都用集成文档 § Adversarial Prompt 模板 + 同一个 schema。
- 「同一份」指提示词与材料内容相同，送达方式可以不同：窗口实例里两方都能自己跑 `git diff`；命令行方式下 agy 不能执行命令，diff 须先存成文件让它读（见集成文档 § agy CLI）。
- 每个审查方独立套用自己的通道、失败分类与截断判定。
- ⛔ agy 用的模型不得与宿主 Agent 同族，也不得与 codex 同族，否则「交叉」退化成自审。
- S4 展示时两方的完整原始输出**分别**展示，不合并、不过滤。

## 对齐

合并两方发现时判断是否同一问题：位置相同或重叠，且描述的是同一个缺陷。做法沿用 SKILL.md § S5「跨轮问题关联」的语义匹配。合并后重新编号 F-001…，每条带来源：

| 来源 | 含义 | S5 处置 |
|---|---|---|
| `both` | 两方都提了 | 与单方来源走**同一套完整验证**。来源只作信息展示，⛔ 不降低验证要求——两方可能共同误解同一条约束 |
| `codex` / `agy` | 只有一方提 | 完整验证，成立才确认 |
| `conflict` | 两方对同一处**明确表态相反**（一方说有问题、另一方明确说没问题，或修复方向互斥）| 协调方核对事实后判定并附证据；核不清的 ⛔ 不得自行拍板，交用户裁定（见下）|

- 一方沉默不算 `conflict`，算单方来源。
- **核不清的冲突怎么走**：S5 生成轮次快照**之前**，用 AskUserQuestion 逐条展示两方的对立观点与各自证据，请用户选：采纳 codex / 采纳 agy / 都不成立。裁定后该条落为确认、部分正确或驳回，再算健康分。`unresolved_conflict` 记交给用户裁定的条数。
- 来源只用于展示与排序：对齐表里 `both` 排前面并提示「两方独立得出」；单方来源提示另一方的盲区。
- 健康分、收敛检测、熔断在合并后的列表上计算，公式不变。

## 一方失败

| 情况 | 处置 |
|---|---|
| 一方成功、一方失败或截断 | 用成功一方的结果走单方流程；结论首行写明「本轮只有 <某方>，<另一方> 因 <原因> 未完成」；摘要 `single_reviewer: true` |
| codex 额度耗尽 | 先试 T1b。T1b 也不可用时：**agy 成功则不停下**，按上一行继续，结论首行照抄已耗尽的通道与重置时间 |
| 两方都未成功，或单方模式下所选的一方未成功 | 报告并停下：写明每一方的失败原因（额度耗尽的照抄通道与重置时间），由用户决定等待 / 换另一方（若可用且未试过）/ 降 T3（附折损说明）/ 换后端。⛔ 不自动降 T3 |
| 一方截断 | ⛔ 截断方的输出不进入对齐，不计为「该方没意见」 |

「报告并停下」只在**没有任何外部审查方成功**时触发：另一个外部审查方已成功时，继续不会降到同模型，没有检出率损失需要用户先同意。

## 摘要字段

`details` 新增：

```yaml
reviewers:                    # 每个审查方一项
  - name: codex | agy
    method: codex-hcom | codex-cli | codex-cli-alt | codex-mcp | agy-hcom | agy-cli | null   # 未启用该方填 null；中途落回的填最后实际产出结果的通道
    status: ok | failed | truncated | skipped
    reason: null              # 失败 / 跳过原因
single_reviewer: false        # true = 本轮实际只有一方（含用户指定）
agreement:                    # 合并后各来源的条数
  both: 0
  single_source: 0
  conflict: 0
  unresolved_conflict: 0      # 交用户裁定的条数
```

现有字段的含义：

| 字段 | 含义 |
|---|---|
| `review_method` | 两方都成功填 `cross`；只有一方成功填该方实际通道 |
| `primary_method` | 只描述 codex 一侧首次探测锁定的通道；未启用 codex（只用 agy）时填 `null` |
| `truncated` | 只在本轮**没有任何一方给出完整结果**时为 `true`。单方截断、另一方成功时为 `false`，截断记在 `reviewers[].status` |
| `quota_exhausted` / `reset_hint` | 任一方遇到额度耗尽即如实填写，不论另一方是否成功 |
| `degraded_detection` | 只在实际走了同模型子 Agent 时为 `true` |
