# 发现验证评判标准（Finding Verification Rubric）

## 概述

对外部审查者提出的每条发现进行独立验证，确保真问题得到重视、误报被有据驳回。

---

## 验证步骤

对每条发现（F-XXX），按以下步骤逐一验证：

### 1. 事实核查

读取发现中引用的具体位置（文件:行号、文档段落），确认：
- 审查者描述的代码/文档**是否真实存在**？
- 描述的行为**是否与实际一致**？
- 引用的位置**是否准确**？

如果审查者引用了不存在的文件或行号，直接标记为事实错误。

### 2. 上下文检查

评估审查者是否拥有足够的上下文：
- 审查者是否**缺少关键背景信息**导致误判？（如：不知道某个约束条件、不了解上游依赖）
- 审查者的判断在其**已知信息范围内**是否合理？
- 是否有**隐含的设计决策**审查者没有看到？

上下文缺失不等于发现无效——需要区分"因为不知道 X 所以判断错了"和"即使知道 X 问题仍然存在"。

### 3. 严重程度评估

| 级别 | 含义 | 判定标准 |
|------|------|---------|
| **P1** | 阻塞正确性 | 会导致功能错误、数据丢失、安全漏洞、或违反核心需求 |
| **P2** | 应修复 | 不会立即出错，但会导致维护困难、性能问题、或违反最佳实践 |
| **P3** | 建议改进 | 锦上添花的优化，可以接受当前状态 |

严重程度由验证方（当前 Agent）判定，可以与审查者的判定不同，但需要说明调整原因。

### 4. 可操作性评估

- 是否可以修复？修复方案是否清晰？
- 修复是否会引入新的风险？
- 是否需要更多信息才能确定修复方案？

---

## 判定类别

### ✅ 确认（Confirmed）

**条件**：事实核查通过，问题确实存在。

**必须提供**：
- **成因分析**：这个问题是怎么产生的？（如：遗漏了边界条件、复制粘贴错误、对 API 理解有误）
- **修复方案**：具体的修复建议，包括修改哪个文件的哪段代码/文档

### ❌ 驳回（Rejected）

**条件**：事实核查不通过，或上下文检查表明这不是问题。

**必须提供**：
- **反驳证据**：具体引用代码/文档，说明为什么这不是问题
- 不可仅说"不同意"或"这是设计意图"——必须展示证据

常见驳回理由：
- 审查者引用的代码/文件不存在或已过时
- 审查者缺少关键上下文（需说明是什么上下文）
- 审查者描述的行为与实际不符（需展示实际行为）
- 所谓"问题"是有意为之的设计决策（需引用设计文档或说明理由）

### ⚠️ 部分正确（Partial）

**条件**：发现的某些方面成立，某些方面不成立。

**必须提供**：
- 哪部分成立，为什么
- 哪部分不成立，为什么
- 针对成立部分的修复建议

### 🔜 推迟（Deferred）

**条件**：问题有效，但超出当前审查范围。

**必须提供**：
- 为什么推迟（超出范围、依赖其他工作完成、需要更多调研）
- 建议何时/如何跟进

---

## 验证证据要求

每条验证判定必须包含证据引用：
- 代码：`文件路径:行号` + 相关代码片段
- 文档：文档路径 + 具体段落引用
- 行为：命令输出、测试结果、或运行日志

没有证据的判定不可接受。
