# 实测协议(e2e-test-flow 私有)

> 本文件是阶段④⑤黑盒实测执行的协议权威:接口怎么找、写型用例怎么执行、数据库怎么只读观测、UI 怎么测、故障怎么注入、怎么判定、证据怎么脱敏。SKILL.md 只给四条纪律与路由概览,执行细节以本文件为准。

## 1. 接口怎么找:录制,不猜

用例文档(见 [case-ingestion.md](case-ingestion.md))不含接口信息——`steps`/`expected` 只描述业务行为,没有路径、方法、参数。找接口的优先级:

1. **浏览器录制真实请求(主力)**——走一遍用例步骤,用 `mcp__chrome-devtools__list_network_requests` 拿真实请求。**把"猜接口"变成"观测接口"**,与 D4(黑盒判定不依赖代码推断)天然契合。
2. **交叉校验**——用阶段③传入的 `{entry_path, http_method, priority}` 核对录制到的请求是否命中受影响入口;不命中不等于用例作废,先确认路由判断是否有误,再问用户。
3. **curl 样例兜底**——页面到不了的接口(如无 UI 入口的纯后端用例),用用户提供的 curl 样例给出请求头/代理/签名骨架,照此补齐实际请求。

**录制 ≠ 天然可重放**:录制到的请求可能带短时 token、CSRF、签名 nonce,或本身是 BFF 聚合出的临时凭据,直接重放大概率失败。首次重放前,先用一个**只读**请求(如 `GET`)验证能否复现;不行 → 改走浏览器实时驱动,或**问用户**要一份当下可用的请求生成方式(如刷新脚本、代理转发规则)。**不把重放失败当作被测系统的缺陷**——那是录制产物的时效问题,不是功能问题。

## 2. 写型用例执行规则

写型用例的执行规则以 [SKILL.md](../SKILL.md) 「写型用例三条规则」为唯一权威,本文**不复述**。

本节只补充 SKILL.md 未覆盖的内容:

- **附带写入无法避免**:审计日志、已读标记、会话状态这类伴随写型动作产生的附带副作用,不可能逐条单独确认,由**开跑前 run 级确认一次性覆盖**(见 SKILL.md「开跑前一次性确认」),不再逐条重复询问。
- **逐例判断只针对业务语义**:执行前的写/非写判定(见 [case-ingestion.md](case-ingestion.md) 副作用预分类)只看用例文本描述的业务动作是否变更状态,不把上述附带副作用计入判断。

## 3. 数据库只读观测(D1)

- **连接方式问用户**:`mcp__sqldev__run_query`、`mcp__idea__execute_sql_query`、项目自带 CLI 均可,由用户指定,要求提供**只读账号**。
- **授权粒度必须与 D4 相容**(黑盒子 Agent 不给 idea MCP、Bash 仅用于 curl):优先 `mcp__sqldev__run_query`(独立只读 server,与 D4 天然相容);若只能走 `mcp__idea__execute_sql_query`,**只授予该单个工具**,不得按 server 粒度授予其余 `mcp__idea__*`;若只能走项目自带 CLI,则该次 Bash 授权已超出「仅 curl」范围 → 报告须按 D4 标注 `isolation_level: best-effort`,**不假装 structural**。DB 只读工具**在派发黑盒子 Agent 时按需授予**,不进主 skill 的 `allowed-tools`。
- **只跑单语句 `SELECT`**:不用存储过程/函数(可能内含写)、不用显式事务。
- ⛔ **不做写探针**验证只读权限——尝试一条"预期失败"的写语句去确认账号权限,这个动作本身就是写,违反 D1 而不自洽。只能查权限元数据(如账号的角色/授权表),或采信用户声明;两者都拿不到 → **问用户**,不擅自尝试写探针。
- **观测时机**:写操作前、后各取一次,对比差异;**观测内容由用例预期驱动**——`expected` 提到哪个字段/表就查哪个,不 dump 整表。
- **观测可靠性**:共享环境下并发写入会干扰因果性判断,异步落库还需要等待落地。因此:用**专属测试账号**收敛观测范围、用**关联键**(订单号等业务主键)锚定要查的具体记录、异步场景**轮询到终态**(设超时,超时判 `BLOCKED`)。三者都做不到时,该次观测标为「**指示性而非结论性**」,**不单独作为 FAIL 依据**(需结合其他证据),或直接问用户环境是否具备观测条件。

## 4. UI 功能实测

- 浏览器 MCP 固定选 **chrome-devtools**(网络层 `list_network_requests`/`get_network_request` 是接口录制的主力工具;本仓 ms-board 已验证过其可用性)。
- **定位优先级**(承 D3「不改被测对象」):
  1. 页面既有锚点(可见文本 / `data-testid` / role + 可访问名)
  2. `take_snapshot` 返回的 `uid`
  3. 截图 + 坐标
  4. **最后手段**:`evaluate_script` 临时注入 `aria-label` 辅助定位——**transient**(只在当次会话生效)、**永不作断言依据**(只用于定位,不用于判定结果)、**必留痕**(记入报告说明用了此手段),并顺带产出「页面无障碍标注缺失」的缺陷建议给用户。
- 只做功能断言,范围以 SKILL.md「测试范围」表为准,不做视觉比对。

## 5. fault-injection

> **能力核实(2026-07-27)**:`chrome-devtools` 与 `playwright` MCP **都只暴露只读网络工具**(`list_network_requests` / `get_network_request` 等),**没有**请求拦截 / 响应篡改 / fulfill 能力。**"网络拦截"不是现成能力**,不得假设可以直接拦截/篡改响应来做故障注入。

据此,fault-injection 手段(**实现前必须先做能力探测,确认下列手段在当前环境实际可行**)按顺序尝试:

1. `evaluate_script` 给 `fetch`/`XMLHttpRequest` 打补丁,使其返回构造的失败响应——这是**注入**,**必留痕**(遵守 D3),要在报告中说明具体打了什么补丁。
2. 用非法参数触发系统的真实错误分支——最干净的方式,**无注入**,优先于方式 1。
3. 断网/超时模拟——粒度粗,只适合验证"整体不可用"类场景。

**三者都不适用 → 执行前判 `BLOCKED(无 fault-injection 执行路径)`,不进入执行,不假装测过**——不允许为了凑通过率而弱化验证方式或跳过能力探测直接下结论。

#### ⛔ 反模式:用"mock"一词绕过本节(真实运行中已发生)

**禁止用"mock"描述本流程的故障注入。** 2026-07-30 的首次真实运行里,15 条 TC-ERR 用例被以「需 mock 接口异常」直接判 BLOCKED,而报告中 `非法参数` / `evaluate_script` / `断网` / `能力探测` **全部零出现** —— 三手段一个都没试。

根因是"mock"这个词自带结论:**"我没有 mock 工具" → "所以测不了"**。但手段 1(非法参数)与手段 2(`evaluate_script` 打补丁)**都不需要任何 mock 能力**,`evaluate_script` 是现成工具。

**强制留痕**:判 `BLOCKED(无 fault-injection 执行路径)` 时,报告必须逐一写明:

```
手段1 非法参数:已试 / 不适用(原因:…)
手段2 evaluate_script 打补丁 fetch|XHR:已试 / 不适用(原因:…)
手段3 断网|超时:已试 / 不适用(原因:…)
```

三行缺任一行 → 该 BLOCKED **不成立**,须回去补做探测。报告中出现"需 mock""无法 mock""缺少 mock 能力"等表述,一律视为本节未被执行。

## 6. 判定

逐条比对 `expected`,给出 `PASS`/`FAIL`/`BLOCKED`/`OUT-OF-SCOPE` 之一,并附证据。**每个 PASS/FAIL 都绑定一个三元组**:`expected` **原文子句** + 观测证据(响应片段/SQL 观测/截图) + 比较规则(如何从证据推出与原文子句相符或不符)。

无法机械比较的预期(需要主观解释才能判定,比如表述模糊到无法直接对照证据)→ **自动 `BLOCKED(预期不可机械判定)`**,不允许"结合实现理解"之后放宽为 PASS。**禁止**用实现代码来解释"为什么这样的结果也算符合预期"(D4)——判定只能依据用例原文与观测证据。

### BLOCKED 的交付要求(与 PASS/FAIL 同等严格)

`BLOCKED` 不是"跳过"的同义词,它是一个**必须带出路的结论**。每条 BLOCKED 交付时必须齐备(定义与分级见 [SKILL.md「BLOCKED 不是终态」](../SKILL.md)、判据见 [case-ingestion.md](case-ingestion.md)):

| 字段 | 要求 |
|------|------|
| `tier` | `A`(用户当场能解)/ `B`(需环境改造)/ `C`(本流程永远测不到) |
| `blocker` | 缺什么,**具体到可操作**;"需构造数据"不合格 |
| `unblock` | 谁做什么能解开;`C` 级须给**替代路径**(转人工 / 修用例 / 改由集成测试覆盖) |
| `risk` | 这条挡住的是什么风险(若此处真有 bug,后果是什么) |

**`risk` 的意义**:BLOCKED 表示**无法判断此处是否有 bug** —— 不得假装判断,也不得暗示"没问题"。但必须让用户知道这条覆盖的风险量级,以决定是否投入解阻。

**报告中 BLOCKED 一律按 `tier` 聚类**(A/B/C),**不得**按阻断原因(需构造 / 写型 / 需异常)聚类 —— 后者对用户无行动价值。

**A 级须单独汇总成一份「用户可立即解阻清单」**放在报告显著位置(用户看完就能行动)。

## 7. 证据脱敏

落盘前默认脱敏,不等用户要求:

- 认证头(`Cookie`/`Authorization`)、签名字段、token/nonce → 替换为占位符。
- 交付给用户的 curl 用 `$AUTH_COOKIE` 之类占位符 + 一句填写说明,**不内嵌真实凭据**。
- 业务敏感数据(手机号/邮箱/地址等)按需打码,保留可用于判定的部分(如手机号仅打码中间四位)。
- 面板状态(见 [panel-protocol.md](panel-protocol.md))只存**证据引用**,不存敏感明文。
- 未脱敏的原始数据(若确实需要调试)只允许短生命周期存在系统临时目录,**不进入 HTML 面板**。

**证据结构**(供阶段⑥报告面板消费):

```yaml
kind: response | sql | screenshot | snapshot
ref: string        # 证据在临时目录中的引用(文件路径/片段标识),已脱敏
redacted: true     # 固定为 true,标记本证据已经过第 7 节脱敏处理
```
