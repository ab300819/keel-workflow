# 影响分析协议(e2e-test-flow 私有)

> 本文件是阶段③影响分析的协议权威,是 [SKILL.md](../SKILL.md) `D4` 中"白盒那一半"的细则。阶段③由白盒子 Agent 执行,产出结构及实际跨越隔离边界的范围见第 7 节。

## 1. 为什么不能只做 HTTP 签名 diff

真实的逻辑变更常常发生在 RPC/service 层,**HTTP endpoint 的方法签名可能毫无变化**——参数不变、路径不变,但内部调用的下游服务或计算逻辑已经改变。只对比两个分支的 HTTP 接口签名(方法名、参数、返回类型)会漏掉这类改动。因此阶段③做的是**影响分析**(改动的方法/类经调用链传导到了哪些顶层入口),而不是签名对比。

## 2. 入口锚点表(可配置)

| 入口类型 | 锚点 | 触发方式 |
|---|---|---|
| HTTP | `@RestController` / `@*Mapping` | curl 直接触发 |
| 定时任务 | `@Job` | 不能 curl → 集成测试腿 |
| RPC | `@Provider` | 间接:经消费方 HTTP 入口 |
| 其它 | 用户可补充的注解清单 | 按类型定 |

锚点清单可配置,允许项目补充自有注解(如自定义的消息消费者、网关路由注解等);**不写死 HTTP**,遇到表中未覆盖的入口类型问用户补充锚点。

## 3. 追溯链

1. `git diff <当前分支>...master`(覆盖工作区**全部项目**,而非仅当前项目)→ 得到改动的方法/类清单
2. **服务内**:对每个改动方法用 `mcp__idea__analyze_calls` **向上**追溯调用链,直至到达 `@RestController`
3. **跨服务**:若改动落在 `@Provider` 声明的接口/方法上 → 按接口名/方法名在工作区(可静态互搜的多项目)用 `mcp__idea__search_text` / Grep 搜索对应的 `@Consumer` 声明 → 从消费点再用 `analyze_calls` 向上追溯至消费方的 `@RestController`
4. 汇总第 2、3 步得到的受影响入口 → 映射到用例(阶段①摄取的用例集)→ 决定优先级

## 4. 证据优先级

若项目具备 RPC 注册表 / IDL 或代码生成物元数据 / 运行时调用链 trace,**优先采信这些证据**,它们比静态分析更准确;**静态注解搜索(第 3 节的 `@Provider`/`@Consumer` 文本匹配)是最弱一环**,只在缺乏上述证据时兜底使用。若项目提供 OpenAPI/Swagger,可用两分支的 spec diff 加速定位 HTTP 层变化(但仍需第 1 节的理由——spec diff 只覆盖签名层,不能替代调用链追溯)。

## 5. 解析失败的处置

以下场景会让追溯链在某一步绕不过去:接口继承、方法重载、按 version/group/alias 区分实现、动态代理、生成 stub、共享 SDK 封装、配置变更、消息投递(异步、非直接调用链)。

处置表:

| 情形 | 处置 |
|---|---|
| 搜不到对应 `@Consumer` | 判"影响未知" → **扩大到全量回归**,或**问用户**要人工映射 |
| 继承/重载/动态代理/version 歧义无法唯一解析 | 扩大到该契约的**全部已知消费方** |
| 改动落在共享契约/序列化器/拦截器等横切位置 | 视为**广域影响**,不尝试精确定位 |

> **铁律:影响分析永不用于缩小测试范围,只用于提升优先级。** 解析不出 → 导向"多测",绝不导向"少测"。

## 6. 退化

以下情况下影响分析**退化**:无 git 环境、用户要求跳过、需要全量回归。退化时按用例文档自带的 `priority` 字段排序(见 [case-ingestion.md](case-ingestion.md) 用例模型),流程照常跑,只是缺少优先级提升的依据。**影响分析是优化项,不是准入门槛**——退化不阻塞阶段④⑤执行。

## 7. 输出契约(过界约束)

阶段③白盒子 Agent 的产出结构(每个受影响入口一条),消费方分两层:

```yaml
entry_path: string          # 入口路径(如 HTTP 路径,或 @Job 的任务名)
http_method: string         # HTTP 方法;非 HTTP 入口留空或标注 N/A
priority: string            # 高/中/低,综合 git diff 影响范围与用例原生 priority
entry_type: string          # http / non-http / rpc
trigger_how: string         # 直接 curl / 集成测试腿 / 手动触发入口等
uncertain_reason: string?   # 可选,仅当第 5 节判"影响未知"或扩大范围时填写
```

- **阶段③产出结构(供编排层消费)**:以上 6 个字段全部提供给编排层,`entry_type`/`trigger_how` 供编排层选择阶段④⑤的调度腿(如 `non-http` 走集成测试腿),`uncertain_reason` 仅入报告供用户看。
- **实际跨越隔离边界、进入阶段④⑤黑盒子 Agent 的**:只有 `entry_path` / `http_method` / `priority` 三个字段(外加用例原文,见 SKILL.md `D4`)。`entry_type`、`trigger_how` **留在编排层**用于调度腿选择,**不过界**;`uncertain_reason` **仅入报告**,同样不过界。

**不过界清单**(以下内容一律不得跨界传给阶段④⑤黑盒子 Agent):

- 源码
- `git diff` 原始内容
- 调用链(`analyze_calls` 的完整路径)
- `@Provider` → `@Consumer` 的追溯过程
- 代码级参数签名推断
- 得出上述结论的推理理由
- `entry_type`、`trigger_how`(留在编排层用于调度腿选择)
- `uncertain_reason`(仅入报告)

判据:**能过界的必须是纯外部黑盒测试者本来就能获得的信息**——一个纯外部黑盒测试者只可能知道要打的路径、方法、以及测试优先级,不可能知道这是个 `@Job` 还是 `@Provider`(那是读注解才知道的信息)。因此只有 `entry_path` / `http_method` / `priority` 三项能过界,其余字段无论是否"看起来无害",一律留在编排层内侧。
