# 重写流程详情

当代码被判定为"不可测试"时，进入重写流程。

## 触发条件

```
进入重写流程的条件：
- 代码被评估为"不可测试"
- 重构后测试仍无法达到 80% 覆盖率
- 用户明确要求重写
```

## 重写流程

```
1. /retrofit 建立项目基线
   │
   ├── 输出：docs/devdocs/00-baseline.md
   ├── 关键是这两节 ——
   │     「代码外部的硬约束」：真实消费者 / 兼容范围 / 不可逆操作
   │                          → 重写**不能破坏**的东西
   │     「已知未知 + 证据冲突」：不确定项 + 确认前的安全默认动作
   │                          → 重写**不能随便改**的东西
   │
   ▼
2. ⛔ 与用户确认目标行为
   │
   ├── 重写的目标**不能从旧代码推导**
   ├── 从不可测试的代码推出需求、再照着重写，等于把现有行为
   │   连同 Bug 一起复制一遍 —— 而重写的全部意义正是不要那些
   └── 基线里标 `未知` 的行为，必须在这一步问清楚或明确「保持现状」
   │
   ▼
3. 走正常 keel 流程
   │   ⚠️ 这一步之后会遇到 4 处摩擦（红绿协议判保持性测试无效、静态核对无处挂编号等），
   │      绕法见 docs/workflows.md § 技术升级 / 重构 / 治理
   │
   ├── /requirements   定新需求（F-001 起，存量代码不编号）
   ├── /system-design  可测试的新设计
   └── /test-cases     测试方案
   │
   ▼
4. 测试先行 + 实现
   │
   ├── 覆盖率 ≥ 80%
   ├── 遵循 /code-quality MTE 原则
   └── UI 部分遵循 /ui-orchestrator
   │
   ▼
5. 迁移验证
   │
   ├── 功能对比测试：接口/入口清单对照 `docs/codebase-insight.md`（重扫可重建，正是它的地盘）；
   │                 外部契约对照基线「代码外部的硬约束」逐条验
   ├── 性能对比（如适用）
   └── 回归测试
```

> **重写前先补 characterization test**：基线不装行为清单（那是代码的投影，硬约束禁项），
> 所以「重写不能弄丢现有行为」这个要求要靠**测试**承载，不是靠文档。
> 先对现有行为写一批表征测试锁住它，再重写——这与「不把现有行为当需求」不冲突：
> 表征测试记录「它现在这样」，需求记录「它应该这样」，两者可以不一致，不一致处正是重写要解决的。

## 重写文档

重写时生成的文档：

```
docs/devdocs/
├── 00-baseline.md           # 基线：现状 / 外部硬约束 / 已知未知（重写的边界）
├── 01-requirements.md       # 与用户确认的目标行为（F-001 起）
├── 02-system-design.md      # 新设计（可测试）
├── 03-test-cases.md          # 测试方案
└── 05-refactor-rewrite.md   # 重写报告
```
