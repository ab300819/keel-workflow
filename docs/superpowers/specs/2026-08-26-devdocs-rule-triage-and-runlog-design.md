# DevDocs 重新审视：规则收敛判据 + 运行日志

## 0. 用户原话（逐字，不转述）

本方案起于用户的一段判断。任何后续评审以本节为基线，不以本文其余部分为基线：

> 随着大模型能力的增强，需要重新审视 devdocs 工作流并优化，否则不但没帮忙反而是倒忙，基于以下几点我的认知：

## 1. 判定

两条判断分开裁定。裁定依据是仓库现状实证，不是「模型变强了」这个前提——该前提**无法从本仓证明**（见 §8）。

### 1.1 第 1 条：成立，但理由要换

用户给的因果是「模型变强 → 可以简化」。本方案**不采用**这个因果，因为仓库里没有任何模型行为对照数据可支撑它。

### 1.2 第 2 条：一半成立

「角色」与「外置记忆+spec」基本是给现状换说法：

- 22 个 ms- skill 中已有 10 个声明角色 / 视角
- `代码=SSOT、文档=why 记忆层` 是 2026-06-08 已定的立场
- 跨角色只传 YAML 摘要 + 文件路径、各角色自行从文件系统接手，已在 `pipeline` 强制

真正有实质的是「**外包**」二字，而且不在于它像团队，在于它意味着：**只验交付物，不管过程**。这与现状恰好相反。它推出三个取舍：

1. skill 正文从「11 步怎么做」改写为「输入 / 交付物 / 验收证据 / 升级条件」，方法自主权归执行角色
2. 用户从流程共同操作者退回委托方，只在范围、风险、验收、不可逆决策处介入
3. 角色数量不等于独立性——Phase 1~3 是同一 Agent 切视角，只有 Phase 4 是真外部进程

⚠️ **必须同时接受的代价**：外包的质量上限等于验收能力。删过程门省下的预算必须投到 verify / 对抗审查一侧，否则「重新定位」只是单纯放松。

## 2. 保留判据（本方案的核心产出）

「保留核心」里的「核心」必须可判定，否则下一轮又会长回来——本仓历史上每一轮都长回来了。

判据复用 `ms-retrofit` 基线的**认知权威四分法**，把判官从「文档该装什么」换成「规则该留什么」：

| 规则性质 | 处置 | 例 |
|---|---|---|
| 模型默认就会做 | **删** | 「务实优先不过度设计」；「统一中文回复」重复 24 处 |
| 模型默认会**做错** | **留**——全部价值所在 | 测试不可变；信息屏障；代码优先于文档；沉默不升格；根因未证实不得修复 |
| 模型**无从知道** | **留** | 编号体系；文件路径；握手 schema；安全与授权边界 |
| 凑数配额 / 一刀切阈值 | **删** | SOLID 适用下限；每功能点至少 1 个 IT；所有任务 ≤4h |

第二行是这套体系的真正资产：它们全是**纠偏护栏**，对抗模型的稳定倾向（改测试而非改实现、把代码现状当成应然、用推测填空白）。模型变强不削弱它们，反而因更自信而更需要。

### 2.1 「零触发」的两种，处置不同

- **经验性零触发**（跑了很多次，没见它拦过东西）→ 进**观察名单**，不进删除名单。频次分不出「废的」与「因为写在那儿所以没人违反」。
  - ⛔ **在有 ablation 数据之前，不得以「它没用」为理由删除经验性零触发项。** 唯一能分开这两者的手段是「关掉它、重跑、看 delta」（外部实证见 §11.4：`no_steps` 与 `no_nudge` 触发率都低，一个是废的一个是承重墙，**触发计数看不出区别**）。
  - ⚠️ 但这条**不等于「留着不动」**：不触发的**代码**护栏成本≈0，不触发的**文字**规则每次读入都占上下文、抢注意力（§11.6 的成本不对称）。因此零触发项仍应承担常驻成本的处置——合并同类、移入 `references/`、`⛔` 门控降为普通条目——**这些都不是删除**，不受本条约束。
  - ⚠️ 推论：C1「对存疑堆定向埋点」若只埋触发计数，**产不出删除决策所需的证据**。本仓无 eval harness、无场景集，且无法在同一次真实会话里跑 A/B —— 故本方案**只立此判据，不建 ablation 台**。不做的后果：观察名单长期是观察名单，减量能力停在此处；但这好过靠感觉删掉承重墙。
- **结构性不可能触发**（判据引用的状态根本无法出现）→ 可删。例：E2 的 `*_PENDING` 提交门——该枚举值已被删除，此门永远不可能触发。

> ⚠️ 反例：`on_incompatible: block` 的 layout drift 检测**不属于**此类。layout.v2 将被实现（§6），届时判据可真实触发；它属于「尚未启用」，不是「不可能触发」。

⛔ 不得把结构性判据套用到经验性零触发上——那是本方案最容易被误用的一条。

## 3. 运行日志（runlog）

### 3.1 为什么需要，以及先读再埋

用户的顾虑成立：`skill` 正文里读不到项目实际过程与形态。但**最高价值的埋点已经埋好了，从未被读过。**

`dev-workflow` / `pipeline` 定义了 11 种 commit trailer，其中 5 种在语义上就是「我绕过了这道门，理由如下」：

| trailer | 记录 |
|---|---|
| `Profile-Downgrade-Reason` | 风险分档被人为降档 |
| `Skip-Trace-Reason` | 追溯校验被关闭 |
| `SSOT-Lint-Skip-Reason` | SSOT 检查被跳过 |
| `Pending-Reason` | 审查被延后 |
| `Exploration-Mode` | 整套文档强制被豁免 |

这些是强制字段，写进 commit message，进 git，事后改不掉。**「哪些门与现实不符」的答案一直躺在 `git log` 里**：一条被规律性绕过的门就是一条设计错了的门。此项零新增成本，只需要一个读它的动作。

### 3.2 硬边界：不能埋什么

⛔ **禁止让 agent 自报合规。** 不得新增「本次是否遵守了 X」「跳过了哪些步骤」「这道门是否有用」一类字段。

判据与 `ms-retrofit` 废弃逆向推导同源：**被测者书写测量记录**。一个无视了 `⛔` 的模型同样不会记录「我无视了 `⛔`」——该失败模式在构造上即静默，采集结果会系统性偏向「遵守良好」。拿这种数据做删除决策**比没有数据更糟**。

### 3.3 三档证据，只建前两档

| 档 | 性质 | 建否 |
|---|---|---|
| 1 | 不可伪造：commit trailer、测试退出码、文件 diff、时间戳——干活的副产物，非供词 | ✅ |
| 2 | 半可信可交叉校验：`yaml-summary-v1` 信封。自报，但 `output_files` 可对 git diff 校验、`blockers` 可对「流程是否真的停下」校验 | ✅ |
| 3 | 纯自报、无交叉校验面 | ❌ |

### 3.4 最小实现

**唯一改动是「别把已有的东西扔掉」。** 现状：每次子 Agent 返回的 `yaml-summary-v1` 在编排器上下文里过一遍即蒸发。

- **路径**：`<docs_dir>/devdocs/.runlog.yaml`
- **格式**：多文档 YAML 流，每条记录以 `---` 分隔
- **写入方**：编排器，在收到子 Agent 摘要之后
- **内容**：`yaml-summary-v1` 信封**逐字原样**，追加两个键：
  - `ts`：ISO 8601 时间戳
  - `entry`：**用户的原始措辞**（不是归一化后的命令）。§5.5.3 使其成为授权推断的审计线索，故必须逐字保存

⛔ **不新增字段、不新增 status 值、不改信封。** 私有统计一律走既有的 `summary.details`。

选 YAML 多文档流而非 JSONL：写入方是负载下的 LLM，它本就在产出这段 YAML，零转换零转义风险；聚合端的便利性让位于写入端的可靠性。

**首条记录**为形态指纹（`type: shape`），专答「形态你读不到」：

```yaml
type: shape
lang: <取自 codebase-insight.md frontmatter 的 tech_stack，缺失则 null>
mode: <取自 workspace_context 的拓扑 mode>
scale: <"<5k" | "5k-50k" | ">50k" 三档，一次性计算>
created_at: <ISO 8601>
verdict_due: 2026-11-30
```

⛔ **不得为写 runlog 而发起扫描。** 形态字段只从已有产物读取，读不到就写 `null`。

有了形态指纹，跨项目读 N 次运行才能区分「这条门普遍无用」与「这条门只对某类项目无用」——一刀切配额（所有任务 ≤4h、每功能点 1 个 IT、SOLID 适用下限）的存废恰好全押在这个区分上。

### 3.5 纪律

- ⛔ **runlog 不设门禁。** 写失败即静默跳过，**不得**因埋点未写成而阻断任何流程。否则它会成为第 303 道 `⛔`，然后被绕过，然后需要埋点来测量埋点。
- **随 Commit 2 提交**（文档提交，已存在），不新增提交机制。合并冲突按 append-only 取并集，配 `.gitattributes` 的 `merge=union`。
- 产物写在 `docs_dir` 下，三种拓扑一致，不触碰任何代码根，符合零污染红线。

### 3.6 判决点（本方案唯一的自毁开关）

本仓病史是**造了机器就再也不删**。因此 runlog 自带保险丝：

> **判决点 = 累计 60 条 task 级记录，或 2026-11-30，孰先到。**
> 到期读一次，然后二选一：**依据它删规则**，或**删它自己**。
> 到期未读，本节自动作废，`.runlog.yaml` 应被删除。

判决点日期同时写在文件首条记录的 `verdict_due` 与 `AGENTS.md` 的「当前状态」中——后者每会话都会被读到，是零机器成本的提醒方式。

⛔ 不为此新建检查器、不接入 `realign --scope=health`。诊断是「机器太多」，新增的机器必须比它测量的对象小一个数量级。

### 3.7 能问与不能问

| 问题 | 数据能答吗 |
|---|---|
| 哪些门被规律性绕过 | ✅ 今天即可答，在 `git log` 里 |
| 门触发后是否真的改了东西 | ✅ blocker 记录 → 后续 diff 是否触及该处 |
| 哪些门从未触发 | ⚠️ 能测频次，推不出无用——见 §2.1 |
| 模型是否遵守了规则 | ❌ 不可测，见 §3.2 |

### 5.3 词汇碰撞

两套并行的「档位」词汇，同名不同义：

| 位置 | 词汇 | `fast` 的含义 |
|---|---|---|
| `ms-feature` / `ms-pipeline` | `--fast` / `--lite` / `--deep` | 跳过逐步确认 |
| `ms-dev-workflow` | `review_profile: fast \| guarded \| audit` | 独立审查延后到 drain |

同一个词在同一条流水线的两个阶段指两件不相干的事。

### 5.4 关键技术事实：没有解析器

⚠️ **这些子指令不被任何程序解析。** skill 是 Markdown，`/ms-verify --impl` 的参数作为纯文本进入上下文，由模型对照 SKILL.md 的表格自行理解。

即是说：**flag 早已是自然语言，只是一种需要用户背诵的蹩脚方言。** 它不换来确定性，只换来记忆负担——这正是用户「人压根儿不会显式触发，而且也不知道」的成因。

本方案主张的方向**已在库内跑着**，有两处先例：

- `ms-verify` 正文明写：「除 `--live` 外，二级控制（`--layer1/2/3`、`--ac`、`--design`、`--trace`、UI 阶段选择）**不作为顶部用户面入口暴露**；用户用自然语言表达聚焦意图。」——这正是 §5.5 判据的完整实现，且已运行
- `requirements/SKILL.md` 写着「**LLM 自动判断**：用户表达『快速通过 / 少确认 / 直接生成』等意图时，自动启用快速通过语义」——同一条轴，`ms-requirements` 用推断，`ms-feature` 用 `--fast`；推断那一侧不需要用户知道任何词

因此 §5.5 不是新机制，是把已有做法**推广到尚未采用它的 skill**。这也把改动风险从「引入新范式」降为「对齐既有范式」。

### 5.5 判据：用户面零子指令

**用户裁定（2026-08-26）**：

> 子指令对于用户而言没有意义，用户不知道，也不会显示触发

据此**推翻本方案原先的四分法在用户面保留「授权 / 安全」类 flag 的结论**。理由三条：

1. **用户不打，该 flag 就从不生效** —— 保留它不保护任何东西，只是留着一个没人用的词
2. **「授权不可推断」被我写错了含义。** 它的正确含义是**模型不得自行给自己授权**，不是「用户必须打对某个词」。用户说「不用问我，跑完为止」就是明示授权——来源是用户，只是没采用 flag 的形式
3. **缺省即最保守档。** 没有明示就按需确认。因此撤掉 flag 不引入风险，只是让「升格」必须由用户开口

### 5.5.1 不可逆操作：改得更严，不是更松

⛔ **`--apply` / `--dry-run` / `--force-*` 一类不再作为入口 flag，改为在动作发生的那一刻就地确认。**

判据：**20 分钟前在命令行打的一个词，是比动作当下的确认更弱的同意。** 它无法反映用户看到 dry-run 结果之后的判断，也无法覆盖执行中途才暴露出的不可逆性。撤 flag + 就地确认是**净安全增强**，不是放松。

⚠️ **触发面不止「不可逆」**（外部评审指出的缺口）。就地确认须覆盖三类，缺一即漏：

1. **不可逆 / 外发**：写代码根、删除、推送
2. **降低验证强度**：审查档降级、跳过前置验证、审查延后到 drain —— 这类**技术上完全可逆**，但后果是「本次交付没被审」，`review_pending` 已随 Commit 1 落盘
3. **写入版本控制的持久决策**：如 `.devdocs-realign-ack` —— 用户说的是「这次先别升级」，落盘的却是永久静默

⛔ 只按第 1 类设计确认点，第 2、3 类会静默通过。

### 5.5.2 三层处置

| 层 | 处置 |
|---|---|
| **用户面** | **零子指令。** 能力以散文写在 skill 正文与 `docs/workflows.md`；意图、偏好、授权一律自然语言 |
| **编排器 ↔ 子 Agent** | **协议参数保留**（`--from-prd` / `--review-drain` / `--schema-drift` / `--update-design` 等）。它们从来不是用户面的，是委托握手的一部分，删了会破坏协议 |
| **动作当刻** | 不可逆 / 外发 / 越权操作**就地确认**，不依赖入口 flag |

⛔ **删的是语法，不是能力。** 全部能力保留，只是改以散文描述；消失的仅是「用户必须打对某个词」这条强制语法。

### 5.5.3 残余风险与缓解

自然语言识别授权，会在两个方向上失败：

| 失败方向 | 后果 | 缓解 |
|---|---|---|
| **漏认**（用户授权了，模型没识别出来） | 多问一次 —— 烦，但安全 | 不缓解，接受 |
| **过度识别**（模型把偏好当成授权） | 危险 | 缺省保守 + §5.5.1 就地确认 + runlog 记录用户原话（§3.4 `entry` 字段），判决点可回读校验误判率 |

`entry` 字段因此从「顺手记一下」升级为**授权推断的审计线索**：它保存用户的原始措辞，使「模型当时凭什么认为被授权了」在事后可复核。这是本方案里 runlog 唯一承担安全职责的地方。

### 5.5.4 归一化层（外部评审后新增，本方案唯一的新增机制）

外部评审给出 5 个具体失效场景，全部指向**同一个根因**：

> **模式与授权的决定必须活过「用户说话的那一刻」**——穿过子 Agent 边界、穿过断点恢复、进入版本控制状态。flag 是一个载体；自然语言在入口处**没有载体**。

| # | 场景 | 失效方式 |
|---|---|---|
| 1 | `--review-profile` | 「这次快点、少确认」同时命中两条轴：`ms-feature` 的少确认 与 `ms-dev-workflow` 的审查降档。误认后 Commit 1 直接落盘为 `review_pending` |
| 2 | `--force-code-docs` | `explicit_opt_in` 下唯有此 flag 允许写代码根。握手无「用户授权」字段（`constraints.md:117`），深层子 Agent 只看到 `explicit_opt_in` → 该做的不做；编排器代为转述 → 不该做的做了 |
| 3 | `--no-realign` | 写入受版本控制的 `.devdocs-realign-ack`。「这次先别升」可能被落成永久静默；保守不写则 headless 无法继续（`pipeline/SKILL.md:209`） |
| 4 | `--no-report-file` | `--dry-run` 本就会写 `.health-report.md`；严格零写入需额外 flag。「只检查不改」映射成普通 dry-run 即产生未授权文件 |
| 5 | `--from-prd` | 已有 `01` 时，「同步更新后的需求」会落进普通增量模式，丢失 `remapped` 审计链与原地更新语义 |

**解法不是把 flag 放回用户面**——用户依然不会打。解法是**把载体从用户面语法移到握手**：

```text
用户自然语言表达
      │
      ▼
编排器归一化 ──── 歧义？ ──→ 问一次（且只问一次）
      │                          │
      ▼                          ▼
显式协议参数 ←────────────── 用户裁定
      │
      ├──→ 写入 Task 握手（子 Agent 只读归一化字段，不读用户原话）
      └──→ 写入 runlog `entry`（保留用户原话，供事后复核误判率）
```

三条硬规则：

- ⛔ **子 Agent 不得自行解读用户原话。** 它只读归一化后的协议参数。原话只进 runlog 作审计线索，不作执行依据
- ⛔ **归一化结果必须随断点恢复一同持久化**，否则续做时模式丢失
- ⛔ **歧义只问一次，答案落盘。** 反复追问等价于把 flag 的记忆负担改成了对话负担

§5.5.2 的三层因此调整为：**上表 5 个 flag 由「用户面（删）」改判为「协议面（留）」**，它们从此只出现在编排器与子 Agent 之间，用户永远不需要知道它们存在。

⚠️ **诚实标注：这是本方案唯一新增的机制**，与 §7「不新建机器」存在张力。理由：没有载体，§5.5 就不安全——外部评审的 5 个场景是构造性的，不是假想。作用范围限定为**握手加一个归一化字段**，不是新子系统；`yaml-summary-v1` 信封仍不改（握手是 `constraints.md` §3，与 §2 的摘要信封是两件东西）。

⚠️ **退路**：若归一化层在实施中被发现成本超出预期，正确的回退是**把这 5 个 flag 留在用户面**，而不是让它们无载体地消失。宁可留 5 个没人打的词，不可留 5 个静默失效点。

### 5.6 与 §2 的关系

§2 四分法管**规则**，§5.5 管**接口**。形状同源：模型能自己推断的删掉，模型无从知道或会推断错的留下。

差别在于安全边界的落点不同 —— §2 里它是**留下的规则**，§5.5 里它**不落在入口语法上，而落在动作当刻**（§5.5.1）。

### 5.7 代价

- **失去 grep 能力**：本仓治理动作依赖对 flag 名的检索。用户面 flag 清零后这部分统计面消失；协议参数仍可检索。判决点读数改依赖 runlog 的 `entry` 字段，而非 flag 出现次数
- **委托精度不受影响**：协议参数整类保留（§5.5.2 第二行），编排器写 `/ms-verify --review-drain` 仍然精确
- **档位误判静默**：偏好类判断错了不会报错。缓解同 §5.5.3——runlog 记录用户原话与实际档位，判决点回读
- **文档要重写**：`docs/workflows.md` 现以 flag 表格组织，须改为能力散文。这是本方案工作量最大的单项

## 7. 不做什么

- ❌ 不做一次性大改。判定的可靠部分是「规格自相矛盾」，**不是**「删了会更好」
- ❌ 不新增任何 `⛔`。本方案净减少门控数量，runlog 本身不设门

## 8. 本方案证不了什么

⚠️ **仓库能证明「规格已重复、过细、自相矛盾」，不能证明「删减后模型表现更好」。** 无执行统计，无 A/B 对照。

这一点在 §1.1 已体现为「换掉用户给的因果」。它也是 §3 存在的全部理由：runlog 就是为了让第 1 条从**判断**变成**可证伪的命题**。

⚠️ **§11 的外部证据只部分替代这里缺的数据，且替代的不是「删减后更好」那一半。** 它替代的是「该留的是什么形状」（门控 vs 劝导文字）与「四分法第一行成立」；「本仓删减后模型表现更好」仍无本地对照，且按 §11.3 不得用该文献冒充。

判决点到期时，若数据显示被绕过的门寥寥、零触发的门也确实在起预防作用，则第 1 条的「简化」部分应被**部分撤回**，而非硬推。本方案预先接受这个结局。

**判定：它佐证的是 §2 四分法本身，不是「模型变强所以可以简化」；并对 §0 第 1 条后半句「不要过度干预大模型行为」构成反证。**

### 11.1 论文做了什么

Forge 是一层**与工具无关的执行时护栏**——rescue parsing（从散文里救出工具调用）/ retry nudge（没产生有效调用就注入纠正消息重试）/ step enforcement（提前跳到终止工具就推回）/ error recovery（工具报错喂回模型，**且不标该步完成**）/ context compaction / VRAM budgeting，每层可独立开关。

评测规模：9 场景 × 2 模式 × 50 次 = 900 trials/cell，50+ 配置（本地 7B~14B × 4 后端 × 2 量化，对照 Haiku 4.5 / Sonnet 4.6 / Opus 4.6），统一温度 0.7 作实验控制。核心手段是**逐层 ablation + McNemar 配对检验**。

### 11.3 形状错配（引用本文献时的硬边界）

⛔ **不得用本文献论证「SKILL.md 可以简化」。**

论文的 guardrail 是**框架代码里的执行时拦截**：检测 → 注入纠正消息 → 重试 → 失败则不标步骤完成。本仓的「规则」是**写在 SKILL.md 里、靠模型自愿遵守的文字**。论文对后者**没有任何数据**，它测的是「模型能不能被外部机制救回来」，不是「模型能不能读懂 900 行提示词」。

它能证明的是**该留的东西是什么形状**：不是「你必须做 X」的条文，而是「X 没做到时流程停下」的机制。按此回看，`gate/two-senses` 的两种语义得到外部支持——**门控（有阻塞态 + recovery）是论文验证过的形状，禁令与劝导文字不是**。四分法第二行的 K1 恰好都是门控。

### 11.4 唯一可迁移的方法论：ablation 能分开 §2.1 的两种零触发

§2.1 卡在「频次分不出『废的』与『因为写在那儿所以没人违反』」。论文给出解法：**关掉它，重跑，看 delta**。

关键在于 `no_steps`（n.s.）与 `no_nudge`（-45.8）**触发率都低，但一个是废的一个是承重的**——这个区别**光看触发率看不出来**，必须靠 ablation。这正是本仓目前缺的唯一工具，也说明 C1「定向埋点」若只埋触发计数，**无法产出删除决策所需的证据**。

代价：900 trials/cell × 5 配置。本仓无 eval harness、无场景集，且无法在同一次真实会话里跑 A/B。⚠️ 因此本条**只更新判据、不建台**，见 §2.1 修订。

### 11.5 针对现役流程的三条具体发现

论文的 error recovery 定义有两半：**喂回错误** + **不标该步完成**。逐条对照本仓：

| # | 论文对应 | 本仓现状 | 判定 |
|---|---|---|---|
| G1 | error recovery（喂回 + 不标完成） | `task/failed-contract` + `task/blocker-propagation` 已强制；`dev-workflow` S8 有「声称 vs 实际 diff 交叉验证」 | ✅ **已具备**。论文最普适的一条本仓不缺 |
| G2 | §2.2 `ToolResolutionError`：「工具执行成功但请求的数据不存在」与「成功且返回数据」无区分，编排器两种都标完成 → 静默级联 | `output_files` 是保留字段，但**全仓没有任何规则要求编排层核对它是否真的存在**。子 Agent 报 `success` + 一串路径，编排层无条件相信，下游按 constraints 强制「自行从文件系统接手」→ 读到不存在或旧版文件 | ⚠️ **同形缺口**。§3.3 档 2 已声明「`output_files` 可对 git diff 校验」，但从未成为规则 |
| G3 | retry nudge（最大单项 -24~-49）= 输出不是有效调用时纠正并重试 | `task/yaml-summary-required` 只写「必须以 yaml-summary-v1 返回」，**未定义违反时编排层做什么**。它不是门控（无阻塞态、无 recovery），也不是禁令 | ⚠️ **缺 recovery 的要求**。论文说这一类是承重墙 |

⚠️ **G2 / G3 的修法与 §7「不新增任何 `⛔`」冲突**，且 G2 的修法是给 `success` 加一条判据（`output_files` 每项须实际存在，否则降 `failed`），属协议层 SSOT 改动。**本方案不自行执行**——记录为发现，处置交用户。不做的后果：两处静默级联保持现状，且都发生在编排层，出错时表现为「下游 skill 读到旧文件却报 success」，事后从 `git log` 读不出来。

### 11.6 本文献自身的效力边界

⚠️ 5 页 demo paper，单作者，N=50/cell，统一温度 0.7（原文明说**不是** peak per-model 表现），场景集自建、非 BFCL，明确列出未覆盖项（并行调用、长上下文检索、多轮用户交互）；致谢称「Development was assisted by Claude Code」。

因此：P1/P2/P5/P6 的 ablation 结果是本文献中**方法最扎实**的部分（配对检验 + 置信区间），可引；P4 的绝对数值随场景集变化，只可引方向不可引数字；Finding 1/2/4/5 与本仓无关或只作旁证。

⛔ **最不可迁移的一条**：论文替低频护栏辩护的那段——「单次失败的不对称代价，使得即使统计贡献很小也值得把 latent guardrail 留在栈里」——**不得迁移到文字规则上**。Forge 的 latent guardrail 是**不触发就几乎零成本的代码**；一条不触发的 Markdown 规则**每次被读入都在花上下文预算并分散注意力**。成本结构不同，结论不能照搬。（本条由 2026-09-07 的外部独立调研指出，本方案初稿的 §2.1 曾犯这个错，已回修。）

### 12.2 裁定不做

- ❌ **再来一轮凭直觉的大删。** 上一轮的实测代价：222 删 → 恢复 11（**5.0%**），且 11 条里**只有 2 条是外部审查发现的**，9 条靠机械验证捞回（`docs/audits/2026-08-26-rule-triage.md:664-684`）。审查替代不了验证。
- ❌ **把 Markdown 规则整体改成脚本 / hook。** 编号扫描、死链、字节数适合机械化；需求语义、设计权衡、用户授权仍需模型或人判断。把语义判断伪装成 lint 只会得到更硬的误判。
- ❌ **调大 `project_doc_max_bytes` 来解 AGENTS.md 超限。** 那解的是「必要指令被截断」，不是「内容价值低」。先删常驻历史。
- ❌ **按 X 帖删测试要求。** 「新模型会自己跑测试」无基线，且与 doc1「必须给 agent 可读的验证信号」冲突；本仓跨模型跨客户端。
