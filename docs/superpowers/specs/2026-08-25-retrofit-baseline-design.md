# ms-retrofit：逆向推导改为建立项目基线

## 0. 问题（用户原话）

1. 「逆向出的用户 us 和 ac 压根没啥用，还浪费 token」
2. 「不如把逆向动作改为建立项目基线，后续使用 devdocs 维护」
3. 「基线怎么建立，委托读代码 skill 经一次项目摸排，带着这个项目是？解决什么问题？当前是什么状态？去建立基线」
4. 「“简化”就是把当前代码当作事实原，无需额外建立事实文档」
5. 「baseline 文档是必要的，相当于读代码做的『笔记』，只是之前建立的 us、ac 等不需要」
6. 「贴近 SSOT，尽可能少的文件，不然太分散了」
7. 「3.1 我觉的得先推导并调查，然后有不确定的在问用户」
8. 「现实场景，一个项目我中途接手，其实我很多都不知道」
9. 「而且接手的项目文档并不一定权威可靠可信，但是代码是实打实的」
10. 「它的消费对象仍然是大模型，当然人也会看……实事求是如果不需要基线文档也可以去掉，但是要考虑如何接手已有的项目」

## 1. 逆向产物为什么没用

### 1.1 推的是 what，而 what 的 SSOT 是代码

现行 `references/new-project-retrofit.md` Step 4 的推导表：

| 分析对象 | 推导为 |
|---|---|
| 路由 / 页面 | F-XXX |
| API 端点 | 归属 F |
| 测试描述 | US-XXX |
| 测试断言 | AC-XXX |

它给出的样例是：

- `US-001: 作为用户，我可以注册新账号`（来源 `POST /api/users`）
- `AC-001: 邮箱格式正确时注册成功`（来源 `auth.test.ts: "should register with valid email"`）

前者是把端点换成用户故事语法重说一遍，后者是把测试名换个说法。**信息量为零**——两条结论的原始出处（路由表、测试文件）都在仓库里，且都是 SSOT。

更严重的是它构成**循环论证**：

```text
测试断言 ──逆向──> AC ──追溯──> 同一条测试证明该 AC 已覆盖
```

而 `ms-test-cases` 的原则恰恰是「测试从需求推导，不是从代码推导」（[test-cases/SKILL.md](../../../skills/test-cases/SKILL.md):53）。逆向把这条原则倒转过来跑了一遍，产出一个**必然 100% 的追溯率**——它证明不了需求正确或完整，只证明测试等于测试。漂亮的覆盖率数字比浪费 token 危险得多。

附带后果：AC 由测试断言反推，会把**已有 Bug 的现状行为固化成验收标准**。

### 1.2 零信息量的编号是负债，不是中性

编号不是标签，是**权威身份**。一旦 `AC-012` 存在：

- `ms-verify` 把它当验收锚点核对
- `ms-board` 把它渲进评审页
- 追溯矩阵 F→US→AC→测试 把它算进覆盖率

于是「没人真正决定过的东西」获得了和真实验收标准同等的地位，并进入维护成本。这比不生成更糟。

### 1.3 真正该记的东西，逆向恰好推不出来

「为什么存在、解决什么问题、现在什么状态、哪儿有坑」——四问全部无法从代码推导。现行流程对此的处理是在报告末尾写一句「推荐先用 `/ms-requirements --context`」把它踢给下游。

值得注意的是，现行 `templates/retrofit-report-template.md` 的「下一步建议」里已经写着「**必须**执行以下之一**建立基线**」。**「基线」是这个 skill 里已有的词，只是被推到了下游一步。** 本方案是把它拉到前面成为主交付物，不是引入新概念。

## 2. 判据：派生 vs 原生

用户第 4、5、6 条原话之间存在张力——「无需额外建立事实文档」与「baseline 是必要的」——化解它的判据不是「事实 vs 解释」，也不是「清单 vs 叙述」，而是**能否重建**：

| 文档 | 性质 | 丢了能重建吗 | 谁拥有 |
|---|---|---|---|
| `docs/codebase-insight.md` | 派生自代码，按 commit hash 缓存 | ✅ 重扫就有 | ms-codebase-insight |
| `docs/devdocs/00-context.md` | 派生自 DevDocs + 代码 + git，`--update` **覆盖** | ✅ 重扫就有 | ms-onboard |
| `docs/devdocs/00-baseline.md` | **原生**——收敛后的结论 + 来源 + 置信度 | ❌ 重扫代码产不出 | ms-retrofit |

这条判据直接回答了「为什么非得多一个文件」：**不可由扫描重建的信息，不能存放在会被扫描覆盖的文档里**。把基线塞进 `00-context.md`，一次 `--update` 就冲干净了。

注意「原生」不等于「用户口述」。基线里一条「定位 = X（据 `README.md:3`），但 `payment/` 模块的行为与之矛盾（推导待确认）」——原料 README 和代码都可重读，**这条结论本身不可重建**：它是收敛、比对、标注置信度之后的产物。基线存的是这个，不是原料。

它同时给出基线的硬边界（见 §3.2）：**凡是重扫代码能重建的，基线一律不装，无例外。**

## 3. 基线文档

### 3.0 判据：接手难在建立「认知权威」

**基线的主要消费者是大模型**——在后续的全新会话里读它来接手项目；人也看，但不是主要读者。这个框定决定了它该装什么。

接手一个已有项目，最难的不是理解代码，而是区分四件事：

| # | 问题 | LLM 的表现 |
|---|---|---|
| 1 | 代码**实际**做了什么 | 极擅长——读一遍就知道 |
| 2 | 系统**本该**做什么 | 读不出来 |
| 3 | 外部世界**要求**它必须做什么 | 读不出来 |
| 4 | 目前**根本不知道**什么 | 读不出来，且会用推测填空 |

**LLM 极易把第 1 项误当成后三项。** 没人能解释历史时尤其危险——它会把一段实现偶然性当成设计意图去保护。

基线的全部职责就是承载 2、3、4，并明确标出 1 的边界。**凡是第 1 项能回答的，基线一律不装**——那是代码和 `codebase-insight.md` 的地盘，LLM 重扫成本很低，写进基线只是从「读真实代码」那里抢 token。

### 3.1 结构（六节）

文件路径：`docs/devdocs/00-baseline.md`。**短、稀疏、不自动覆盖。**

| 节 | 内容 | 对应第几问 |
|---|---|---|
| 建立记录 | `adoption_commit`、日期、工作区是否 dirty、基线时点的构建/测试实跑结果、未答清单 | — |
| 项目目的与边界 | 为谁解决什么问题，**以及明确不负责什么** | 2 |
| 代码外部的硬约束 | 真实消费者、数据归属、兼容范围、部署边界、不可逆操作、安全/合规限制 | 3 |
| 仍在约束未来改动的护栏 | 决定是什么 + 它约束哪些改动 + 依据在哪 | 2 |
| 已知未知 + 证据冲突 | 不确定项、文档与代码矛盾、**确认前该采取什么安全默认动作** | 4 |
| 权威来源地图 | 哪类信息该信谁 | 边界 |

#### 逐节判据

**建立记录**：`adoption_commit` 是 DevDocs 接管的分界线 commit，让「基线前 / 基线后」成为**可判定的**——§7.4 的追溯语义、§7.3 的下游判定全部锚在它上面。它固定不变，与每次重读代码的观察时点无关。构建/测试结果压在这里只占一行：它标定的是**基线时点的可信度**（新会话知道红了不是自己弄坏的），不是持续状态，所以不设独立节。

**项目目的与边界**：「不负责什么」和「负责什么」同等重要——不知道边界，LLM 会接受任何需求。接手场景下这一节经常整节是 `未知`，那也是正确结论（§3.4）。

**代码外部的硬约束**：判据是「不读生产环境、外部系统或历史协议，单看本仓代码无法可靠知道」。这一类最实用——「这个接口有外部消费者，改了炸别人」，LLM 单读代码绝对不知道，改了就出事。

**仍在约束未来改动的护栏**：三要素**缺一不写**。这条要求同时是流水账过滤器——「某年某月试过 X 后来删了」写不出「它约束哪些改动」，自然出局；「不要重新引入多需求并行，mic-en 已证伪」写得出，留下。完整推理若存在放 ADR，基线只留结论 + 指针。

**已知未知 + 证据冲突**：**最重要、也最容易漏的一节。**对 LLM 而言「不要把这个推断当事实」往往比一段架构介绍有价值得多。「确认前该采取什么安全默认动作」是这一节的落脚点——只说「不确定」而不说「那怎么办」，等于把判断又扔回给最容易猜错的一方。

**权威来源地图**：一小节，声明代码现状信当前代码与匹配 HEAD 的 `codebase-insight.md`、当前任务信 `00-context.md`、项目约束与未知信基线、新需求信正式需求文档。它直接对治 §3.0 的第 1 项误判。

### 3.2 硬约束

⛔ **`00-baseline.md` 不得出现**：模块表 / 接口表 / 数据对象表 / 依赖图 / 技术栈清单 / 目录结构树 / 当前分支与未提交改动 / 完成率与待办 / 泛化的编码提交规范 / 旧文档全文摘录 / 完整变更历史与流水账式决策过程。

⛔ **不得从实现细节推导出「必须保持此行为」。**

⛔ **不得出现没有来源、没有适用范围、没有可信状态的自信陈述**（标注制度见 §3.3）。

**最大的危害不是过时，是把实现偶然性写成设计意图。** 后续 LLM 会把它当成约束**主动保护**——保护的可能只是一个 bug、一笔技术债，或一段早已失效的行为。这比信息过期严重得多：过期的信息读者还会怀疑，被写成「设计意图」的偶然性没人会去质疑。

这些闸必须写死，因为 LLM 在「问人 / 挖证据」和「抄清单」之间一定倒向后者——抄清单不需要等回话，且看起来产出更丰满。不设闸，基线会退化成 `codebase-insight.md` 的一份会过期的副本。

### 3.3 每一条都必须标来源

基线里非纯生成的每一项，须标注四者之一：

| 标注 | 含义 | 硬要求 |
|---|---|---|
| `用户确认` | 用户明确说过，或确认了草案 | — |
| `已有文档` | 来自 README / CHANGELOG / 旧业务文档 | **必附路径行号 + 校验标记**（§3.5） |
| `推导待确认` | 从代码、结构、提交历史推出，用户尚未表态 | **必附推导依据** |
| `未知` | 调查过，推不出，问了也没答 | — |

`已有文档` 的校验标记为 `已佐证` / `未可验` / `与代码矛盾` 三者之一，规则见 §3.5。

⛔ **不得出现无标注、无依据的断言。** 推不出就标 `未知`，不许用「大概是做 XX 的」填满页面。

⛔ **`推导待确认` 不得因用户沉默而升格为 `用户确认`。** 用户没表态就一直是待确认——这是它和 §1 逆向的根本区别：逆向把推导直接当成结论落库，这里推导始终带着「未经确认」的标记活着。

这套标注是本方案最重要的一道闸。§1 批判逆向的理由是「推导出没人决定过的结论」——如果基线允许在用户答不出来时自行补全，它犯的是同一个错，只换了个文件名。标注制度让每一条都必须交代自己是怎么来的。

`推导待确认` 与 `未知` 项汇总进「建立记录」，作为这份基线的已知局限。

### 3.4 「未知」是正确结论，不是失败

最常见的使用场景是**中途接手项目**——此时用户对「为什么做、解决什么问题、哪儿有坑」的了解**未必比 agent 多**。设计不能假设人是 why 的权威。

由此定下三条：

1. ⛔ **每一次提问都必须提供「我也不清楚」出口，且选它不算失败。** 不给出口，用户会被迫在几个选项里挑一个——产生的假信息**比标「未知」更糟**，因为它带着「用户确认」的权威。这正是 §1 批判的病，只是换了个产生方式。
2. **大面积 `未知` 是接手场景的正常形态。** 一份诚实标出十几处「未知」的基线，价值高于一份看起来完整但有一半是猜的。它告诉接手者**自己不知道什么**——这本身就是接手时最需要的信息。
3. **基线可增量补全，不是一次性冻结。** 接手者三个月后摸清了某块，应该能填回去。补充入口见 §6.3。

这也扩大了 §4 Step 1 的调查范围：用户答不出来时，还有 commit message、issue、PR 讨论、旧文档这些**别人留下的陈述**可挖。它们是接手场景下 why 的主要来源。

### 3.5 文档不是权威，代码是

接手项目的文档**不必然可信**——README 可能描述的是两年前被重构掉的系统，而它带着确信地错，比空白更危险。代码是实打实的。

由此定三条：

1. ⛔ **凡文档陈述可被代码检验的，必须检验。** 不检验就采信 = 把过期信息当证据。检验结果落成校验标记：

   | 标记 | 含义 |
   |---|---|
   | `已佐证` | 文档说 X，代码确实如此 |
   | `未可验` | 纯意图类陈述（为什么做 / 给谁用），代码检验不了 |
   | `与代码矛盾` | 文档说 X，代码实际是 Y |

2. ⛔ **冲突时以代码为准。** 文档陈述不删除，改记为「文档声称 X（`README.md:3`），代码实际 Y——已过期或从未实现」。两边都留着，因为「曾经打算做 X」本身是关于项目历史的信息。

3. **`未可验` 不得与 `已佐证` 同等呈现。** 纯意图陈述仍是接手场景下最好的线索（§3.4），但它没有任何东西为它背书——可能是过期的项目定位，也可能是从没实现过的愿景。

**冲突本身是最有价值的产出。** 「文档说 A，代码是 B」正是接手者最容易踩的坑——它必须进「已知未知 + 证据冲突」那一节，并写明确认前该采取什么安全默认动作，不能只当脚注。

**但别把代码的权威用过头。** 代码是「在做什么」的权威，**不是**「还在被用吗 / 做对了吗」的权威：死代码和活代码长得一模一样，关掉的 feature flag、没人调用的端点、固化了 Bug 的逻辑，代码都不会告诉你。这些归「已知未知」（标出来，给安全默认动作）和提问环节，别拿代码当全能裁判。

## 4. 建立流程

```text
1. 调查：把别人留下的陈述挖干净
   │   ├── 委托 ms-codebase-insight 摸排  → docs/codebase-insight.md（清单层）
   │   ├── README / CHANGELOG / docs/ / 包描述字段
   │   ├── git log 提交信息（尤其早期提交和大改动的说明）
   │   ├── issue / PR 讨论（如可访问）
   │   └── 实跑构建 / 测试 / 启动，记录真实结果
   │
   ▼
2. 校验：拿代码检验文档里的每一条可验证陈述（§3.5）
   │   ├── 与代码一致          → 已佐证
   │   ├── 与代码矛盾          → 与代码矛盾，冲突进「已知未知」
   │   └── 纯意图，代码验不了  → 未可验
   │
   ▼
3. 推导：起草带依据标注的基线草案
   │   每条都写清「据什么」——路径行号 + 校验标记，或推导依据
   │
   ▼
4. 提问：只问推不出、依据薄弱、或校验出矛盾的项
   │   ├── 形式为「确认 / 修正」，不是开放式空白页
   │   ├── ⛔ 每题必须有「我也不清楚」出口（§3.4）
   │   └── 现状：拿模块清单 × 提交时间分布 × TODO/FIXME 密度 × 测试覆盖
   │            出候选，让用户判「完成 / 半成品 / 废弃 / 不清楚」
   │
   ▼
5. 落盘 docs/devdocs/00-baseline.md
       用户确认的 → 用户确认   用户没表态的 → 保持推导待确认
       推不出也问不到的 → 未知，汇总进建立记录
```

**为什么调查必须在提问之前**：README 里写着的东西还去问用户，是浪费用户时间；而在接手场景下（§3.4），别人留下的陈述往往是 why 的**唯一**来源——用户自己也是从这些材料里知道的。

**「现状」一问的定位**：代码信号出候选、判断权在人。两个极端都被否决——

- **纯问人**：面对空白页答不出来；接手场景下更是根本不知道
- **纯代码推断**（TODO 密度 / 提交时间 / 覆盖率自动判成熟度）：这正是 §1.2 「推导出没人决定过的结论」的老毛病换个马甲

草案不是猜的豁免证。三种来源、三种待遇，都不得无标注地写成断言：

| 材料 | 标注 |
|---|---|
| README 写着「本服务解决订单超卖」 | `已有文档` + `README.md:3` + `未可验`——纯意图，代码证不了也伪不了（§3.5） |
| README 写着「用 Redis 做分布式锁」，代码里确实是 | `已有文档` + 路径行号 + `已佐证` |
| README 写着「用 Redis 做分布式锁」，代码里已换成数据库行锁 | `已有文档` + `与代码矛盾`，以代码为准，冲突进「已知未知」 |
| 从类名 `StockLockService` 推「大概与库存并发有关」 | `推导待确认` + 推导依据 |

| `description` 中「逆向」「从代码生成文档」触发词 | `SKILL.md` frontmatter | 不删的话，用户喊「逆向」仍被带回老路 |
| 基线路径的 `00-retrofit-report.md` | `SKILL.md` | §6.2 |

**不删**：版本迁移那条腿（旧 DevDocs → 新规范）整体不动，含它的 `00-retrofit-report.md`。

## 6. 单一出处裁定

### 6.1 四处重叠

| 结论 | 唯一出处 | 其余位置的处理 |
|---|---|---|
| 项目目的与边界 / 外部硬约束 / 护栏 / 已知未知 | `00-baseline.md` | `01-requirements.md §1.1 项目背景` 改指针；`00-context.md` 可引用，⛔ 不得复制一份 |
| 模块 / 接口 / 数据对象 / 技术栈 | `codebase-insight.md` | 基线一律不装（§3.2） |
| 术语解码表 / 命名与目录约定 | `AGENTS.md`（agent-memory 维护） | 基线不设节，见 §6.4 |
| 当前进度 / 待办 | `00-context.md` | 基线一律不装（§3.2） |

### 6.2 `00-retrofit-report.md` 并入基线（仅基线路径）

现行报告模板在新方案下的存活情况：

| 章节 | 新方案下 |
|---|---|
| 编号分配表 | ❌ 整张作废——不再产编号 |
| 文档状态表 | ❌ 塌成一行——只产一份基线 |
| 待完善项 | → 迁入基线「建立记录」节 |
| 下一步建议 | → 迁入基线「建立记录」节，且内容已部分过期 |

剩下的是空壳仪式。基线路径不产报告。

版本迁移路径保留报告：它真有迁移动作清单要记（改了哪些编号、重命名了哪些文件），不是空壳。

### 6.3 `ms-requirements --context` 只让出一项

`01-requirements.md §1 背景与目标` 现有五项：项目背景 / 领域知识 / 技术约束 / 参考资料 / 决策记录。

**只有「项目背景」与基线重叠**，其余四项与基线不冲突，改造场景下本来就是空的，后续 `requirements` 往里填。整节搬迁是用户没要的重构。

落法：`references/context-mode.md` 加一条边界说明——项目级的「我是谁、解决什么问题」归 `00-baseline.md`，`§1.1` 在有基线时只写指针。不动 `ms-requirements` 主流程。

**同时它就是基线的增量补全入口（§3.4 第 3 条）。** `--context` 本来的定位就是「问人补代码里看不出的背景」，与基线同源；`context-mode.md` 已支持增量更新不覆盖原有内容。接手者三个月后摸清了某块，跑 `/ms-requirements --context` 把它填回 `00-baseline.md`，并把该条从 `推导待确认` / `未知` 升为 `用户确认`。

不为此新建 `/ms-retrofit --baseline-update` 一类的入口：补全基线是「补背景」，不是「改造项目」。

### 6.4 术语表与命名约定归 `AGENTS.md`，不进基线

调查阶段（§4 Step 1）一定会产出两样东西：**术语解码表**（标识符 ↔ 业务含义）和**猜会猜错的约定**（命名映射、目录语义、非常规约定）。它们对接手极有价值——本仓 `AGENTS.md` 里这两类占了全文约四分之一。

但它们不进基线，归 `AGENTS.md`：

| | 常驻价值 | 归属 |
|---|---|---|
| 术语表 / 命名约定 | **每次读代码都要用** | `AGENTS.md`（每会话加载） |
| 目的边界 / 外部约束 / 护栏 / 已知未知 | 接手时读一次，之后按需查 | `00-baseline.md`（不常驻） |

落法：retrofit 建完基线后调 `Task: /agent-memory --update`（**现有流程里已经有这一步**），由 `agent-memory` 把这两类写进 `AGENTS.md` 的「领域术语」「架构决策」节——那正是它的 `memory-template.md` 已有的章节。retrofit 不直接写 `AGENTS.md`。

**为什么基线必须独立于 `AGENTS.md`**：`AGENTS.md` 每会话加载，因此有 60 行硬限（[agent-memory/SKILL.md](../../../skills/agent-memory/SKILL.md):100）。实测本仓的 `AGENTS.md` 已是 **82 行 / 20KB，超限 22 行**——一个规格库尚且如此，真实存量项目的接手记录（冲突清单、未知项、外部约束）绝无可能塞进去。而且也不该塞：一份五十项的未知清单没有理由常驻在每一个会话的上下文里。

⚠️ 本仓 `AGENTS.md` 同时是**反面样本**：它的「当前状态」节混入了大量变更历史与流水账（「codex 6 轮 R6 PASS」「E2E 冒烟通过」之类），占掉大量常驻上下文却不约束任何未来改动。基线的护栏节用「三要素缺一不写」（§3.1）挡住这类内容；`AGENTS.md` 自身的这个问题是既存缺陷，不在本方案范围。

### 6.5 `ms-onboard` 顺手修一个既存缺陷

`00-context.md §1.1 项目目标` 现在写死「从 `01-requirements.md` 提取」。改造后 01 不存在——**这在改造后的项目上本来就是坏的**，与本方案无关，是既存缺陷。

修法：提取源加上 `00-baseline.md`。不改 `00-context.md` 的派生快照定位。

## 7. 编号体系影响

**存量代码不编号。** 改造后 `01-requirements.md` 不存在，由首次 `/ms-feature` 创建，`F-001` 从新需求起。

已知副作用：改造完成到首个需求之间，以下 skill 会拒绝运行——

- `ms-board`：⛔ 硬要求 `01-requirements.md` 存在
- `ms-test-cases`：读 `01-requirements.md`
- `ms-verify`：读 `01` 中的 AC

**这是正确行为**：还没有需求，当然不能评审需求、不能设计需求的测试、不能核验需求的验收。不做兼容处理，但基线的「建立记录」节须写清下一步走向（有新需求 → `/ms-feature`）。

### 7.1 ⛔ `ms-retrofit` 自身重入会死循环（必修）

现行检测逻辑（`SKILL.md`「项目状态检测」）：

```text
docs/devdocs/ 存在？
  ├── 不存在 → 新项目改造
  └── 存在 → 规范符合性检查
        ├── 符合 → 无需改造
        └── 不符合 → 版本迁移
```

基线建立后 `docs/devdocs/` 存在，但里面只有 `00-baseline.md`。而「规范符合性检查清单」要求编号体系 / 测试编号 / 追溯矩阵 / 文件命名四项**全部必须**——基线项目一项都不满足，于是被判为「不符合 → 版本迁移」。

后果：`references/version-migration.md` Step M1 会生成「⚠️ 需迁移：缺少 F/US/AC 编号」，**试图把刚建好的基线项目迁回旧的编号形态**。用户第二次跑 `/ms-retrofit` 就会撞上。

**修法**：检测逻辑加一个前置分支——

```text
docs/devdocs/ 存在？
  ├── 不存在 → 建立基线
  └── 存在 → 只有 00-baseline.md（无 01~04）？
        ├── 是 → 基线已建，终态，无需改造（提示下一步 /ms-feature）
        └── 否 → 规范符合性检查（原逻辑）
```

「基线已建」是与「符合规范」并列的**第三种终态**，不是「旧版待迁移」。

### 7.2 ⛔ `ms-pipeline` 路由表缺「仅基线」一行（必修）

`skills/pipeline/SKILL.md`「已有 DevDocs 文件时」路由表最短的一行是「仅 `01-requirements.md` → `/ms-system-design`」。基线项目 `docs/devdocs/` 存在，会进入这张表，但**匹配不到任何行**——落空。

**修法**：表首加一行

| 检测项 | 路由建议 |
|---|---|
| 仅 `00-baseline.md`（基线已建，尚无需求） | 有新需求 → `/ms-feature`；补充项目背景 → `/ms-requirements --context` |

### 7.3 ⛔ 下游入口断点（必修，codex 独立评审发现）

删掉基线前编号之后，三条入口在基线项目上会拒绝运行。**其中两条是结构性的，一条是文案过期。**

#### 7.3.1 `ms-feature` 死循环（最严重）

`skills/feature/SKILL.md:29` 前置条件写「至少存在 `01-requirements.md`」，不存在时建议 `/ms-retrofit`。于是：

```text
基线项目 → 想加新功能 → /ms-feature
  → 「01 不存在，建议 /ms-retrofit」
  → /ms-retrofit → 「基线已建，无需改造」（§7.1）
  → 回到 /ms-feature ⟲
```

**这直接打断用户意图 2「后续使用 devdocs 维护」**——基线建完就进不去后续流程了。

**修法**：前置条件改为「存在 `01-requirements.md` **或** `00-baseline.md`」。只有基线时，`ms-feature` 创建 `01-requirements.md`，`F-001` 从这个新需求起。

#### 7.3.2 `ms-bugfix` 无编号可关联

`skills/bugfix/SKILL.md:138 / 281` 要求「关联功能 `F-XXX` / `AC-XXX`」为 **必须**。基线项目第一次修 Bug，涉及的是基线前的存量代码——它没有 F 编号，也不该临时编一个（编了就是 §1 的老毛病）。

**修法**：「关联功能」在基线项目上允许填 `baseline`，语义为「涉及基线前代码，无需求编号」。回归测试仍必须写，只是 `@verifies` 标注对象从 `AC-XXX` 换成 `BUG-XXX`。

#### 7.3.3 `ms-onboard` 文案过期

`skills/onboard/SKILL.md:394`「DevDocs 不存在 → `/ms-retrofit` 先从代码逆向生成文档」——逆向没了，这句话描述的行为不复存在。改为「建立项目基线」。

同处 `:388`「如 DevDocs 不存在，提示用户先运行相关 skill」不变。

#### 7.3.4 `ms-dev-workflow` 探索模式承诺失效

`skills/dev-workflow/SKILL.md:60` 写「写入 Commit 1 `Exploration-Mode: true` 尾注便于 `/ms-retrofit` 补 AC」。retrofit 不再补 AC。

**修法**：改为「便于事后由用户确认目标行为后补建真实 AC」。尾注本身保留——它记录的是「这次提交跳过了文档强制」，这个事实仍然有效。

#### 7.3.5 `ms-dev-tasks` 经核实不是独立断点

`skills/dev-tasks/SKILL.md:204` 要求每个任务关联 `F-XXX` 和 `AC-XXX`。但 `dev-tasks` 的输入是 `01`/`02`/`03`——走 `ms-feature` 正常流程时这三份都已存在，F/AC 已由 feature 创建。**只要 §7.3.1 修好，这里自动不成立。**不单独改。

### 7.4 ⚠️ 追溯覆盖率的语义污染（必修）

基线项目上，`ms-sync` 和 `ms-verify` 算出的「AC 覆盖率 100%」只覆盖 `adoption_commit` 之后的变更，却会被读者理解成**全系统覆盖率**。存量代码占比越大，这个误读越危险——它会让人以为一个基本没有测试的老项目「测试覆盖完美」。

**修法**：追溯矩阵与覆盖率报告在基线项目上必须显式标注 `coverage_scope: post-baseline`，并写明 `adoption_commit`。

这条是 codex 提出的，我方案原本完全没考虑。

### 7.5 两处虚警（已核实不受影响，勿重复排查）

- **`ms-sync --back-propagate-prd`**：Step 2 读 `01-requirements.md` 的 F-XXX，但该流程「仅在用户显式调用时执行」且 Step 1 先要求 `docs/prd/requirements/index.md` 存在——基线项目上没有，在 Step 1 就以「无 prd 映射表，无需反向同步」正常退出，够不到 Step 2。
- **`agent-memory` 工作流路由节**：补节判据是 `docs/devdocs/` 存在，基线项目会触发；但节内容是通用路由声明（「一律走 `/ms-pipeline`」），不假设 01~04 存在。正常工作。

## 8. 不做什么

| 不做 | 理由 |
|---|---|
| skill 改名 | `retrofit` = 改造既有物使其适配新标准，**仍然准确**。变的是手段（逆向 → 建基线），不是「改造已有项目」这件事。改名是纯成本：约 20 个文件的交叉引用 + 用户肌肉记忆，换一点语感 |
| 合并 `codebase-insight.md` 与基线 | 已由用户裁定共存。且 `codebase-insight.md` 被 prd / dev / test 三条流程消费，retrofit 无权改它的产物位置 |
| 改 `00-context.md` 的定位 | 它是派生快照，职责与基线不同（§2）。只多认一个提取源 |
| 保留逆向为可选档 | 留着就要维护整套推导规范，而它的产物在 §1 已证无用。半档是最差解 |
| 为「现状」做自动成熟度判定 | §4 |
| 迁移存量项目已有的逆向产物 | 已生成的 F/US/AC 留在原地由用户处置。自动清理会删掉用户后来手工修正过的内容 |
| 修 `AGENTS.md`「当前状态」节的流水账问题 | 已识别为既存缺陷（§6.4），但它属于 `agent-memory` 的地盘，不是本方案引入的。基线自身用护栏三要素挡住同类内容即可 |
| 让基线自动从代码覆盖生成 | 基线的修改只应来自新证据或人工确认。自动覆盖会冲掉标注体系（§3.3）里所有 `用户确认` 的条目——这正是它必须独立于 `codebase-insight.md` 与 `00-context.md` 的理由（§2） |

### 9.1 为什么要给基线登记治理身份

`00-baseline.md` 是新增的持久化 DevDocs 产物。本仓规则 [_shared/constraints.md](../../../skills/_shared/constraints.md) §8：

- `realign/template-frontmatter-minimum`：A/B 类产物模板 frontmatter 最小字段为 `generated_by` / `spec_version` / `generated_at`
- `realign/current-constant-location`：`spec_version` 常量放在各 skill 的 `references/realign.md` 顶部

`ms-retrofit` 目前没有 `references/realign.md`——因为它此前不产带 `spec_version` 的产物。现在产了，就得建。

不登记的代价是明确的：`ms-verify --schema-drift` 扫不到它、`realign --scope=spec` 不知道怎么升它，基线成为治理盲区。对照物 `00-context.md`（ms-onboard）已在扫描表内，两者同为 `00-*` 持久产物，不该一个在册一个在野。

**这两项属于 skill 侧管道，不增加被改造项目的产物文件数**（用户「尽可能少的文件」约束针对的是后者，见 §2 表）。

## 10. codex 独立评审结论

评审方式：只给 codex 用户原话 + 现状 skill 文件，**明确禁止读本设计稿**，避免评审沦为对已有方案的对齐（教训来自 workspace-topology 那轮「六轮里五轮在审自己加的戏」）。

### 10.1 一致（评审独立得出同一结论）

| 结论 | 本方案位置 |
|---|---|
| 逆向 US/AC 应删除；编号体系本身必须保留 | §1、§7 |
| 版本迁移分支必须保留 | §5 |
| `ms-board` 在基线态保持不可用是正确的 | §7 |
| `ms-pipeline` 会把基线项目重新路由回 retrofit | §7.2（本方案自审独立发现） |

### 10.2 采纳（本方案原本没有）

| `ms-bugfix` 无编号可关联 | §7.3.2 |
| `ms-onboard` / `ms-dev-workflow` 文案过期 | §7.3.3 / §7.3.4 |
| 工作区 dirty 时基线锚定不明确 | §3.1 建立记录 |

### 10.3 不采纳

**评审主张：不新增 `00-baseline.md`，把 `docs/codebase-insight.md` 升级为基线 SSOT。**

不采纳，两条理由：

1. **用户已明确裁定共存**——在得知「清单 vs 叙述」权衡后选择两份并存。
2. **该主张有未处理的硬伤**：它给基线列的内容包含「项目是什么、面向谁、解决什么问题（用户确认）」，也就是**问人得来的内容**。但 `codebase-insight.md` 按 commit hash 缓存，`--force` 会**全量重新扫描覆盖**。评审没有回答：重扫时这些问人得来的内容怎么保住？要么引入「部分节不覆盖」的有状态合并（脆弱），要么就会丢。这正是 §2 判据要避开的坑。

评审的核心关切（文件太多、SSOT 分散）是对的，本方案的回应是 §2 的划法：事实清单留 `codebase-insight.md`，问人得来的留基线，两者不重叠。

**评审主张：`ms-dev-tasks` 需独立修复。** 经核实不成立，理由见 §7.3.5。

**评审主张：基线应包含已实现能力 / 模块 / 入口 / 公开接口 / 关键数据 / 外部集成。** 不采纳——与 §3.2 硬约束直接冲突，也与用户原话 4「无需额外建立事实文档」冲突。这些是清单，归 `codebase-insight.md`。

### 10.4 第二轮：基线该装什么（独立调查 + 对齐）

第二轮的问题不同于第一轮——用户补充了决定性框定「消费对象仍然是大模型」，于是重问：基线到底该装什么，甚至还需不需要。双方**分头独立调查后对齐**，本方案的独立结论记录在调查完成时点、看到评审结论之前。

#### 一致

需要这份文档 · 不装模块/接口/数据/文件树/技术栈清单 · 不装进度待办完成率 · 「已知未知 + 证据冲突」是最重要的一节 · 不知道就写「未知」不从类名反推 · 不该塞进常驻加载的 `AGENTS.md`

#### ⚠️ 冲突一处，本方案原结论被推翻

**「已证伪的路」该不该装。**

- 本方案原结论：**必装**。依据是对本仓 `AGENTS.md` 的实测——「当前状态」27 行中，「证伪/推翻/删除/废弃/否决/不做/不采纳/放弃」出现 30 次，「误判/缺陷/坑」7 次，「新增」12 次，负向知识压倒性占优。
- 评审结论：**绝对不装**（「完整变更历史、所有被否决方案和流水账式决策过程」），并点名 `AGENTS.md`「当前状态」是**反面样本**。

**本方案的推理有缺陷**：把「`AGENTS.md` 里有很多」当成了「它有价值」。内容多也可能只是**没人删**——那份文件只增不减，82 行 / 20KB、超 60 行硬限 22 行，本身就是失控的证据，不是价值的证据。

裁定取第三种表述，两边原结论都不采用：

> **只装仍在约束未来改动的证伪结论，且必须写成护栏形式（不要做 X，因为 Y），不是历史记叙（某月试过 X）。**

它落进「护栏」节，由三要素（决定是什么 / 约束哪些改动 / 依据在哪）自动过滤——流水账写不出「它约束哪些改动」。

#### 采纳（本方案原本没有）

| 采纳项 | 落点 |
|---|---|
| **代码外部的硬约束**：真实消费者、数据归属、兼容范围、部署边界、不可逆操作、合规限制 | §3.1 |
| **权威来源地图**：哪类信息该信谁 | §3.1 |
| **最大危害不是过时，是把实现偶然性写成设计意图**——后续 LLM 会主动保护本只是 bug 或技术债的行为 | §3.2 |
| 「不负责什么」与「负责什么」同等重要 | §3.1 |
| 「确认前该采取什么安全默认动作」是已知未知节的落脚点 | §3.1 |
| **认知权威四分法**（代码实际做了什么 / 本该做什么 / 外部要求必须做什么 / 根本不知道什么）作为全节判据 | §3.0 |

最后一条是判据层面的升级：本方案原判据是**信息可得性**（读代码拿不拿得到），评审判据是**误判风险**（LLM 会把哪一项误当成哪一项）。后者更根本，已取代前者作为 §3 的组织原则。

#### 本方案独有

- `adoption_commit`（第一轮由评审提出，第二轮未重申，保留）
- `AGENTS.md` 60 行硬限的实测超限数据（82 行 / 20KB），用于论证基线必须独立于常驻记忆（§6.4）

#### 结构收敛结果

基线由 8 节收敛为 6 节。砍掉「系统怎么运转」（LLM 能重建主干链路，留它是**人**的需求）、「现状（完成/半成品/废弃）」（化解进护栏与已知未知）、「可验证状态」独立节（压成建立记录一行）、「事实索引」（并入权威来源地图）。

## 11. 遗留

- **未验证**：本仓不是被改造对象，基线流程无法在此实测。需在真实存量项目上跑一次才知道两件事——§4 Step 1 的调查能挖出多少（决定 `未知` 的实际比例），以及 Step 4 的候选清单质量如何。
- **接手场景下 `未知` 的实际比例是核心未知数**：若真实项目跑下来九成条目是 `未知`，说明调查范围（§4 Step 1）不够或基线该换个形态。这不是失败信号，是校准信号——但要有真实数据才知道往哪校。
- **六节结构是否够用、是否过多**：§3.1 的六节由两轮独立调查对齐得出，但**没有一份真实基线可供检验**。特别存疑的是「代码外部的硬约束」——它的价值判断成立，但一个接手者能不能填得出来（真实消费者是谁、数据归属在哪）本身就依赖他不具备的信息。真跑一次可能发现它和「已知未知」大面积合并。
- **`00-context.md` 与基线的长期关系**：本方案只让 onboard 多认一个提取源。若后续发现 `00-context.md` 在改造后项目上仍大面积为空（§4/§5/§8 节依赖 F/T 编号），再单独处置——不在本方案范围。
