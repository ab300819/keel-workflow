# 模式 B：CHG 对象与技术变更流程

## 0. 定位

模式 A（现有 DevDocs，21 个 `ms-*` skill）服务**需求与功能开发**。
模式 B 服务**技术升级 / 重构 / 治理**。两者并行，共享 SSOT（第 1 步已划定边界）。

**B 的新增名称 = 1 个对象（`CHG`）+ 1 个 skill + 1 条共享契约。**

⚠️ 「名称数量」≠「改动范围」。实际要接通 7 个既有消费点（§4.1~§4.2），⛔ 不要把前者当后者宣传。

## 1. 两种模式的分界

| | 契约对方 | "做完了"的定义来自 |
|---|---|---|
| **A** | **用户** | 代码之外——用户能做成一件新事 |
| **B** | **代码库本身** | 一半来自代码现状 |

这是 Fowler 对重构的定义（behavior-preserving transformation）的推广，⛔ 不是从某个项目的产物归纳出来的。

⇒ B 的工作形态恒为：**项目从技术状态 X 迁到 Y，同时某些可观察结果保持不变。**

由此，B 的必需要素是可推导的，⛔ 不需要发明：

| 要素 | 为什么不可省 |
|---|---|
| **现状基线 X** | 不知道现在什么样，就无法判断"保持不变" |
| **目标状态 Y** | 没有它就没有"做完了" |
| **保持项** | "行为不变"是**契约**，不是天然事实——必须列出来才能验 |
| **允许变化** | 不列就等于"保持项"在撒谎（总有已知差异）|
| **影响面** | 不知道去哪看，就无法验证保持项 |

## 2. `CHG` 对象

### 2.1 Frontmatter（机器读）

```yaml
---
id: CHG-007
kind: upgrade | refactor | governance
status: proposed | ready | active | blocked | done | superseded
title: 后端迁移到 .NET 10
spec_version: change.v1
generated_by: ms-change
generated_at: 2026-09-14T10:00:00+08:00
baseline:
  - repo: backend
    commit: 3bc68ed0
keeps:                      # 保持项台账，⛔ 只放可判定的键值
  - id: K1
    verdict: pending        # pending | pass | fail
  - id: K2
    verdict: pass
tasks: [T-13, T-26]
blocked_by: []
---
```

### 2.2 ⛔ 机器要解析的东西不得住在 Markdown 表格单元格里 `[新增]`

**frontmatter = 台账（可判定的键值）· 正文 = 论证。**

保持项的**编号与判定**在 frontmatter；它的**内容与理由**在正文。完成门只读 frontmatter。

> **为什么是硬约束**：本仓实测（2026-09 编号体系调查），从 Markdown 表格提取结构化数据连续失败 6 次——`| **CON-026** 🔴 |` 破正则漏 3 条、`~~**D-39**~~` 被判成空号、结果表里的引用被当成定义、章节主题被推成关联关系（20 vs 实际 4）。**人和工具在这个格式下都做不到可靠提取**，因为"这一行是定义还是引用"需要读语义。
>
> 这条是 B 与 A 的一处刻意分歧：A 的 `01`~`04` 用表格承载编号，B ⛔ 不重复这个错误。

### 2.3 正文必填章节

| 章节 | 内容 | 省略后果 |
|---|---|---|
| 动因 | 为什么现在不能继续维持 | 无法判断值不值得做 |
| 目标状态 | 完成后项目处于什么**可判定**状态 | 没有完成条件 |
| 现状基线 | 当前版本/行为/结构的**可复核证据** | 保持项无对照物 |
| 范围 | 纳入 · 排除 · 受影响的代码根/模块/接口/数据/运行环境/开发流程 | 验证不知道去哪看 |
| 保持项 | 逐条 `K<n>`：必须不变的可观察结果 + 它的基线指针 | "行为不变"成口号 |
| 允许变化 | 已知且被接受的差异；有取舍的引 `ADR` | 保持项与现实冲突时无处安放 |
| 方案与风险 | 实施方向 · 失败模式 · 回滚或前滚 | 出事无预案 |
| 验证矩阵 | 目标状态 / 每条保持项 / 风险 → 证据 | 完成门无输入 |
| 待决项 | 问题 · owner · 关闭条件 · 阻塞对象 | 未知被伪装成已知 |
| 闭环记录 | 实际变更来源 · 验证输出 · 剩余风险 | 事后无法复核 |

### 2.4 保持项用 CHG 内局部编号

`K1` / `K2`，跨 CHG 引用写 `CHG-007#K3`。

⛔ **不开全局命名空间。** 保持项永远从属于一个 CHG，没有独立生命周期——给它全局编号就是再开一个前缀（现有机器白名单已 13 种 + `M`，`CHG` 本身还要新增一个）。

### 2.5 `CHG` 的消费契约（按 `id/prefix-consumption-contract` 登记）

| 项 | 内容 |
|---|---|
| 作用域 | 项目级全局唯一 |
| 消费方 | B 的建档/就绪门/关闭 · `ms-dev-workflow`（执行）· `ms-verify`（实现正确性）· 治理层（dead-link）|
| 检查归属 | **进** `dead-link`。`CHG-XXX` 引用不到定义 = 死链 |

## 3. 流程与门

### 3.1 四步

| 步 | 动作 | 出口门 |
|---|---|---|
| 1 建档 | 判是否够一个独立 `CHG`；采集基线/目标/范围/保持项/允许变化 | `status: proposed` |
| 2 就绪门 | 一次性审影响边界 · 未决决策 · 任务依赖 · 验证方法 · 回滚策略 | ⛔ 有未关闭的**决策级**待决项 ⇒ 不得进 `ready` |
| 3 执行 | 按 `T` 逐项实现，复用 `ms-dev-workflow` 全套质量地板 | 超出 `CHG` 范围时停该分支，⛔ 不静默扩大（`confirm/scope-inflation`）|
| 4 验证关闭 | 从**完整影响面**重新验证 | 见 §3.2 |

> **⛔ 不设计六阶段。** A 的六阶段服务"需求→设计→测试→开发"的链路；B 没有需求澄清环节，硬套只会产生空文档。

### 3.2 完成门（`status: done` 的充要条件）

- 目标状态有**当前**证据（⛔ 不是"当初通过了"）
- 纳入范围全部处理，排除范围**未被暗中改动**
- **每条保持项 `verdict: pass`**，且各有独立证据
- 每条允许变化已确认；结构性取舍有 `ADR`
- 全部 `T` 完成，无 `review_pending`、无未解除 blocker
- 受影响的接口/数据/运行/部署/构建/治理规则**按实际影响**验证（`scope/gate-coverage`：评审边界 ≥ 影响边界）
- 回滚、旧路径保留或删除有明确结论
- 文档与代码实际状态已同步

### 3.3 验证矩阵：要求覆盖，⛔ 不规定方法白名单

每条保持项与目标状态**必须有至少一条证据**，但 ⛔ **不枚举合法证据类型**。

> **为什么不建白名单**：封闭分类正是 A 那边逼出第五套测试前缀的原因。工具检查的是「**每条保持项有没有证据**」，⛔ 不是「证据类型在不在批准清单里」。新出现一种验证手段时，不需要改规格。

⚠️ **「验证以单元测试或集成测试为主」是默认，⛔ 不是排他**——三条硬证据：

| 证据 | 说明 |
|---|---|
| `ai-code` `04-dev-tasks.md:253`（`G-f`，⚠️ 行号已从 239 漂移）| i18n 语料搬全了但 `main.ts` 漏 `.use(i18n)`，**两道编译门全绿而缺陷仍在**，`$t` 只在运行期炸 ⇒「编译通过」≠「装配正确」|
| `ai-code` `04-task-criteria-shape-audit.md:17` | **9 处空输出型判据，其中 3 处的通过态完全无法与「命令坏了」区分**，1 处实测出假阳性 |
| 三类工作的性质差异 | 重构以 UT/IT 为主；升级还需构建矩阵/部署/回滚/数据对账；治理需正反样本 + dry-run 幂等 |

⇒ **判据的通过态 ⛔ 不得是"空输出"或"零计数"**，除非同时给出正面控制（证明命令本身有效）。

### 4.2 共同验收输入契约（替代逐处打补丁）

**七个消费点想要的是同一件事**：「这个任务的验收项是什么、怎么验」。它们只是各自把答案硬编码成了 `AC`。

⇒ 在**共享层**定义一次，七处都引用它，⛔ 不逐处补条件。

#### 契约：`acceptance/resolve-from-source` `[新增，进 constraints.md]`

```
输入：一个 T
输出：验收项列表，每项 = { id, 类型, 期望来源, 证据要求 }

解析：按 T 的 source 字段分派
  source = F-XXX + AC-XXX  → 验收项 = 该 F 的 AC 逐条
                              类型 ∈ {行为型, 视觉型, 结构型}（A 现有分类，不变）
                              期望来源 = 规格
  source = CHG-XXX         → 验收项 = 该 CHG 的 保持项 K<n> + 目标状态
                              类型 ∈ {保持项, 目标状态}
                              期望来源 = 保持项→基线 · 目标状态→规格
  source 缺失              → ⛔ 禁止继续（现有 ms-dev-tasks:187 已要求必须有 source）
```

#### 七个消费点改为引用契约

| 消费点 | 现在 | 改为 |
|---|---|---|
| `ms-dev-workflow:92,101` S1 | 读 F/AC 关联 | 调 `acceptance/resolve-from-source` |
| 同 `:102` S1.5 | 基于 AC 生成 Sprint Contract | 基于**验收项**生成 |
| `task-orchestration:553-556` | 输入要 `F-XXX, AC-XXX` | 输入要**验收项列表** |
| 同 `:579` | `assertion_sources: [AC-001,…]` | `assertion_sources: [<验收项 id>,…]` |
| `ms-dev-workflow:222` S8 | AC 完备性表 | **验收完备性表**（列不变：编号/类型/证据/位置/判定）|
| `ms-verify:157-160` | 从 `01` 逐条读 AC | 从 source 解析 |
| `ms-sync:199` / `ms-test-run:203` | 关联 AC/F/US；无 AC 判孤立 | 关联**验收项**；无验收项才判孤立 |

> **为什么这样不会重演 `CON` 的分叉**：`constraints.md:407` 记的失败是「同一执行事实分散在强制矩阵/主循环/子 Agent 协议/完成流程/模板，**没有单一执行 SSOT**」。本契约就是那个缺失的 SSOT——七处**引用同一个解析函数**，⛔ 不各自实现。
>
> ⚠️ 代价：这是**先建契约再改七处**，⛔ 不是"只改一处"。改动面见 §7。

#### 质量地板不变

5 条质量地板、声称 vs 实际 diff 交叉验证、`review_profile` 档位——全部与验收项来源无关，⛔ 不动。

## 5. A / B 路由

### 5.1 判据：问两个问题

1. **完成后，用户或外部调用者应观察到什么新结果？**
2. **哪些现有结果必须保持不变？项目的技术状态要变成什么？**

| 情况 | 走 |
|---|---|
| 第 1 问有明确答案 | **A** |
| 第 2 问能给出目标技术状态 + 保持项 | **B** |
| **两问都有答案** | **拆成互相依赖的 `F` 与 `CHG`**，⛔ 不建混合对象 |
| 两问都答不出 | 保持只读调查，`status: partial`，⛔ **不分配编号、不进入执行** |

⛔ **`kind` 按动因判，⛔ 不按实施手段判。** 用 `git diff` 验证不代表它是治理；升级项目里也有需要 E2E 的部分。

### 5.2 ⛔ 不创建 `CHG` 的情况

- 某个 A 任务内部的小范围重命名、抽函数
- 机械依赖补丁，无独立影响面/决策/回滚需求
- 单个 BUG 修复附带的局部清理

⇒ 留在原 `T` 内。**⛔ 不让模式 B 变成新的文档税。**

### 5.3 混合工作的处理

`F` 与 `CHG` 互相引用（`F depends_on CHG` / `CHG related_to F`），但**一个 `T` 只能有一个主来源**。

## 6. 坑检查

逐条对照本仓 2026-09 编号体系调查中观察到的**失败现象**（⛔ 不是对照某项目的条目清单）：

| 现象 | B 的设计如何避免 |
|---|---|
| 分类封闭 → 项目自造命名空间 | 验证矩阵**不建方法白名单**；新前缀走 `id/prefix-consumption-contract` 登记路径 |
| 有兜底对象 → 它装进 9 种东西 | `CHG` 有**明确的必填章节**，装不下的走登记路径，⛔ 不塞最近的桶 |
| 表格单元格存语义 → 提取不可靠 | §2.2 硬约束 |
| 规格默认值逼项目写反话 | `T` 的执行属性从**工作自身的事实**推导（有无可测代码），⛔ 不从父对象类型推导 |
| 预拆产出不可派单任务 | 就绪门前 ⛔ 不发 `T` 号；重构的目标结构依赖迁移后的代码，本就无法预先枚举 |
| 消费方硬编码类型清单 | `CHG` 只加一个前缀，且从设计之初就登记消费契约 |
| 编号区间被当成阶段/范围 | `CHG` 的纳入/排除范围是**唯一分母**，`T` 号 ⛔ 无业务语义 |
| 编译/测试全绿仍漏装配 | 验证矩阵按**影响面**展开，⛔ 不按测试类型展开；空输出判据须有正面控制 |

## 7. 代价与未决

### 代价

1. **`CHG` 是新的全局对象**——规划/执行/验证/治理必须**同批**成为真实消费方。只加模板会重演「有编号、无人消费」。
2. **要改 7 个既有消费点**（§4.2），外加 `verification-flow.md` 25 个 AC 命中行。这是本设计最大的一块，⛔ 不可低估。
3. **`T` 与测试编号跨 A+B 全局续编**，需统一定义索引；两个分配器并行会撞号。
4. **保持项质量依赖基线调查**——基线漏面时流程仍可能得到假绿。
5. **路由判据靠人执行**。判错（把有用户可观测行为的工作判成 B）会绕过 US/AC 保护。缓解：§5.1 两问都有答案时强制拆分。

### 两处需要说清的设计解释（⛔ 不是"对用户判断的修正"）

1. **「没有 US/AC」指的是 ⛔ 不造 `US`/`AC` 这两个对象**，⛔ 不指"没有验收标准"。B 的验收项是保持项 + 目标状态。
2. **「功能保持不变」需要先定义什么算"功能"**——接口、数据副作用、权限、定时行为、部署行为、错误语义是否包含在内。这正是「保持项」必填的原因。

> ⚠️ v1 把这两条写成「对用户判断的修正」，**错了**——用户从未说过"不需要验收"或"不需要证明"。这是实现用户决策所需的设计解释。
