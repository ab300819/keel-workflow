# adversarial-review 审查方改为 hcom 实例优先

> 2026-11-19。状态：待用户审阅。前置设计：[交叉验证](2026-11-16-adversarial-review-cross-validation-design.md)（已实施）。

## 1. 意图

用户原话：

> 我是希望使用 hcom 方式给codex/agy 发消息的方式在实例中进行，这样能获得完整上下文和工具使用，failback 用命令行方式

> 「完整上下文」是指连续对话产生的，而不是一次性任务，每次从头开始

> keel 主要使用人是我，不考虑通用性

现状：每一轮审查都是一个新的一次性进程。复审要把材料重讲一遍；agy 在这种方式下不能执行命令，改动内容要先存成文件喂给它。改成在一个持续存在的实例里对话，复审接着上一轮说，审查方能自己跑命令、翻仓库。

## 2. 目标、非目标、反目标

**目标**

- 交互调用 `/adversarial-review` 时，codex 与 agy 优先以 hcom 后台实例方式工作；一次审查会话内每个审查方只用一个实例，首轮和所有复审轮都发给它。
- 实例方式不可用或中途卡住时，该方落回现有的命令行方式，并在结论里写明。
- 询问、对齐、一方失败、摘要字段的现有规则（`cross-validation.md`）不变，只是多了一种送达方式。

**非目标**

- 不为没装 hcom 的环境做适配：没装就直接走命令行方式，不提示安装。
- 实例不跨审查会话保留，审完即关。
- `dev-workflow` 内嵌的自动审查（embedded-headless）不变，仍只用 codex 的命令行通道。
- 不改 T1b（备用计费后端）、T2、T3 的规则。

**反目标**

- 协调方 ⛔ 不替用户处理实例里的弹框（信任目录、换模型、登录等）。
- ⛔ 不因为用了实例就放松「审查方只读」与「两方互相不可见」。

## 3. 试跑事实（2026-11-18 ~ 19，hcom 0.7.31，本机）

| 检查项 | codex 实例 | agy 实例 |
|---|---|---|
| 自己执行 `git show` | 能 | 能 |
| 按约定回一行 JSON | 能，约 15 秒 | 能，首轮约 2 分钟，后续约 40 秒 |
| 同一实例收第二、三条消息并记得上一轮 | 能 | 能 |
| 只读限制 | 有效：`--sandbox read-only` 下 `touch` 被拒（`Operation not permitted`），`hcom send` 不受影响 | **无效**：带 `--sandbox` 启动，`touch` 仍在仓库里建出了文件 |
| 能列出并读到其他实例的对话 | 能（`hcom transcript <对方>` 成功） | 能列出（含用户自己开的实例） |

另外三条：

- **弹框会挡住消息**。hcom 把消息打进实例的输入框，输入框被弹框盖住就送不进去。遇到两种：codex 的「额度快用完，是否换模型」（额度紧张时每轮结束都弹）；agy 的「是否信任此目录」（`~/.gemini/antigravity-cli/settings.json` 的 `trustedWorkspaces` 要写**完整路径**，上级目录不继承；hcom 的 `auto_trust_workspace` 对 agy 不起作用）。两种情况下 `hcom list` 都把实例标为 `blocked`，未读数不归零。
- **事件记录能查偷看**。`hcom events --agent <名字> --cmd "hcom transcript"` 列出该实例执行过的读对话命令，实测能查到 codex 实例那一次。
- agy 需要先装常驻接入：`hcom hooks add antigravity`（一次性）。

## 4. 方案

考虑过三种：

| 方案 | 取舍 |
|---|---|
| A. 后台实例，一次审查一个，弹框即失败并落回命令行（**采用**）| 连续对话与工具访问都拿到；弹框时本轮退回一次性方式，损失的只是连续性 |
| B. 前台可见窗口，弹框等用户处理 | 弹框不算失败；但协调方要无限期等人，审查时长不可控 |
| C. 复用用户已开着的实例 | 能带上更早的上下文；但对方可能已看过我方结论，独立性没保证，还会打断用户在那个实例里的事 |

用户已定：A；agy 只读靠提示词加事后检查（不在副本里审，也不让 agy 退回命令行）；实例不跨审查保留。

### 4.1 通道顺序

每个审查方各自判定，互不影响：

| 审查方 | 顺序 |
|---|---|
| codex | hcom 实例 → T1（CLI）→ T1b → T2，后三级规则不变 |
| agy | hcom 实例 → `agy` CLI 非交互模式 |

实例方式可用的判据（S2.5 探测时一并做）：`hcom` 在 PATH 上；该工具的接入就绪（`hcom hooks status <工具>` 不是「not installed」）；启动返回的 `readiness.status` 为 `ready`。任一不满足 → 该方本次会话走命令行方式，不重试实例。

### 4.2 生命周期

- **启动**：S3 首轮调度时各起一个，`hcom <工具> --headless --go --tag <本次会话标签> --dir <仓库> --json`；codex 加 `--sandbox read-only`；agy 加 `--model <按现有规则选的模型>`。首轮 brief 用 `hcom send` 发，不放在启动参数里（启动与送达分开判失败）。
- **发消息**：`hcom send @<实例> -b --intent request --file <brief 文件>`。两方的 brief 内容相同，这一点不变；因为实例能自己跑命令，不必再为 agy 把 diff 存成文件。
- **等回复**：`hcom events --wait <秒> --type message --from <实例> --after-id <发送时的事件号>`。超时后看 `hcom list <实例>`：
  - `blocked` 或未读数不为 0 → 实例被弹框卡住，按 4.4 处理；
  - 仍在 `active` → 再等一次；累计超过上限仍无回复按失败处理。
- **复审**：发给同一个实例，只说这一轮改了什么、要复核哪几条，不重发全部材料。
- **关闭**：审查会话结束（含中途失败、用户中止）时 `hcom kill tag:<本次会话标签>`。⛔ 只按本次会话的标签关，不碰用户自己的实例。

### 4.3 回复格式

实例方式没有 `--output-schema`。brief 末尾要求审查方用 `hcom send @bigboss` 回复，内容是与现有 schema 同形的 JSON（代码审查）或带约定末尾标记的文本（方案 / 文档审查）。协调方收到后按现有解析与截断判定处理：JSON 解析失败或缺必填字段、文本缺末尾标记，都按截断处理，规则与命令行方式相同。

### 4.4 实例方式特有的失败

| 情况 | 处置 |
|---|---|
| 启动返回 `blocked` 或 `failed` | 该方落回命令行方式；把 hcom 带回的弹框原文报给用户 |
| 发消息后实例 `blocked`、消息未读 | 关掉该实例，本轮用命令行方式重发同一份 brief；结论里写明「<某方> 本轮起改用命令行方式，原因：<弹框原文>」；本次会话该方后续轮次都走命令行 |
| 回复解析失败 | 按截断处理（现有规则） |
| 命令行方式也失败 | 进入 `cross-validation.md` § 一方失败（现有规则） |

落回命令行后连续性丢失：下一轮要像现在一样带上完整材料。

### 4.5 只读与独立性的事后检查

每一轮收到回复后、进入对齐前，协调方做两项检查，任一项不通过则**该方本轮结果无效**，按「一方失败」处理并报告用户：

1. **只读**：`git status --porcelain` 与调度前的快照一致。不一致 → 列出差异，由用户决定是否回退；⛔ 协调方不自行回退。
2. **独立**：`hcom events --agent <实例> --cmd "hcom transcript"` 与 `--cmd "hcom term"` 在本轮时间窗内无结果。有 → 该方看过别的实例的对话。

brief 里同时写明：只读，不修改任何文件；不读取其他实例的对话。首轮回复之前 ⛔ 不向任一方透露另一个实例的名字。

这两项对 codex 是加固（它本来就有沙箱），对 agy 是唯一保障——agy 的只读在实例方式下**不是事前保证**，文档里要照实写。

### 4.6 摘要字段

`reviewers[].method` 的取值加两个：`codex-hcom`、`agy-hcom`。中途落回命令行的，填最后实际产出结果的通道。其余字段不变。

## 6. 留给实施时确认的

- agy 的 `--sandbox` 在命令行方式下是否挡写入——现行规格写的「agy 只读」靠的是 `--mode plan` 拒绝执行命令，没单独测过写文件。
- 回复较长时 `hcom send` 是否有长度上限；有的话改为让审查方把结果写到约定的临时文件再发路径（这会与「只读」冲突，届时把该临时目录从 4.5 的检查里排除）。
- 等回复的累计上限取多少（agy 首轮实测约 2 分钟，真实审查会更长）。

## 7. 没有验证的

- 一次完整的真实审查没有在实例方式下跑过，试跑用的都是「报告改了几个文件」这种最小任务。
- 两方并行启动、并行等回复没有测过，试跑是先后进行的。
- 弹框只遇到两种；登录过期、版本更新提示等会不会同样被标为 `blocked`，未知。
- 4.5 的检查能发现 `hcom transcript`，但审查方若直接读 `~/.codex/sessions/` 或 `~/.hcom/` 下的文件，这条检查发现不了。
