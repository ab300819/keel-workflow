# adversarial-review 审查方改为 hcom 实例优先

> 2026-11-19。状态：待用户审阅。前置设计：[交叉验证](2026-11-16-adversarial-review-cross-validation-design.md)（已实施）。

## 1. 意图

用户原话：

> 我是希望使用 hcom 方式给codex/agy 发消息的方式在实例中进行，这样能获得完整上下文和工具使用，failback 用命令行方式

> 「完整上下文」是指连续对话产生的，而不是一次性任务，每次从头开始

> keel 主要使用人是我，不考虑通用性

现状：每一轮审查都是一个新的一次性进程。复审要把材料重讲一遍；agy 在这种方式下不能执行命令，改动内容要先存成文件喂给它。改成在一个持续存在的实例里对话，复审接着上一轮说，审查方能自己跑命令、翻仓库。

## 2. 目标、非目标、反目标

**目标**

- 交互调用 `/adversarial-review` 且协调方运行在 tmux 里时，codex 与 agy 各开一个审查专用的 hcom 实例窗口；一次审查会话内每方只用一个实例，首轮和所有复审轮都发给它。
- 实例方式不可用或中途卡住时，该方落回现有的命令行方式，并在结论里写明。
- 询问、对齐、一方失败、摘要字段的现有规则（`cross-validation.md`）不变，只是多了一种送达方式。

**非目标**

- 不为没装 hcom、不在 tmux 里的环境做适配：直接走命令行方式，不提示安装。
- 不复用用户自己开着的实例（`hmux` 起的 `<目录名>-codex` / `-agy`）；用户在请求里明说「用现有实例」时除外。
- 实例不跨审查会话保留，审完即关。
- `dev-workflow` 内嵌的自动审查（embedded-headless）不变，仍只用 codex 的命令行通道。
- 不改 T1b、T2、T3 的规则。

**反目标**

- 协调方 ⛔ 不替用户处理实例里的弹框（信任目录、换模型、命令批准、登录等）。唯一允许的界面注入是 4.3 的「推一下」。
- ⛔ 不因为用了实例就放松「审查方只读」与「两方互相不可见」。
- ⛔ 不碰用户自己的 tmux 窗口与 hcom 实例。

## 3. 试跑事实（2026-11-18 ~ 19；hcom 0.7.31，agy 1.5.12，本机）

| 检查项 | codex 实例 | agy 实例 |
|---|---|---|
| 自己执行 `git show` | 能 | 能 |
| 按约定回一行 JSON | 能，约 15 秒 | 能，约 40 ~ 60 秒 |
| 同一实例连续多条消息并记得上一轮 | 能 | 能 |
| 只读 | 有效：`--sandbox read-only` 下 `touch` 被系统拒绝，`hcom send` 不受影响 | **无效**：`--sandbox` 加命令放行清单都挡不住，`touch` 不经批准直接成功（auto 模式把它当安全命令）|
| 能列出并读到其他实例的对话 | 能 | 能列出（含用户自己的实例）|

实例方式特有的问题：

1. **agy 空闲时收不到消息**。agy 输入框的模式提示行（`Auto mode: …` / `Plan mode: …` / `Accept-edits mode: …`，三种 `--mode` 都有）被 hcom 读成「未提交的草稿」，于是不送消息。`hcom term <名字> --json` 显示 `ready: true`、`prompt_empty: false`、`input_text` 即那行提示。等 7 分钟不会自己送达。上游已知：[aannoo/hcom#114](https://github.com/aannoo/hcom/issues/114)，关闭时未修。**绕法实测有效**：`hcom term inject <名字> "<一句话>" --enter`，实例一开始处理，排队的消息立即送达。
2. **agy 窗口方式下每条命令都要批准**。启动时加 `--settings <文件>`（只对本次会话生效、不落盘）放行只读 git 命令与 `hcom send` 后不再弹。
3. **弹框会挡住消息**。遇到过：codex「额度快用完，是否换模型」（额度紧张时每轮结束都弹）；agy「是否信任此目录」（hcom 给每个 agy 实例单独的数据目录，`trustedWorkspaces` 要写完整路径，`auto_trust_workspace` 对 agy 无效）；agy「是否执行此命令」。`hcom list` 都会标 `blocked`。
4. **启动方式**。让 hcom 自己开窗口（`--terminal "<命令> {script}"`）两方都秒退（参数被并成一个）。可用的是 `hmux` 的做法：先建 tmux 窗口，再把 `hcom <工具> … --terminal here` 打进去。`--terminal here` 未写进帮助。打命令前窗口必须已回到 shell，否则命令会丢。
5. **关闭**。`hcom kill` 之后 tmux 窗口有时跟着关、有时留着，两种都遇到过；清理要两步都做并容忍「窗口已不存在」。
6. **事件记录能查偷看**。`hcom events --agent <名字> --cmd "hcom transcript"` 实测能查到。注意用户的 agy 全局设置里 `hcom transcript` / `hcom term` 是免批准的。
7. agy 需要一次性安装常驻接入：`hcom hooks add antigravity`。

## 4. 方案

考虑过的启动方式：

| 方案 | 取舍 |
|---|---|
| 协调方所在 tmux 会话里开审查专用窗口（**采用**）| 用户看得见，弹框顺手能按；实例是新的，独立性有保证 |
| 后台实例（`--headless`）| 不占窗口；但弹框无人处理，只能判失败 |
| 复用 `hmux` 已起的实例 | 带着更早的上下文；但可能已参与过被审内容，codex 那个也没带只读沙箱，审查消息还会插进用户正在进行的对话 |

用户已定：窗口方式优先，不行就落回命令行，两方一致，不设后台实例这一级；agy 用「推一下」绕过送达问题；agy 只读靠提示词加事后检查；实例不跨审查保留。

### 4.1 通道顺序

每个审查方各自判定，互不影响：

| 审查方 | 顺序 |
|---|---|
| codex | tmux 窗口实例 → T1（CLI）→ T1b → T2，后三级规则不变 |
| agy | tmux 窗口实例 → `agy` CLI 非交互模式 |

窗口实例可用的判据（S2.5 探测时做）：协调方自己在 tmux 里（`$TMUX` 非空）；`hcom` 在 PATH 上；该工具的接入就绪（`hcom hooks status <工具>` 不是 not installed）。任一不满足 → 该方本次会话走命令行方式。

### 4.2 启动与关闭

- **标签**：`<目录名>-review-codex` / `<目录名>-review-agy`（目录名按 `hmux` 的规则只留字母、数字、连字符），发消息用 `@<标签>-` 寻址，不记随机名。窗口名 `review-codex` / `review-agy`，开在协调方所在的 tmux 会话里，`-d` 不抢焦点。
- **启动**：`tmux new-window` 建窗口，再 `send-keys` 打入：
  - codex：`hcom codex --tag <标签> --terminal here --sandbox read-only`
  - agy：`hcom agy --tag <标签> --terminal here --sandbox --model <按现有规则选的模型> --settings <本次会话的放行文件>`。放行文件只列只读 git 命令（`git show` / `diff` / `log` / `status` / `blame` / `ls-files`）与 `hcom send` / `hcom list`，写在临时目录。
- **就绪**：等该标签的实例出现在 `hcom list` 且状态为 `listening`。出现 `blocked` → 把屏幕上的弹框原文报给用户并等其处理；超过等待上限仍未就绪 → 该方落到下一级通道。不另发握手消息。
- **关闭**：会话结束（含失败、用户中止）时 `hcom kill tag:<标签>`，再 `tmux kill-window`（窗口已不在则忽略）。⛔ 只认 `review` 标签与自己建的窗口。

### 4.3 发消息与等回复

- **发**：`hcom send @<标签>- -b --intent request --file <brief 文件>`。两方 brief 内容相同；实例能自己跑命令，不必再为 agy 把 diff 存成文件。
- **agy 推一下**：发完后若 `hcom list` 显示该实例仍有未读且状态含 `uncommitted text`，执行一次 `hcom term inject <名字> "有新的 hcom 消息，请处理。" --enter`。只对自己起的审查实例做，只推这一句；推过仍未送达 → 该方落到下一级通道。
- **等**：`hcom events --wait <秒> --type message --from <名字> --sql "id><发送时的事件号>"`。超时后看状态：`blocked` → 报弹框原文并等用户；`active` → 再等；累计超过上限按失败处理。
- **复审**：发给同一个实例，只说这一轮改了什么、要复核哪几条。
- **回复格式**：实例方式没有 `--output-schema`。brief 末尾要求用 `hcom send @bigboss` 回复与现有 schema 同形的 JSON（代码审查）或带约定末尾标记的文本（方案 / 文档审查）。解析失败或缺标记按截断处理，规则与命令行方式相同。

### 4.4 落回

| 情况 | 处置 |
|---|---|
| 窗口实例起不来、等用户处理弹框超时、agy 推过仍未送达 | 关掉该实例，落到下一级通道；结论里写明「<某方> 本轮起改用 <通道>，原因：<原文>」；本次会话该方后续轮次沿用新通道 |
| 所有通道都失败 | 进入 `cross-validation.md` § 一方失败（现有规则）|

落到命令行后连续性丢失：下一轮要像现在一样带上完整材料。

### 4.5 只读与独立性的事后检查

每一轮收到回复后、进入对齐前做两项检查，任一项不通过则**该方本轮结果无效**，按「一方失败」处理并报告用户：

1. **只读**：`git status --porcelain` 与调度前的快照一致。不一致 → 列出差异，由用户决定是否回退；⛔ 协调方不自行回退。
2. **独立**：`hcom events --agent <名字> --cmd "hcom transcript"` 与 `--cmd "hcom term"` 在本轮时间窗内无结果。

brief 里同时写明：只读，不修改任何文件；不读取其他实例的对话。首轮回复之前 ⛔ 不向任一方透露另一个实例的名字。

对 codex 这是加固（它有沙箱），对 agy 是唯一保障——agy 的只读**不是事前保证**，文档里照实写。

### 4.6 摘要字段

`reviewers[].method` 加两个取值：`codex-hcom`、`agy-hcom`。中途落回的，填最后实际产出结果的通道。其余字段不变。

| 文件 | 改动 |

## 6. 留给实施时确认的

- 回复较长时 `hcom send` 是否有长度上限。
- 各处等待上限取多少（agy 最小任务约 1 分钟，真实审查会更长）。

## 7. 没有验证的

- 一次完整的真实审查没有在实例方式下跑过，试跑用的都是「报告改了几个文件」这种最小任务。
- 两方并行启动、并行等回复只做过一次，那次 agy 没回（第 3 节问题 1），不算验证过。
- codex 窗口方式只测了一条消息；它的连续多轮是在后台方式下测的。
- 弹框只遇到三种；登录过期、版本更新提示等是否同样被标为 `blocked`，未知。
- 4.5 的独立性检查只能发现通过 hcom 命令读对话的情况；审查方直接读 `~/.codex/sessions/` 或 `~/.hcom/` 下的文件，这条检查发现不了。
- 上游修掉 #114 之后「推一下」是否有副作用（重复触发一轮），未知。
