## 1. 问题：过程门与验收门被混为一谈

「外包」意味着**只验交付物，不管过程**。但把过程门直接删掉是错的——得先知道**删掉之后谁来验**。

改造前的实际形态（以 `ms-system-design` 为样本）：

- L1~L4 每层一次 `AskUserQuestion`，问的是「架构层对不对」「模块划分对不对」
- 确认草案里放着模块划分表、接口概要、数据模型表、原则校验表、对抗审查表
- 存在一个叫「快速档」的档位，**被引用 6 次，零处定义触发条件**

三个连锁后果：

1. **人验不了给他看的东西。** 那五张表要么是结构，要么是 agent 自查结果——人扫一眼判不了对错，agent 判得更准。
2. **于是确认退化成走过场**，但它留下了「已确认」的记录。**假门比没门糟**：下游会信它。
3. **档位分的是「问几次」，不是「问什么」。** 快速档把 L1~L4 合成一次问，产出还是那份 452 行模板，4 项自查照样「不得跳过」。

## 2. 验收角色与能力表（本文核心）

**每一种验收人的能力边界是硬的，不因流程设计而改变。**

| 验收人 | 能验什么 | 验不了什么 | 成本特征 |
|---|---|---|---|
| **测试** | 代码是否满足**已经写下来**的 AC | AC 本身写得对不对 | 一次性投入，之后近乎零 |
| **agent**（`ms-verify` / `adversarial-review`） | 内部一致性、追溯完整性、自洽性、有没有漏项、格式契约 | **「这是不是我要的」** | 低，可重复、可并行 |
| **人** | 意图对不对、边界划在哪、这个取舍值不值 | 细节一致性（扫不完 400 行，也不该扫） | 高，且**不可扩展** |

### 2.1 三条推论

**推论 1：意图确认无法外包。**

agent 能查出「AC-03 没有对应测试」，查不出「AC-03 根本不是我想要的」——它没有那个信息源，**用户是唯一的源**。

> 这是外包模型的硬边界：**意图确认必须留人，其余可以全外包。**

**推论 2：生产方的自查表不是验收证据。**

02 里的「边界自查」「原则校验表」「对抗性设计审查」都由产出这份设计的 agent 自己填。验收方若只是读一遍这些表就放行，等于没审——**与「被测者书写测量记录」是同一失效模式**（同 [runlog 硬纪律 3](../../../skills/_shared/runlog.md)：一个无视了 `⛔` 的模型同样不会记录「我无视了 `⛔`」）。

> 验收方必须**从正文重新算一遍**。自查表是**被审对象**，不是证据。

**推论 3：确认界面只放人能验的东西。**

把 agent 自查产物混进确认界面，唯一效果是让确认退化。人能验的只有方向；结构与自查直接落盘，由 agent 验。

### 2.2 每道门的分配判据

对每一道现存的门，问一句：

| 它在问什么 | 归谁 |
|---|---|
| **「你要的是不是这个」** | 留人，且必须让人读得懂 |
| 「格式对不对 / 步骤跑没跑 / 内部自洽吗」 | 交 agent，**从源头重算，不读自查表** |
| 「代码做到了没有」 | 交测试 |

## 3. 何时需要人拍板：岔路判据

用户的原话是「小需求几乎没必要验收，因为功能单一且明确；大需求需要，因为大所以需要决策和把握方向」。

落成可判定的一句：

> **这个需求有没有两种以上合理走法？**
> **有** → 需要人定方向，确认内容 = 这几条路各自的代价 + 建议走哪条 + 理由。
> **没有** → 不问。直接产出，一致性交给验收方 agent。

⚠️ **判据落在「有没有岔路」，不在需求大小。** 规模只是廉价代理：大需求通常有岔路，小需求通常没有。真遇到小而有岔路的（只写一个函数，但要选加密算法），照问。

曾考虑并**否决**的判据：「有没有不可逆决策」。它衡量的是**后悔成本**，而用户要的是**有没有方向要定**——一个小需求可能有不可逆决策（选了个库）但方向自明，不需要拍板。用户的判据更准。

### 3.1 与 `ceremony` 的关系

编排层归一化下传的 `ceremony`（`fast` / `standard` / `deep`，见 [constraints.md](../../../skills/_shared/constraints.md) `task/normalized-intent-shape`）决定**问不问**；岔路判据决定**有没有可问的**。两者是与的关系：

| | 无岔路 | 有岔路 |
|---|---|---|
| `ceremony: fast` | 不问 | **不问，但必须交代**——岔路、选了哪条、理由，写进产物显眼处 |
| `standard` / `deep` | 不问 | 问一次 |

> `fast` 是用户免掉了**被打断**，不是免掉了**知情**。外包方自己拍板可以，不交代不行。

## 4. 交付物的两类读者

用户约束：「如果是人验收，文档的信息的密集度得降低，不要说黑话，用人话说」。

但降密度**不是删内容**，是**分读者、排顺序**：

| 读者 | 要什么 | 怎么给 |
|---|---|---|
| **人**（拍板时 / 事后回看） | 方向、代价、后悔点 | 拍板界面只放岔路；文档顶部放摘要节 |
| **agent**（后续会话接手） | 编号、结构、契约、追溯锚 | 原样保留，位置后移 |

编号体系（`F-01` / `AC-03` / `I*(§5.x)`）是机器追溯的锚，**不删**。改的是**入口**。

### 4.1 落地形态

**产物顶部加摘要节**（`ms-system-design` 试点为 02 的 `## 0. 摘要`，最多 8 行）：

- 要解决什么（一句话，不复述编号）
- 怎么解决（一句话）
- 定了哪些方向 → 指向 ADR
- 还没定的
- **最可能后悔的地方**（写具体场景，如「日订单超 50 万这套单表得拆」）

> 原本「为什么这么定」的 ADR 在 452 行模板的第 406 行——人从头读要先撞 13 节结构。

**报告顶部加人话节**（`ms-verify` 试点为 verify-report 的「要你知道的」）：

- 有 P1/P2 时必填，全绿时删除
- 一句话说清**问题是什么、会导致什么**，不带编号
- 最多 5 条；超过 5 条说明该退回重做而不是逐条修

## 5. 角色契约的形状（未来改写各 skill 时照此填）

上游 §1.2 给的方向是「从『11 步怎么做』改写为『输入 / 交付物 / 验收证据 / 升级条件』」。本文把第三栏拆细：

```
## 角色

<一句话：这个角色在外包团队里干什么>

## 输入

- 必需：<产物路径 / 归一化字段>
- 可选：<...>
- 缺失时：<降级还是拒绝>

## 交付物

- <路径>：<形状，指向模板>
- 人读的部分：<摘要节，几行以内>
- agent 读的部分：<结构、编号、契约>

## 验收证据

| 验什么 | 谁验 | 怎么算过 |
|---|---|---|
| <意图维度> | 人 | 拍板通过（仅在有岔路时发生） |
| <一致性维度> | agent | <从源头重算的具体判据，⛔ 不读自查表> |
| <行为维度> | 测试 | <具体命令与期望> |

## 需要人拍板的条件

- 有岔路（两种以上合理走法）→ 呈现路径 + 代价 + 建议
- 超出已授权范围的不可逆动作 → 就地确认（`task/consent-at-action`）
- 其余一律不问

## 升级条件

- <什么情况下必须停下来找人，而不是自己判>
```

**方法自主权归执行角色。** 契约规定交付什么、怎么验，不规定分几步、每步问什么。

## 6. 两个试点

选它们的理由：`ms-system-design` 过程门最重且交付物是人签字的那份，(a)(b) 两半能一起验；`ms-verify` 是承接面——只改生产侧不改验收侧就是单纯放松。

**故意不选 `ms-dev-workflow`**，尽管 S1~S11 最重：它的验收人是**测试**不是人，「人验收」这条对它不成立；且它是最高频路径，改坏代价最大。等 02 跑出观察再说。

| | ms-system-design（`31d0a07`） | ms-verify（`91a9135`） |
|---|---|---|
| 确认 | L1~L4 逐层 → 按岔路，至多一次 | — |
| L1~L4 | 确认节奏 → **设计方法**（自顶向下逐步求精，保留） | — |
| agent 自查 | 混在确认界面 → 恒定执行、直接落盘 | 新增：**从 02 正文重算** 6 项，⛔ 不引用自查表 |
| 「快速档」 | 删（无触发判据的逃生舱），改接 `ceremony` | — |
| 人话入口 | 02 新增 `## 0. 摘要` | verify-report 新增「要你知道的」 |
| 版本 | `design.v1 → design.v2` + Migration Matrix | 报告非版本化产物，不涉及 |

verify 层 2 新增的六项：接口引用可解析（P1）/ 接口有归属（P2）/ 数据模型有消费者（P3）/ `—不适用`须有场景（P2）/ §0 摘要存在（P2）/ §0 与正文不矛盾（P2）。

## 7. 不做什么

- **不全改。** 用户明确「挑几个 ROI 高的改，然后投入实际运用观察效果」。推广前必须有真实运行数据。
- **不删编号体系。** 它是机器追溯的锚，只调整呈现顺序。
- **不为「人话」建检测器。** 「是不是黑话」无法机械判定，同 [doc-organization](../../../skills/doc-organization/SKILL.md) 的结论：判据无法机械化就只给原则。
- **不动 `ms-dev-workflow`。** 理由见 §6。

---

## 8. 证不了什么

- **本文未经真实运行验证。** 两个试点都没在真实需求上跑过。
- **岔路判据的松紧未知。** 太松 → 该问的不问；太紧 → 回到走过场。只有真实使用能校准。
- **「人话」是否真的降低了密度，只有用户能判。** 唯一的验证信号是：**你是否真的读完并给出了实质意见**。仍然扫一眼就说「行」，说明密度没降下来。
- **verify 是否真会重算，还是读了自查表就放行**——`⛔` 标记本身不保证执行（这正是上游方案 E5 的教训）。

### 8.1 投用时该观察的三件事

| 观察项 | 说明什么 |
|---|---|
| 无岔路判定准不准 | 该问的没问 = 判据太松；不该问的问了 = 太紧 |
| 「要你知道的」你是否真读了 | 照旧扫一眼 = 密度仍没降下来，改法不对 |
| verify 有没有真去重算 | 读了自查表就放行 = 这次改动是纯放松 |
