# DevDocs 对象模型收敛与文档结构设计

## 0. 背景

### 0.1 触发

用户在真实项目 `ai-code`（.NET/Vue 遗留系统重构，`docs/devdocs/` 52 文件 / 26,195 行）上跑 DevDocs 流程，依次报告三件事：

1. 「在使用 devdocs 工作流时，编号体系失控」
2. 「devdocs 不适合技术升级或重构需求」
3. 「devdocs 作为通用开发工作流肯定包括需求、功能、升级、重构和治理相关开发任务」

### 0.2 三次补丁都失败了

| 轮次 | 方案 | 结果 |
|---|---|---|
| 1 | 编号前缀封闭集合 + 归宿表 | 归宿表按前缀名猜语义，逐条被证伪（`R-` 是重定向安全规则不是风险，`B-` 是白名单放宽登记不是批次）。撤回 |
| 2 | 让 `CON` 当编码任务父级 | `CON` 定义含「没有可写测试的业务逻辑」，此方案改了它的定义，违反「不把 CON 搞复杂」。否决 |
| 3 | `F` 加「行为影响」属性，`AC` 父级放宽到 F | 静态核对 / 上线动作 / 迁移对账三类拿不到测试编号，仍撞 `ms-verify:479`「AC 无测试 = P1」；`T-76`~`T-90` 不可派单问题未解。不完整 |

**三轮都是"遇到一个问题解决一个"。** 本文改为攻根因。

### 0.3 本文的证据基础

- 规格仓全量阅读 + 两轮独立外部调查（Codex），结论已对齐
- 唯一实证样本 `ai-code`，全部结论锚定到 `文件:行`
- 项目自建的 `00-id-registry.md`（2026-09-10）是关键旁证：**项目独立收敛到了「命名空间登记表」这一形状**，并自行标注了哪些前缀是私造

## 1. 根因

**DevDocs 的编号对象按「文档阶段」划分，不按「事物性质」划分。**

```
01 → F/US/AC/CON      02 → ADR      03 → UT/IT/E2E/Journey      04 → T
```

每个阶段固定产出固定类型。当一个真实事物不符合任何阶段的类型，它无处可去 ⇒ 项目自造。

`ai-code` 自造的六套，正好是六个「没有阶段收留」的事物：

| 私造 | 数量 | 它其实是什么 | 证据 |
|---|---|---|---|
| `D-` | 34 | 用户拍板的事实（含原话 + 日期）| `00-id-registry.md:41` |
| `DEV-` | 10 | 实现被迫偏离设计的登记 | 同上 |
| `G-` | 41 | 踩坑变成的 agent 操作纪律（单字母已用尽，续用 `aa`~`ao`）| 同上 |
| `Q-` | 11 | 待用户裁的开放问题 | 同上 |
| `MR-` | 38 | 第五种验证方法（人工/静态/部署/迁移）| `03-test-e2e.md:243` |
| `BLK-` | 18 | 阻塞事实 | `03-test-cases.md:214` |

⇒ **补丁只能一个个收编它们。下一个项目会造出第七种。**

### 1.1 同一根因的其他症状

| 症状 | 证据 |
|---|---|
| `CON` 混装 ≥7 种对象（版本目标 / 部署形态 / 范围边界 / 流程纪律 / 资源投入 / 架构红线 / 缺陷政策 / 不可验收项）| `01-requirements.md:925`~`:976`；`CON-010` 自述「⛔不可验收」、`CON-025` 是缺陷处理政策 |
| 重构项目里 `CON`(25) 比 `F`(21) 还多，而 `CON` 明文不进追溯/覆盖率/健康分 | `constraints.md:404` |
| 等价迁移型功能点系统性缺席，项目自写方法论补救 | `01-requirements.md:134`「📐 方法论：「等价迁移型功能点」为什么会系统性缺席」 |
| `T-76`~`T-90` 占着任务号却明文「⛔ 不得直接派单」 | `04-dev-tasks.md:278`（`用户确认` 2026-09-08）|
| 33 个 `04-task-*.md` 无 frontmatter ⇒ `realign` 扫不到、`ms-verify --docs` 检不到 | `00-id-registry.md` P4 |

## 2. 设计原则

### P1 把类型差异降级为字段，⛔ 不开新对象

新增一种验证方法、一种变更性质、一种决策来源时，加一个**枚举值**，⛔ 不加编号前缀。

> 排除了：第五类测试前缀、`CHG`/`EC` 这类与 `F`/`AC` 平行的新对象。
> 这条是本文与前三轮补丁、以及外部方案的分水岭——**它把「以后还会遇到什么」从"要不要开新前缀"降级成"要不要加一个枚举值"。**

### P2 分叉判据只有一个：用户可观测行为是否变化

⛔ 不按场景名（升级/重构/治理）分叉——名字不可靠。

> 实证：`F-021` 名为「新工程外壳**等价迁移**」，实含角色切换、确认框、跨 SPA 跳转、登出（`01-requirements.md:183`）。按名字免除 US/AC 会丢掉真实保护。
> 这条判据 spec 里**已存在**（`ms-dev-tasks:191`「⛔ 有用户可观测行为的任务不得用 CON 绕过 AC。判不准时默认走 F+AC」），本文只是把它从一处提升为全局主分叉。

### P3 「没有 AC」只能理解为「没有 `AC-XXX` 父级是 US」，⛔ 不是「没有完成条件」

升级/重构/治理必须有可证伪的完成条件，否则「功能保持不变」只是口号。

### P4 阻塞候选不是任务

输入不齐、范围未定、判据不可执行、无责任人的工作 ⛔ 不得取得 `T-XXX`。

> 排除了 `T-76`~`T-90` 这种「既是任务又不得派单」的自相矛盾状态。

### P5 验证方法不决定需求类别

`method=unit` 不意味着它验的是功能需求；`method=static` 不意味着它不是验收。

> 排除了「用 `git diff` 验证 ⇒ 它是非编码任务 ⇒ 免测试」这条本轮第 2 版踩过的错误推理。

## 3. 对象模型（收敛后）

### 3.1 对象清单

| 对象 | 字段（新增部分加粗）| 处理 |
|---|---|---|
| `F-XXX` | **`kind`**: `feature` \| `upgrade` \| `refactor` \| `governance`<br>**`behavior`**: `change`（新增/改变用户可观测行为）\| `preserve`（行为保持不变）| **保留 + 2 字段** |
| `US-XXX` | — | **保留，仅 `behavior=change` 时必需** |
| `AC-XXX` | **`kind`**: `condition`（满足条件 X）\| `invariant`（与基线 B 一致）| **保留 + 1 字段** |
| `CHK-XXX` | **`method`**: `unit` \| `integration` \| `e2e` \| `journey` \| `replay` \| `static` \| `manual` \| `deploy` \| `migration`<br>**`legacy_alias`**: 原编号 | **新增**，吞并 `UT`/`IT`/`E2E`/`Journey` |
| `T-XXX` | — | **保留，⛔ 只发给可派单的** |
| `BLK-XXX` | **`owner`** / **`close_condition`** / **`blocks`** | **新增** |
| `ADR-XXX` | **`decided_by`**: `team` \| `user`<br>**`quote`**: 用户原话 + 日期（`decided_by=user` 时必填）| **保留 + 2 字段** |
| `M-XXX` `BUG-XXX` `INS-XXX` | — | 不变 |
| `CON-XXX` | — | **删除新分配**，存量按性质分流（§3.4）|

**净变化：新增 2（`CHK` / `BLK`），删除 5（`UT`/`IT`/`E2E`/`Journey`/`CON`），净减 3 个对象。**

### 3.2 追溯链

```
用户行为变化   F(behavior=change)   → US → AC(kind=condition)  → CHK → T → commit
行为保持不变   F(behavior=preserve) →      AC(kind=invariant)  → CHK → T → commit
阻塞事实       BLK ──────关闭后────→ 才允许生成 T
```

⇒ **五个场景共用一条链，分叉只在 `F.behavior` 一个字段上。⛔ 不新增 pipeline 入口。**

### 3.3 为什么这不是"引入新概念"

| 新对象 | 它替换了什么 | 净效果 |
|---|---|---|
| `CHK` | `UT` + `IT` + `E2E` + `Journey`（4 个）+ 项目自造的 `MR`（第 5 个）| **5 → 1**。验证方法从"决定前缀"降级为"一个字段值" |
| `BLK` | 项目自造的 `BLK`(18) + `Q`(11) + `NR`(16) + 占用 T 号的 `T-76`~`T-90`(15) | **4 类 → 1**。且它承接的是**现在就已经存在、只是没有合法位置**的事物 |

`CHG` / `EC` 两个对象**被刻意排除**：它们分别是 `F.kind≠feature` 和 `AC.kind=invariant`，按 P1 应当是字段而非对象。

### 3.4 `CON` 存量分流表

依据 `ai-code` 的 `CON-001`~`CON-025` 逐条实测（`01-requirements.md:929`~`:977`）：

| 代表 | 实际性质 | 新归宿 |
|---|---|---|
| `CON-001/002` Vue3 / net10 | 技术目标状态 | `F(kind=upgrade, behavior=preserve)` 的 `AC(kind=condition)` |
| `CON-003/004/005` 仓库/部署/范围 | 变更的范围边界 | `F` 的「范围」字段；需验收的部分转 `AC` |
| `CON-006` 四阶段实施纪律 | 交付策略决策 | `ADR(decided_by=user)` + 搬运 `AC(kind=invariant)` |
| `CON-007` 2.0 FTE 分工 | 计划假设 | ⛔ 不是验收对象，进 `00-context.md` |
| `CON-008/021/023` 回放/语料/副作用隔离 | 验证策略 | `CHK` 的前置条件 |
| `CON-009` 架构红线 | 非目标 | `ADR` 的「非目标」节 |
| `CON-010` 性能（自述⛔不可验收）| **阻塞事实** | `BLK`（owner + 关闭条件）|
| `CON-011` 组件副本数=1 | 结构不变量 | `AC(kind=invariant)` |
| `CON-014/016/019` 环境/方案未定 | **阻塞事实** | `BLK` |
| `CON-017/018/020/022/024` 兼容与等价迁移 | 行为不变量 | `AC(kind=invariant)` |
| `CON-025` 缺陷只登记不处理 | 工作政策 | `F(kind=governance)` 或项目 `AGENTS.md` |

### 3.5 私造前缀分流表

项目在 `00-id-registry.md:41` 论证了 `D-`/`DEV-`/`G-` **不能并入 DevDocs 原生**。逐条回应：

| 私造 | 项目的反对理由 | 本设计的回应 |
|---|---|---|
| `D-`(34) | 「记的是用户拍板的事实（含原话+日期），塞进 `CON-` 会让『谁定的』丢失，而本项目 90% 的争议都在『这是谁定的』」 | **理由成立，但结论不成立。** 它反对的是并入 `CON`，本设计并入的是 `ADR` + 新增 `decided_by=user` / `quote` 两个字段——「谁定的」和原话**被显式保留**，且获得 `dead-link` 等全部治理 |
| `DEV`(10) | 「实现被迫偏离设计，DevDocs ⛔ 无对应概念」 | `ADR(kind=deviation)`（承认偏离并记理由）或 `backlog.md`（打算改回去）。二选一按是否打算修正判 |
| `G-`(41) | 「踩坑变成的 agent 操作纪律，读者是 agent 不是人」 | **不属于 devdocs**。归项目 `AGENTS.md` / `CLAUDE.md`，由 `agent-memory` skill 维护。这解释了为什么它单字母会用尽——它本来就不是需求域的对象 |
| `Q-`(11) | 待用户裁的开放问题 | `BLK` |
| `MR-`(38) | 第五类测试 | `CHK` + 对应 `method`（见 §5.2）|

> **项目自述的代价**（`00-id-registry.md`）：「这三套 ⛔ 不受 `ms-verify --docs` / `realign` 检查 ⇒ 死链、孤儿、漂移只能靠人工发现」。本设计消除这个代价。

## 4. 五场景流程

### 4.1 共用骨架

| 阶段 | 动作 | 完成判据 |
|---|---|---|
| 1 分类 | 判 `F.kind` 与 **`F.behavior`** | 目标行为、影响对象、非目标可区分 |
| 2 建契约 | 生成 `F` + (`US`) + `AC`；登记 `BLK` | 每条 AC 可证伪；未知⛔不伪装成确定事实 |
| 3 设计 | 仅在有技术岔路 / 边界变化 / 不可逆决策时产 `ADR` | 决策与受影响消费者明确 |
| 4 计划 | `AC → CHK`，再由 CHK + 设计拆 `T` | 每条 AC 有 CHK；每个 T 可派单（P4）|
| 5 执行 | 实施 → 跑 CHK → 留证据 | ⛔ 不得用实现代码自证行为正确 |
| 6 关闭 | 核对 AC、更新当前态与索引 | 无未解除完成门 |

**分叉只发生在阶段 1 和 2。** ⛔ 不为五个场景各复制一条流水线。

### 4.2 各场景差异

| 场景 | `F.kind` | `F.behavior` | US | AC 主形态 | CHK 主 method |
|---|---|---|---|---|---|
| 需求 | — | — | — | —（`/ms-prd` 产出上游，桥接后才编号）| — |
| 功能 | `feature` | `change` | **必需** | `condition` | `e2e` / `integration` / `unit` |
| 升级 | `upgrade` | `preserve` | ⛔ 无 | `invariant` + `condition`（版本/构建/部署）| `integration` / `deploy` / `migration` / `static` |
| 重构 | `refactor` | `preserve` | ⛔ 无 | `invariant` | `unit` / `integration` / `replay` |
| 治理 | `governance` | `preserve` | ⛔ 无 | `condition`（规则生效）| `static` / `manual` |

> **⚠️ 对用户原判断的修正**：「验证以单元测试或集成测试为主」——`UT/IT` 是**默认**，⛔ 不是排他。实证反驳：`MR-013`~`023` 是静态/PR 核对，`MR-033`~`037` 是上线一次性动作 + 存量数据迁移对账（`03-test-e2e.md:304` 独立成节），`MR-038` 是部署就绪核对。这三类在重构项目里跑不掉。

### 4.3 混合场景必须拆

一个 `F` 只能有一个 `behavior`。名为等价迁移但含真实行为变化的，⛔ 必须拆成两个 `F`。

> 实证：`F-021` 拆为 `F-021a(refactor/preserve)`（复制文件、构建配置、双副本纪律）+ `F-021b(feature/change)`（角色切换、确认框、跨 SPA 跳转、登出）。

## 6. 文档结构

> 用户要求「先做对象模型收敛，然后文档结构」。本节是第二优先级，且**可以独立于 §3~§5 决策**。

### 6.1 问题：膨胀，不是类型

`ai-code` 现状（2026-09-11 实测）：

| 文件 | 体量 |
|---|---|
| `02-system-design.md` | 212 KB / 1,820 行 |
| `01-requirements.md` | 180 KB / 1,306 行 |
| `00-context.md` | 180 KB / 1,326 行 |
| `backlog.md` | 172 KB / 2,809 行 |
| `04-dev-tasks.md` + 4 分册 | 144 KB + 366 KB |

这是**对象数量随项目规模线性增长**的必然结果，与 §1 的类型问题正交。

### 6.2 ⛔ 不采用「按变更重组目录」

外部方案提议改为 `changes/<ID>.md` + `verification/` + `tasks/` + `evidence/` 按变更组织。**本设计拒绝**，理由：

1. DevDocs 的核心价值是**跨变更的阶段视图**——追溯矩阵、覆盖率、`ms-verify --docs` 的层间对齐，全部是横切的。按变更组织后这些都要靠 index 重建，而 index 失管会形成新死链。
2. 迁移面巨大，而 `ai-code` 正在跑。
3. 它解决的是膨胀，而膨胀有更便宜的解法（§6.3）。

### 6.3 分册依据 = 对象模型的字段

`04-dev-tasks` 已经用「按层级分册」（core/api/ui/infra）验证了分册模式可行。本设计把它**提升为通用规则，并用 §3 新增的字段做分册键**：

| 文件 | 超阈值时的分册键 | 分册后 |
|---|---|---|
| `01-requirements.md` | `F.kind` | `01-requirements-feature.md` / `-upgrade.md` / `-refactor.md` / `-governance.md` |
| `03-test-cases.md` | `CHK.method` 分组 | `03-check-automated.md`（unit/integration/e2e/journey/replay）/ `03-check-manual.md`（static/manual/deploy/migration）|
| `04-dev-tasks.md` | 现状（层级）| 不变 |

**主文件只留索引 + 跨分册的矩阵与统计**，分册持有条目正文。

> 这一节与 §3 是耦合的：**对象模型新增的字段同时就是分册依据**。不做 §3 就没有稳定的分册键——这正是 `ai-code` 的 `04` 分册按"层级"（🔴🟡🟢⚪，一个非正式字段）分的原因。

### 6.4 强制 frontmatter

`00-id-registry.md` P4 实测：33 个 `04-task-*.md` 无 frontmatter ⇒ `realign` 扫不到、`ms-verify --docs` 检不到。

⇒ `docs/devdocs/**/*.md` **全部**必须有 frontmatter（含 `spec_version`）。已有 `schema/spec-version-legacy` rule 检测，只需把 `04-task-*.md` 这类旁路产物纳入扫描范围。

## 8. 代价与残留

1. **`CHK` 看不出测试层级**——必须读 `method` 字段。换来的是验证方式可变而 ID 不变，且容纳 `MR` 那 38 条。
2. **`F.behavior` 靠人填**。填错（把有行为变化的填成 `preserve`）会绕过 US/AC 保护。缓解：`ms-dev-tasks:191` 已有的「判不准默认走 F+AC」提升为 01 层强制规则。
3. **迁移期搜索会同时命中新旧 ID**。需要 alias 表与工具支撑。
4. **⛔ 不解决重构任务的拆分粒度**。`T-31`~`T-90` 被判粒度过粗的根因是「重构目标结构依赖迁移后的真实代码」，任何需求模型都救不了。需要一条独立规则：**重构只能按已证实的影响边界滚动拆分，尚未出现的目标结构⛔不得提前细拆**。
5. **`G-` 移出 devdocs 后**，agent 纪律与需求追溯分家。这是正确的分家，但需要 `agent-memory` 侧承接 41 条。
6. **存量 `ai-code` 迁移有成本**：删 9 条 US、拆 1 个 F、迁 25 条 CON、转 15 个 T 为 BLK、41 条 G 移库。可只约束新增，存量渐迁。
