## 2. 原则 4：反向依赖 —— 连接层永远在文档

未达成程度最深、也是唯一需要重新设计的一条。

### 2.1 判据

> **代码丢了这些上文信息，也能正确被解读、能正常维护，只是丢失背景信息。**（用户原话）

按这条重分性质：

| 该留在代码里 | 不该留 |
|---|---|
| 让人理解和维护这段代码的东西：意图、约束、为什么这么写 | **指向外部系统的编号引用** |

`@satisfies AC-001` 对一个没有 DevDocs 上下文的维护者是纯噪音——不知道 AC-001 是什么、去哪查、还在不在；DevDocs 一旦丢失或过期，它就是指向虚空的指针。

这条界线**仓库自己早就画过**：`ms-code-self-describe` 的对照表把「自描述（INPUT/OUTPUT/POS，架构理解）」与「追溯标注（`@requirement`/`@satisfies`，需求追溯）」分列两栏。本方案沿这条线切：自描述留，追溯标注删。

### 2.2 依赖方向的正确理由：所有权与污染边界

⚠️ **本节推翻本方案第 1 稿的论证。** 第 1 稿写的是「指针应该从易变（文档编号）指向稳定（commit hash）」——经外部评审逐条驳回，且驳得对。用户原话给的理由本来就是**上下文与污染**，不是稳定性；「稳定性」是展开时自行添加的论证，且经不起推敲。

⛔ **正确的依赖规则**：

> **私有上下文可以依赖代码；代码不得依赖私有上下文。**
> commit 是**变更事件锚点**；**当前实现**始终以当前代码和测试为准。

`commit hash 稳定`这条不成立，五条理由：

1. **hash 不是永久稳定地址。** rebase 不是「hash 变了」，是**产生了一个新 commit**，旧对象可能最终不可获取。它的稳定性只在「该 Git 对象仍可达、可取回」的前提下成立。
2. **commit 表示一次变化，不表示当前实现。** 后续重构、移动、替换、删除之后，原 commit 仍能解释「当时为什么改」，但答不了「现在由哪里实现」。
3. **映射天然多对多。** 一条 AC 可跨多个 commit；一个 commit 也可能同时满足多条 AC。单 hash 字段很快不够用。
4. **等价变化拿不到相同 hash。** cherry-pick / rebase / squash / 冲突解决 / 补格式都会产生不同 SHA；revert 之后原 hash 仍在，但其行为已不再生效。
5. **裸 hash 缺仓库作用域。** 多代码根下 `a1b2c3d` 没有意义。

⛔ **不得用 commit hash 替代当前代码导航。** 它擅长回答「这项变化当时发生在哪」，不擅长回答「今天由哪里实现」——后者由当前代码搜索、测试和必要的语义检查回答。

### 2.3 连接形态

⛔ 连接不是裸 hash：

```yaml
changed_by:            # 命名刻意不叫 implemented_by
  - repository: <code_root 名>
    commit: <full-sha>
    patch_id: <git patch-id，机器生成>
    note: <一句话，hash 失效时的人工找回线索>
```

⛔ **字段名是 `changed_by`（变更来源）不是 `implemented_by`（由谁实现）。** 这不是措辞洁癖——按 §2.2 第 2 条，commit 只是**变更事件锚点**，不证明当前实现；它甚至可能已被 revert。叫 `implemented_by` 会把事件锚点重新读成「当前满足关系」，正是本节要防的误读。

- **一条 AC 允许挂多个 commit**（多对多，见 §2.2 第 3 条）。
- 文件路径 / symbol 可作**可刷新缓存**，⛔ 不得作为真源。
- 追溯矩阵原「入口代码 / 测试代码」两列（填 `src/user.ts:15` 这类行号）合并为本结构。**丢掉行号丢的是假精确**——示例里三条 AC 的入口代码全指向同一行。
- ⛔ **任务台账的 `commits` 字段用同一形状**（`04-dev-tasks.md` 条目，供 drain 定位 Commit 1）。两处主体不同（AC ↔ 变更 vs 任务 ↔ 变更）但**形状必须一致**，否则 drain 拿不到 §2.4 的降级链——实施时曾漏掉这点，导致 sha 失效后 drain 永久卡在 `review_pending` 且无恢复路径。

### 2.4 hash 失效的降级链

**已决（用户）**：不建重量机制，但接受一个机器生成的备用指纹。

外部评审指出：shell 上游 force-push 之后，旧 commit 对象可能从上游**取不回来**——已有本地 clone 或许还能读到，新环境可能无法初始化旧 gitlink，本地 GC 后也可能失去对象。那时丢的不只是索引，是**「当时用了什么代码」都无法复现**。对一个专门承担 why 记忆的文档层，完全放弃恢复性过于激进。

三级降级，全程**不阻塞**：

| 情形 | 动作 |
|---|---|
| SHA 可解析 | 直接使用 |
| SHA 不可解析 | 按 `patch_id` 在当前上游历史中找等价提交 |
| 仍找不到 | ⚠️ 警告，回到**当前代码事实**，不阻塞流程 |

`patch_id` 覆盖最常见的「同一补丁被普通 rebase / cherry-pick 换了 SHA」；⛔ **覆盖不了 squash、内容修改、多 commit 合并**——那些仍按用户裁决回退到代码事实。成本只是一个自动生成字段 + 一次 best-effort 查找。

### 2.5 与 shell 已有枢纽的关系：不是同一层

外部评审曾提出：`workspace-topology/references/protocol.md` §6.3 已规定 shell 下外壳仓 commit 记录各子模块 SHA 作为追溯枢纽，新方案不该并行发明第二套连接层。

⚠️ **本方案第 3 稿曾据此设计「shell 下首选记外壳仓 commit」，第 4 稿撤销。** 那个设计一次派生出三个矛盾：`repository` 定义为 `code_root` 名而外壳仓不是 code_root（取值冲突）／ 声称消费方不分支但 shell 要额外 `git ls-tree` 解 gitlink（分支了）／ `patch_id` 变成外壳仓提交的指纹，救不了真正需要恢复的子模块对象（指纹对错了对象）。

**正确的回应不是收敛，是说清两者不在同一层**：

| | gitlink（§6.3 已有）| `changed_by`（本方案）|
|---|---|---|
| 追什么 | 外壳仓某个时间点 ↔ 各子模块版本 | AC ↔ 哪次代码变更 |
| 性质 | **工作区状态**，git 原生机制 | **需求追溯**，本方案定义 |
| 主体 | 外壳仓 commit | AC |

主体和层级都不同，同时存在**不构成两套连接层**——是两个不同问题各自的解。⛔ 本方案不碰 gitlink，`changed_by` 也不经由它。

因此 `changed_by` 恒记**代码所在仓**的 commit，三种 mode 形状与取值规则完全一致（`repository` 就是 `code_root` 名），消费方零分支，`patch_id` 恒是需要恢复的那个对象的指纹。

### 2.6 现役 commit 比代码注释脏

查证结果：现役 7 个 trailer 全是 DevDocs 内部流程状态，消费方 **100% 在 DevDocs 内部**。

| trailer | 消费方文件数 | 对不知道 DevDocs 的维护者 |
|---|---:|---|
| `External-Review-Verdict` | 4 | 纯噪音 |
| `Review-Batch-Id` | 5 | 纯噪音 |
| `Review-Due` | 6 | 纯噪音 |
| `Pending-Reason` | 6 | 纯噪音 |
| `Profile-Downgrade-Reason` | 4 | 纯噪音 |
| `Skip-Trace-Reason` | 5 | 纯噪音 |
| `Exploration-Mode` | 4 | 纯噪音 |

代码注释只有 1 种（`@satisfies`），commit 有 7 种。**本原则的第一个受害者是现役 commit 格式，不是代码注释。**

这 7 条的语义其实都是「**T-07 这个任务**的外审还欠着」——属性主体是任务，不是 commit。绑任务编号即可，任务编号在文档侧、由文档侧管理，完全不碰 commit。这样 squash 只伤考古索引，⛔ 不伤门控。

## 4. commit 模板

**已决（用户）：格式强制，内容不做强校验。**

> 「commit 模板即格式需要强制，内容不做强校验，因为几乎很难做」

### 4.1 准入判据

**每条信息，一个不知道 DevDocs 存在的维护者都能读懂并用上。**

| 进得来 | 进不来 |
|---|---|
| 改了什么 / diff 表达不了的取舍 / 实际跑过的测试命令 / 破坏性变更 | `F-012`·`AC-034`·`T-07` 等私有编号；§2.6 那 7 个流程 trailer |

### 4.2 格式

⚠️ **第 1 稿的五段式已废弃。** 外部评审指出：**字段越多，填空倾向越严重**——只强制格式不判内容，长期必然退化成 `Why: 完成相关修改` / `Tests: 测试通过`，既没拿到记忆又付了成本。

对策不是加字段，是**压到最小 + 把能绑机器事实的都绑上**：

```
<type>(<scope>): <描述可观察结果的一句话>

Why: <只写代码和 diff 表达不了的决策、约束、取舍>
Tests: <实际执行过的精确命令>
```

| 规则 | 强制程度 | 怎么查 |
|---|---|---|
| 标题描述可观察结果，⛔ 不带 `T-`/`F-`/`AC-`/`UT-` 私有编号 | ⛔ | 词法 |
| `Tests` 由**实际执行记录生成**精确命令 | ⛔ | 机器生成，⛔ 不允许手填「已测试」 |
| ⛔ 禁占位文本：模板原文、`TODO`、`N/A`、「相关修改」、「测试通过」 | ⛔ | **词法检查，不是语义校验** |
| `Why` 只写取舍；机械变更 ⛔ 不强迫编造 | 软 | 不判 |
| ⛔ 不要求复述 diff | — | git 已经存了 diff |
| commit 保持原子 | 软 | 小而单一的 diff 比四段空泛说明更容易恢复上下文 |

**禁占位文本这条是关键**：它拿到了「防填空」的大部分收益，却仍然只是词法检查——不违反「内容不做强校验」的裁决。

⛔ 用纯格式规则**保证不了** `Why` 有价值。策略是把必须手写的主观内容压到一个字段，其余证据自动产生，⛔ 不假装格式校验等于内容质量。

### 5.1 `ms-verify --impl` 的替代判据

⚠️ **先更正本方案第 1 稿的事实错误**：`p-severity-rubric.md` 里 **P1 是「核心 AC 无 `@satisfies` 标注」**，**P2 才是「`@satisfies` 覆盖率 < 80%」**。第 1 稿把两条并成了「覆盖率 <80% = P1」，写错了。

⛔ **不用「有 commit 的 AC 比例」替代覆盖率。** 那只是换一种形式统计指针，同样不能证明实现正确——旧指标是便宜的可计数代理、信号很弱，删掉标注后没必要再造一个弱百分比。

覆盖率指标**整体删除**，替换为两条有实际质量含义的判据：

**先定义「独立行为证据」**（下面两处判据与四步检查共用同一定义，⛔ 不得各自解释）：

> 满足以下任一即算：**独立测试**（能实际执行并通过）／ `--ui --live` 截图 ／ **显式豁免记录**（写明理由与豁免范围，落盘可复核）。

| 级别 | 判据 |
|---|---|
| **P1** | 任一**核心行为型 AC** 与当前代码行为矛盾，或**不满足上述「独立行为证据」定义** |
| **P2** | 非核心 AC 无法从当前实现、现存测试和关联变更中形成可复核证据链 |

⚠️ **显式豁免记录解除 P1，但必须在 verify 报告里单列。** 这条边界要写死：豁免是「这条 AC 换一种方式验」，⛔ 不是「这条 AC 以后再验」——后者本仓已在删 skip 参数族时判过死（「唯一效果是把现在必须做的变成事后要补的债」）。豁免记录里写不出「换成什么方式验了」的，不算豁免。

`--impl` 的检查顺序：

1. 从文档的 `repository` + `commit` 找到当时的变更范围
2. 检查这些行为**在当前代码中是否仍然存在**——⛔ 不是只检查旧 diff
3. 定位现存测试并**实际执行**；行为型 AC 必须满足上面定义的「独立行为证据」
4. 对 linked hash、被 revert 的 commit、已删除的实现**分别报告**；⛔ 不得把「hash 存在」等同于「AC 已满足」

这与本仓已确立的质量地板一致（行为型 AC 至少一条独立行为证据、受影响测试必须执行），也守住了「生产方自查表不是验收证据」——验收方从当前代码重算，不读矩阵放行。

### 5.2 原子迁移的范围边界

⛔ **「删标注」在本方案里指两件不同的事，必须分清，否则原子迁移的范围不清楚：**

| 删什么 | 在不在原子迁移范围内 |
|---|---|
| **skill 侧的规则与消费逻辑**——三处「必须添加标注」强制项、标注删减检测、`sync --trace` 的扫描、`verify` 的覆盖率指标、`test-run` 的标注一致性检查 | ✅ **在**。这些必须与新判据一起原子完成，否则进入「规则仍要求、对象已消失」的半迁移状态 |
| **消费方项目代码里的存量标注**（mic-en 636 处）| ❌ **不在**。留着，⛔ 不做一次性清理 |

存量不清理的理由：它们已经在那里了，删除是纯风险且无收益。规则删掉之后，它们退化为**无人消费的历史注释**——不再被强制、不再被扫描、不再影响任何判据，只是还占着几行。新规则只约束新增。

⚠️ 由此产生一条必须写进 `code-quality` 的注释纪律：**⛔ 不得新增 `@satisfies` / `@requirement` / `@verifies` / `@testcase` 标注。** 否则规则删了、习惯还在。

## 9. 本方案证不了什么

- **`patch_id` 的实际命中率没测过。** 它只覆盖普通 rebase / cherry-pick 换 SHA；squash、内容修改、多 commit 合并一律落到「回退代码事实」那一档，而那一档的重建成本未知。
- **「禁占位文本」的词法清单会被绕过。** 拦得住 `TODO` 和「测试通过」，拦不住换一种说法的废话。它降低填空率，⛔ 不消除。
- **`Tests` 由实际执行记录生成，前提是执行记录拿得到。** 手工验证、UI 走查、外部环境测试这几类没有可粘贴的命令，那时仍会退回手填。
- **`sync --trace` 改扫 git 历史的可行性未实测。** 尤其 shell 拓扑下要跨子模块查，还要处理 §2.4 的三级降级。
- **§5.1 的新判据比旧的贵得多。** 旧的是数注释比例，新的要读当前代码、跑现存测试。`--impl` 的运行时间会显著变长，没估过。
- **INS 四路分流的分类准确率未验。** 「这条是决策还是经验」是语义判断，靠 AskUserQuestion 问人——问得准不准取决于选项怎么写。
- **semver 纪律能否替代 330 行反模式清单，未验。** 清单里的决策树和话术模板会一起删掉。
- **本仓无 `docs/devdocs/`，全部效果无法自举验证。** 但删除与新建的风险不对称：删错了 git 能取回，挂着的成本是每天付。

## 9.1 实施暴露的两条教训

1. **差点两次重新发明现役能力。** 「`state/total-size-cap` 扩作用域」与 §3.2「close 时编号级清理」都已由 `/ms-sync --archive` 覆盖。共同成因：设计时**从原方案的目标清单往下推**，没先盘一遍「这个目标今天是不是已经有人在做」。§1 的达成盘点本该拦住，但它只做到原则层，没下到具体能力层。

2. **把「案例过期」误读成「问题作废」，且自己下了判决。** 用户说 mic-en 是过期案例、别再从它推导；本方案读成了「它提过的问题一律不算数」，据此自行划掉 §3.2 §3.3、还提议撤回已落地的 §3.1——三次自己做主，而手上一直有 AskUserQuestion。「影响范围大」「证据只有一例」恰恰是**该问的信号**，不是自行裁决的理由。
