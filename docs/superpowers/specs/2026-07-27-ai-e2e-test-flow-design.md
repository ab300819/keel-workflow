# AI E2E 测试工作流(e2e-test-flow)设计

> 状态:设计定稿 · 日期:2026-07-27
> 定位:**standalone skill**,与 DevDocs 独立,不进 ms- 命名空间

## 1. 定位

消费已有的测试用例文档(md / html),对**运行中的真实系统**做 AI 驱动的**黑盒**端到端实测:先摸清本次分支影响了什么、优先测受影响部分,先打接口再跑 UI,全程只读观测数据库佐证,未通过的交人工确认。

**被测系统**:Java / Spring Boot 微服务,多项目同一工作区,自研 RPC(`@Provider` / `@Consumer`),另有 `@Job` 等非 HTTP 入口。

**与本仓已有 skill 的边界**:

| skill | 职责 | 关系 |
|-------|------|------|
| `ms-test-cases` | 设计用例文档 | 上游,产出物可作输入 |
| `ms-test-run` | 跑项目**自带**测试套件 | 兄弟;集成测试腿可复用 |
| `testing-guide` | 写测试代码的规范 | 被引用 |
| **`e2e-test-flow`** | 消费**已有用例**对**运行中系统**黑盒实打 | 新增,无重叠 |

**与 DevDocs 独立**:不读 `docs/prd/` `docs/devdocs/`,不写 F/US/AC 编号,不产追溯矩阵,不调 ms-* skill。用例编号沿用文档自身(如 `TC-J-001`)。产物落**系统临时目录,不入库**。

## 2. 设计原则

> **流程保持简单干净。任何不确定 —— 环境、连接方式、是否允许写、预期是否明确、用例该怎么测 —— 一律询问用户,而不是靠协议猜。**

这条是本方案的**首要原则**,优先于下面所有细则。细则只描述常规路径;遇到边界情况,**问用户**就是正确答案。

## 3. 四条纪律

**D1 数据库只读** —— Agent 直连数据库只执行 `SELECT`,禁写。对被测系统的写操作走其自身 HTTP 接口(dev/test 环境)。连接时要求只读账号;拿不到只读凭据就问用户怎么办。

**D2 预期结果 = 判定唯一权威** —— 判定只依据用例的 `预期结果`。不自造预期;预期不明确 → 标 `BLOCKED` 并**问用户**。未通过 = **疑似缺陷,交用户确认**,绝不放宽预期或改用例来凑全绿。

**D3 不改被测对象** —— 不为了测试而修改被测页面/代码。唯一例外是 `fault-injection` 必需的页面 hook(§7.3),**必须留痕**。定位元素优先用页面既有锚点(文本 / `data-testid` / role+可访问名 / snapshot uid / 截图),**动态注入 aria 标签默认关闭**;真要用则 transient、**永不作断言依据**、必留痕,并把"页面无障碍差"作为缺陷建议产出。

**D4 白盒只用于排序,判定纯黑盒** —— 阶段③(影响分析)读代码,其结论**只用于提升优先级,永不用于缩小范围**。阶段④⑤只经外部接口驱动、只按用例预期判定,**禁止**用实现代码当"预期应该是什么"的来源。

落地方式:③与④⑤**由不同子 Agent 承担**,跨界只传**用例原文 + `{入口路径, 方法, 优先级}`**(即外部黑盒测试者本可获知的信息),代码/调用链/推理过程不过界。黑盒子 Agent 不给 idea MCP、不读被测源码;Bash 仅用于 curl。

> 隔离强度取决于工具权限能否真正收窄。做不到就在报告里标注"隔离为尽力而为",**不假装做到了**。

## 4. 测试范围:只做功能,不做视觉

| 在范围内 | 出范围 |
|---|---|
| 跳转是否正确、内容是否变化 | 颜色、字体、间距 |
| 字段值、排序、数量限制 | 文本截断与省略号、hover 视觉态 |
| 接口调用与数据落库 | 布局溢出、像素比对 |
| 空态 / 失败态**是否出现** | — |

**文案内容**(按钮文本、金额格式 `USD 2,000.00`)属功能正确性,**在范围内**(靠 snapshot 文本比对);**呈现样式**出范围。

纯视觉用例 → 标 `OUT-OF-SCOPE(视觉类)` 列入报告,**不静默跳过、不假装通过**。

## 5. 流程

```
① 用例摄取      md/html → 结构化用例集
② 分类加工      每条用例定一个执行路由(§6)
③ 影响分析      git diff → 受影响入口 → 优先级   [白盒子 Agent]
                    ↓ 只传 用例原文 + {路径,方法,优先级}
④⑤ 实测        按路由执行,只读观测 DB 佐证       [黑盒子 Agent]
⑥ 报告          自包含 HTML 面板(临时目录,不入库)
```

**开跑前一次性确认**(§8):环境、认证、代理、DB 连接、是否允许写。

## 6. 用例路由(单一分类表)

阶段②给每条用例定**一个**路由,同时决定"走哪条腿"和"有无副作用"。**一条用例只有一个路由,不叠加维度。**

| 路由 | 特征 | 执行方式 | 副作用 |
|------|------|---------|--------|
| `api` | 后端数据驱动(统计口径、换算、排序、数量限制) | curl 经代理 + 只读 DB 观测 | 视接口而定 |
| `ui` | 前端功能行为(跳转、局部刷新、内容变化、文案) | 浏览器(chrome-devtools) | 视操作而定 |
| `ui+api` | 旅程类(点按钮 → 跳转 → 数据一致) | 浏览器为主,同时采网络记录 + DB 观测 | 视操作而定 |
| `fault-injection` | 异常态(接口失败 → 占位、超时 → Retry) | 浏览器 + 页面 hook(§7.3) | 无 |
| `non-http` | `@Job` 等非 HTTP 入口 | 集成测试腿(§9) | 视任务而定 |
| `visual` | 纯视觉表现 | **不执行**,标 `OUT-OF-SCOPE` | — |
| `blocked` | 前置数据/环境不满足,或预期不明确 | 如实标注 + **问用户** | — |

**副作用判定(执行前,从用例文本判断)**:`steps` / `title` 含支付/提交/确认/取消/删除/下单/修改等状态变更语义 → **写型**;语义不明 → **保守按写型**。

**写型用例的三条规则**(适用于全流程,无例外出口):
1. **只执行一次,一次取全证据。** 由**首个外部动作**(浏览器点击 / curl / Job 触发)完成执行,同时采集该用例所需的全部证据(响应 + UI 快照 + DB 观测)。不为了"分阶段"而重复执行同一个写操作。**录制时发生的那次动作就是唯一执行**,事后不得再用 curl 打一遍同一个写操作。
2. **转出的 curl 只作产物交付**给用户手工重放,**工作流不自动重打**。
3. **不自动重试、不自动重跑。** §11 的抖动重试与"修正后重跑"**仅适用于非写型用例**。写型用例任何形式的再次执行(重试 / 重跑 / 验证重复提交)→ **一律先问用户**,并按用户答复确认是换新账号还是接口本身幂等。

> 附带写入(审计日志、已读标记、会话状态)无法避免,由 §8 的 run 级确认一次性覆盖;逐例判断只针对**业务语义写**。

## 7. 实测细则

### 7.1 接口怎么找:录制,不猜

用例文档**不含接口信息**。解法优先级:

1. **浏览器录制真实请求**(主力)—— 用浏览器走一遍用例步骤,`list_network_requests` 拿到真实发出的请求。**把"猜接口"变成"观测接口"**,与 D4 黑盒纪律契合。
2. **交叉校验** —— 用阶段③的 `{路径, 方法}` 核对是否命中受影响入口。
3. **curl 样例兜底** —— 用户提供的 curl 样例给出请求头/代理/签名骨架(页面到不了的接口用)。

**录制 ≠ 天然可重放**:短时 token、CSRF、签名 nonce、BFF 聚合都可能让重放失效。首次重放前先拿一个**只读**请求验一下能否复现;不行 → 改走浏览器验证,或**问用户**要可用的请求生成方式。**不把重放失败当被测系统的缺陷。**

### 7.2 数据库只读观测

- **连接方式问用户**(`mcp__sqldev__run_query` / `mcp__idea__execute_sql_query` / CLI 均可),要求**只读账号**
- 只跑单语句 `SELECT`;不用存储过程/函数(可能内含写)、不用显式事务
- **不做写探针**验证只读权限(那本身就是写);只查权限元数据,或采信用户声明。证明不了 → **问用户**
- **观测时机**:写操作前后各取一次,对比差异;**观测内容由用例预期驱动**,不 dump 表
- **观测可靠性**:共享环境里并发写入会干扰因果性,异步落库需要等待。所以——用**专属测试账号**收敛观测范围、用**关联键**(订单号等)锚定记录、异步场景**轮询到终态**。做不到 → 该观测标为"**指示性而非结论性**",不单独作为 FAIL 依据;或问用户

### 7.3 fault-injection

> **能力核实(2026-07-27)**:`chrome-devtools` 与 `playwright` MCP **都只暴露只读网络工具**,没有请求拦截/响应篡改能力。所以"网络拦截"不是现成能力。

可行手段:① 经 `evaluate_script` 给 `fetch` / `XHR` 打补丁返回构造的失败响应(属注入,**必留痕**,遵守 D3);② 非法参数触发系统真实错误分支(最干净);③ 断网/超时模拟(粒度粗)。

**都不适用 → 执行前判 `BLOCKED`,不假装测过。**

### 7.4 判定

逐条比对用例 `expected`,给 `PASS / FAIL / BLOCKED / OUT-OF-SCOPE` + 证据(响应片段、SQL 观测、截图)。**证据里的凭据必须脱敏**:认证头 / Cookie / token / 签名在落盘前替换为占位符,交付的 curl 用 `$AUTH_COOKIE` 之类占位符 + 填写说明,敏感业务数据按需打码。

## 8. 开跑前的一次性确认

不搞复杂的门禁机器,就是**开跑前问清楚并记下来**:

| 确认项 | 说明 |
|--------|------|
| 环境 | dev / test(**不对生产跑**);目标地址经代理后的真实去向 |
| 认证 | cookie / curl 样例(**整个会话一份**,除非切账号) |
| 代理地址 | curl 经代理访问,代理内部细节对 Agent 透明 |
| DB 连接 | 连接方式 + 只读账号 |
| 测试账号 | 专属测试账号/租户(供 §7.2 收敛观测) |
| 是否允许写 | 写接口照常测(dev/test);**若目标疑似生产 → 停下问用户** |

确认结果随报告产出,使"这批结果是对哪个环境、什么账号跑的"可追溯。**运行中要变(如切账号)→ 重新确认。**

**前置数据**:走被测系统写接口铺,或用提前准备好的账号。不满足 → `BLOCKED(前置数据缺失)` 如实上报(D1 下 Agent 不造数)。

> **铺数也是写动作**:若铺前置数据会产生业务状态变更,该动作**同样适用 §6 写型规则** —— 与用例本身是否写型无关。续跑 / 失败修正 / 重新铺数等可能再次执行铺数动作的场景,**先问用户**。

## 9. 影响分析(阶段③)

**为什么不能只做 HTTP 签名 diff**:真实逻辑变更常在 RPC / service 层,**HTTP endpoint 签名可能毫无变化**。所以做的是影响分析,不是签名对比。

**产出**:受影响的**顶层入口**集合,每项带 `{类型, 如何触发}`。入口类型**可配置**,不写死 HTTP:

| 入口类型 | 锚点 | 触发方式 |
|---------|------|---------|
| HTTP | `@RestController` / `@*Mapping` | curl 直接触发 |
| 定时任务 | `@Job` | 不能 curl → 集成测试腿(§10) |
| RPC | `@Provider` | 间接:经消费方 HTTP 入口 |
| 其它 | 用户可补充的注解 | 按类型定 |

**追溯链**:
1. `git diff <分支>...master`(全工作区)→ 改动方法
2. **服务内**:`analyze_calls` 向上追溯到 `@RestController`
3. **跨服务**:改动落在 `@Provider` → 搜工作区对应 `@Consumer` → 从消费点再向上追溯到消费方入口

**证据优先级**:有 RPC 注册表 / IDL / 运行时 trace 则优先采信,静态注解搜索是最弱一环。有 OpenAPI/Swagger 可用 spec diff 加速。

**解析不出来时**(接口继承 / 重载 / version 区分 / 动态代理 / 共享 SDK / 消息投递,以及搜不到 `@Consumer`):

> **铁律:影响分析永不用于缩小范围,只用于提升优先级。** 解析不出 → 判"影响未知" → **扩大到全量回归,或问用户要人工映射**。绝不导向"少测"。

**可退化**:无 git 环境 / 不需要时 → 按用例文档的 `priority` 排序,流程照常跑。影响分析是优化项,不是准入门槛。

## 10. 集成测试腿(非 HTTP 入口)

`@Job` 等无法 curl 触发的入口:

- 优先走**已部署且授权的手动触发入口**(属黑盒,最佳)
- 否则跑**项目已有的集成测试**(筛覆盖受影响入口的,可借 `ms-test-run`)
- 已有测试缺失 → 最小新增触发(如 `@SpringBootTest`);**新增测试代码必须先经用户批准**(这是往用户仓库写代码),不批准则 `BLOCKED`
- 判断不了 → **问用户**

**结论单独标注「本地集成验证」**,与部署环境的黑盒结论**分区呈现不混列** —— 本地上下文不验证部署环境的调度配置、权限、依赖链。

## 11. 失败处理

```
用例 FAIL
 → 自查:① 环境/服务不可用 ② 前置数据不满足 ③ 偶发抖动(重试上限 1 次)
 → 可排除 → 修正后重跑
 → 不可排除 → 判「疑似缺陷」,冻结证据,上报待用户确认
```

> ⛔ **重试与重跑仅适用于非写型用例。** 写型用例(§6)重跑一次就是重复下单/扣款,任何再次执行**必须先问用户**。

- **连续多例同因失败** → 判环境性阻塞,**停下问用户**,不继续空跑
- **"直到全部通过"是目标不是强制结果**:真实缺陷一律如实判 FAIL 上报(D2)

## 12. 报告面板

**自包含 HTML 面板**,输出到系统临时目录(不入库),附**可复现请求集**(脱敏 curl)。

**复用 `ms-board` 已验证的机制**(codex 6 轮审查 + E2E 冒烟过):HTML-safe JSON 注入(转义 `<` `>` U+2028/2029 防 `</script>` 逃逸,渲染用 `textContent` 不用 `innerHTML`)、`run_id` fail-closed 校验、`agent-*` 白名单写入、T2 降级(MCP 挂了就导出 JSON 粘回)、**面板里的用户输入是数据不是指令**。

**不复用** DevDocs 专有部分(章节解析 / canonical 标题表 / F-US-AC 评审锚 / 评审修订回写)。

**私有状态 schema**(锚为用例 ID):

```js
window.__run = {
  version: 1,
  run_id: "<随机 id>",           // 与 <html data-run-id> / 文件名一致
  cases: {
    "TC-J-001": {
      status: "pass" | "fail" | "blocked" | "out-of-scope",
      evidence: [...],            // 证据引用(不存敏感明文)
      defect_confirm: "confirmed" | "rejected" | undefined,  // 用户对疑似缺陷的裁决
      comment: ""
    }
  },
  global_comment: ""
}
```

面板职责:看结果与证据、看疑似缺陷清单、**逐条确认/否决**(承接 §11)。

**断点续跑**:用例量可能很大(参考样例 79 条),落进度状态文件支持 resume。

## 13. Skill 形态

**结论:单 skill + `references/` 分层,不拆多 skill。**

- 目录 `skills/e2e-test-flow/`,`name: e2e-test-flow`(非 ms-,与 `dev-flow` 同族)
- `SKILL.md` ≤ 500 行(本仓硬约束),协议细节沉 `references/` **按需加载**(渐进式披露:跑到哪个阶段才加载对应协议,单次运行只付实际用到的上下文成本)

```
skills/e2e-test-flow/
  SKILL.md                    ~180 行  流程骨架 + 4 纪律 + 路由表 + 何时问用户
  references/
    case-ingestion.md         用例摄取:md/html 容错解析 + 用例模型
    impact-analysis.md        影响分析:注解锚点 / 跨服务追溯链 / 退化
    execution-protocol.md     录制 / curl / DB 只读观测 / 判定 / fault-injection
    panel-protocol.md         run-state-v1 + 注入安全 + T2 降级(参照 board-protocol)
```

**规模可行性**(本仓先例):`ms-dev-workflow` 单 skill = SKILL.md 426 行 + references 2059 行,规模大于本方案且运行良好;`ms-pipeline` = 413 + 1420。**单 skill 承载多阶段是本仓既定模式,不是新增风险。**

### 13.1 为何不拆成多个 skill

1. **拆分会重新引入 R4 熔断的病根**:多 skill = 跨 skill 契约面(yaml-summary 交接、状态传递),正是"叠加维度产生交叉矛盾"的同一个坑。
2. **D4 的子 Agent 隔离不需要拆 skill 实现**:Task tool 派发子代理时给不同 `allowed-tools` 即可做到工具集隔离,与 skill 文件划分无关。
3. **单一入口**降低认知负担:拆四个会让使用者每次都要判断"这步该调哪个"。
4. **本仓教训**:multi-PRD 机器已因"为假想复用预建结构"而被整套删除。不重犯。

**工具按角色分配**(承 D4,运行时由子 Agent 承担,非拆 skill):

| 角色 | 工具集 |
|------|-------|
| 白盒分析子 Agent(阶段③) | Read / Glob / Grep / Bash(git) + idea MCP |
| 黑盒执行子 Agent(阶段④⑤) | chrome-devtools + Bash(仅 curl) + 只读 DB MCP;**不给 idea MCP、不读被测源码** |

### 13.2 FUTURE:影响分析可独立抽取

阶段③"这个分支影响了哪些顶层入口"**独立于 E2E 测试亦有价值**(code review 范围评估、回归范围界定)。

- **状态**:FUTURE(封存,不实现)
- **触发条件**:真实项目中出现**跨场景复用需求**(即 E2E 之外确实有人要单独用它)
- **不预先抽取的理由**:同 §13.1 第 4 条 —— 触发前抽取属于为假想复用建结构

> 遵循本仓 FUTURE 三态惯例(spec 存在但运行时未实现),与 layout.v2 / trace.v1 同类处理。

## 14. 残余风险

| 风险 | 处置 |
|------|------|
| 跨服务 RPC 映射不可能 100% 精确 | 只用于提升优先级,解析不出即扩大范围或问用户(§9) |
| 录制转 curl 可能被签名/CSRF 破坏 | 先验一次能否复现,不行则改走浏览器或问用户(§7.1) |
| 共享环境并发写入干扰观测因果性 | 专属账号 + 关联键 + 异步轮询;做不到则标"指示性"(§7.2) |
| 附带写入(审计日志等)无法避免 | 由 §8 run 级确认覆盖,逐例只判业务语义写 |
| fault-injection 无现成拦截能力 | 已核实两个 MCP 均只读;改页面 hook(留痕)或 `BLOCKED`(§7.3) |
| 视觉缺陷完全不覆盖 | 显式 `OUT-OF-SCOPE`,提示需人工目视(§4) |
| 用例文档格式千差万别 | 容错解析,抓不到标 `unknown` 不编造 |
| Bash 通道可能击穿工具级隔离 | 收窄至 curl;做不到则报告标注"隔离为尽力而为",不假装(§3 D4) |
| 集成测试腿是白盒且不验部署环境 | 新增代码须用户批准;结论分区标注(§10) |
