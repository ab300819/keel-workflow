# markdown-style skill 设计方案

- 日期：2026-07-31
- 状态：设计定稿，待实施
- 类型：新增独立 skill（非 DevDocs，不接入 ms- 流程）
- 审查：Codex 三轮对抗审查，结论全部采纳。方案经三次塌缩——「附带修复脚本」→「零脚本」→「自动修复白名单 27→9→4」→「首版不实现自动修复」（见 §7）

## 1. 问题

LLM 生成的 Markdown 文档普遍存在两类缺陷：

1. **标记不规范**——标题层级跳级、代码块缺语言标注、列表缩进不一致、行尾空格、缺少环绕空行
2. **排版不规范**——中英文之间无空格、全角标点两侧多余空格、全角字母数字

这两类缺陷不影响语义，但影响可读性与工具链（目录生成、语法高亮、diff 可读性）。目前没有统一入口来检查。

## 1.1 价值内核与身份

自动修复能力经三轮审查大幅塌缩后，须明确本 skill 的身份，否则会被误当作"自动格式化器"而重新引入已排除的风险：

**这是一个 Markdown 审查策略 skill，不是 Markdown 自动格式化 skill。**

价值内核（按重要性排序）：

1. 本仓统一的 markdownlint 配置与分歧决策（含为何偏离 Google docguide）
2. 中文排版规则的**出处、冲突与反例**——包括与国标冲突之处的裁决
3. M / T / L 三组的边界与默认状态
4. 保护区、语意承载豁免与降级策略
5. 稳定的报告结构
6. 生成时清单与事后审查共用同一 SSOT

这些内容若只散落在各次会话的 prompt 中，会反复漂移；作为 skill 才有一致性价值。反之，**若删去 T / L 的规则知识、豁免与出处，只剩一份配置加一句"AI 通读"，则不配单独做 skill**——此时一份 `.markdownlint.jsonc` 加通用审查 prompt 即可。这是本 skill 的存废判据。

固定版本的只读检查（第 1 项）与规则知识（第 2 至 4 项）是内核；自动修复不是，**首版完全不实现自动修复**（§3.2.1）。

## 2. 边界原则

**本 skill 只碰排版与标记，不碰原文语意。**

任何会改变文字表达、删除内容、重写句子的操作都在边界之外。**本原则无例外**——原方案曾以"越界模式"名义保留文风审查组，已删除（§7）。

这条原则是审查推翻原方案的主要依据。审查指出的两个自欺点必须写在这里，因为它们最容易复发：

1. **"只改 Markdown 标记"不等于"不改语意"**——标记、强调、emoji、结构本身都可能承载语意。删掉 `🔒 仅管理员可见` 的 emoji 会丢信息；把独占一行的加粗改成标题会改变目录与锚点；删掉 `**必须**` 的加粗会削弱规范强度
2. **"需要人确认的 assist"不等于"在边界内"**——生成一个可直接应用的语意改写 diff，仍是在做语意改写

违反本原则的规则一律不实现，或降为只报告。

| 组 | 内容 | 权威出处 | 判定者 | 默认 |

| 源 | 状态 | 备注 |

| GB/T 15834—2011 标点符号用法 | ✅ | archive.org OCR 全文，条款号可靠；**OCR 汉字识别有误，引用原文须逐字核对** |
| GB/T 15835—2011 出版物上数字用法 | ⊘ 不适用 | 见下 |

**GB/T 15835 为何不纳入**（原方案将其列为 T 组权威出处，属张冠李戴，此处更正）：该标准规定的是"何时用汉字数字、何时用阿拉伯数字"，即计量、编号、概数的**用字选择**，与 T 组关心的空格排版无关。且 2011 版相比 1995 版明确**不再强调优先使用阿拉伯数字**，规定两种形式在位数少、简洁性无显著差异时均可使用，取决于追求"简洁醒目"还是"庄重典雅"。标准本身不给强制主张，机械检查必然误报。

T 组数字相关规则（T2、T3）的依据是排版指北，不得引用本标准条款号。

### 3.2 M 组配置

**默认值调整**

markdownlint 出厂默认是"全部规则打开 + 按英文散文调的参数"，在中文技术文档上直接运行的噪音已实测量化。

**实测基线**（2026-08-11，`AGENTS.md` + `README.md` + `docs/workflows.md`，markdownlint-cli2 经 npx 取最新版）：

| 配置 | 告警数 | 说明 |
|---|---:|---|
| 出厂默认 | 138 | 其中 MD060 占 78 条（57%）、MD013 占 35 条（25%）——**82% 是噪音** |
| 本 skill 配置 | **22** | 逐条核对为 100% 真问题：MD040 × 11、MD036 × 4、MD031 × 4、MD032 × 2、MD001 × 1 |

这就是默认值调整的全部理由：没有它报告不可用，使用者很快学会无视告警。

| 规则 | 配置 | 理由 |
|---|---|---|
| MD013 line-length | 关闭 | Google 规定 80 列，源于英文纯文本时代终端宽度，对中文与 LLM 段落不适用 |
| MD033 no-inline-html | 关闭 | `<details>` `<br>` 在技术文档中常用且必要 |
| MD041 first-line-h1 | 关闭 | 片段文档、references 子文档常不以 H1 开头 |
| MD024 no-duplicate-heading | `siblings_only: true` | 不同章节下的同名子标题合法 |
| MD029 ol-prefix | `one_or_ordered` | 兼容 `1.` 全同与递增两种写法 |
| MD004 ul-style | `dash` | 统一 `-` |
| MD046 / MD048 | `fenced` / `backtick` | 统一围栏代码块 |
| MD049 / MD050 | `asterisk` | 下划线紧邻 CJK 时部分渲染器不生效 |
| MD007 ul-indent | `2` | 本仓实测 54 处 2 空格、1 处 4 空格，从既有约定 |
| MD010 no-hard-tabs | `code_blocks: false` | 不得改动代码块内的 tab |
| MD060 table-column-style | `style: "padded"` | **实测噪音第一名**（78 条 / 57%）。本仓表格为内容行加空格 + 分隔行 `\|---\|---\|`，`padded` 下降至 0 误报；`compact` 反而升至 100 条。取 `padded` 而非关闭——同样零误报，但仍能抓真正不一致的表格 |

**与 Google docguide 的两处主动分歧**（须在 references 记录理由，避免后续被当作遗漏"修正"）：Google 的 80 字符行长上限不采纳；Google 的 4 空格嵌套缩进不采纳，取 2（从本仓既有约定）。

Google docguide 其余可机械化主张（ATX 标题、围栏代码块并声明语言、行尾禁空格、图片须有 alt、长列表用惰性编号）已由 MD003 / MD040 / MD048 / MD009 / MD045 / MD029 覆盖。其 `[TOC]` 为 Google 内部渲染器专有，不纳入。

#### 3.2.1 为何不使用 `markdownlint --fix`

**首版不实现自动修复。** `markdownlint-cli2` 只做只读扫描，全部检出走报告。

原方案曾建立"安全 fixer 白名单"以支撑自动修复。`fixable` 只表示工具能修，**不表示语意安全**；原判据"纯空白、纯标记等价变换"经两轮审查证明有多个盲区，白名单从 27 条逐次收缩至 9 条、再至 4 条（MD019 · MD021 · MD032 · MD047）。这 4 条的实际价值是罕见笔误与一个文件末尾换行，其中 MD032 还是四条里风险最高者；而支撑它们需要临时目录隔离执行、stdin 切断配置发现、显式版本锁定、闭集配置校验一整套机制。收益与代价明显失衡，故整体放弃。

**以下盲区分类是本 skill 的核心知识资产**（价值内核第 2 项），须完整保留在 `references/markdown-rules.md`。它回答的是"为什么不能无脑相信 `--fix`"，也是将来若有人提议启用自动修复时必须先逐条回答的清单：

| 破坏模式 | 说明 | 涉及规则 |
|---|---|---|
| **翻转强调语义** | CommonMark delimiter run 规则决定嵌套结构。`*_foo_*`（emphasis 套 emphasis）统一为 asterisk 后成 `**foo**` = strong；`__*foo*__`（strong 套 emphasis）转为 `***foo***` 后变 emphasis 套 strong | MD049 · MD050 |
| **合并相邻列表** | 相邻的 `*` `+` `-` 在 CommonMark 中形成**不同**列表；统一 marker 会把两个列表合并 | MD004 |
| **创建结构** | 修复对象本是普通文本，修复后变成 Markdown 结构。`#Heading` 因缺空格而是普通文本，MD018 插入空格后它成为标题——这是造出新结构，不是修正已有结构 | MD011 · MD018 · MD020 · MD034 · MD037 |
| **tight/loose 列表转换** | 在列表项内的标题、围栏、表格外围插入空行，把 tight list 变 loose list，改变生成 HTML 的段落结构 | MD022 · MD031 · MD058 |
| **改变块归属** | 空行数量影响列表终止与后续块归属，压缩空行可能重新连接列表 | MD012 |
| 改动数据 | code span 内容与链接文本是数据；删除首尾空白改变复制出的字符串与可见文本（`a[ b ]c` 由 `a b c` 收缩为 `abc`） | MD038 · MD039 |
| 改动序号 | 有序列表首个数字决定 `<ol start>`；`2. 3.` 改为 `1. 2.` 改变显示编号，而迁移步骤、法规条款的来源编号承载信息 | MD029 |
| 缩进未同步 | 仅移动 list marker 或删除 linePrefix，不同步移动该项的续行、嵌套块与围栏，无法证明修复后子树归属不变 | MD005 · MD007 · MD023 · MD027 · MD030 |
| 文档实现不一致 | 官方文档标注 fixable，但实现未输出 `fixInfo` | MD060 |
| fixable 状态存疑 | 抓取所得规则表标注 fixable，但审查称官方文档未标注。**须核对原文**；若实际不可修，放入白名单只会制造"已覆盖"的错觉 | MD003 |

**MD009 的判断错误**（保留记录）：原方案称配 `br_spaces: 2` 即可保留硬换行。审查指出该参数只让"恰好两个尾随空格"不报错；遇到三个及以上尾随空格时 fixer 删除全部空格而非收敛为 2，硬换行随之消失。

#### 3.2.2 工具获取与调用

**检测顺序**（先用现成的，不重复安装）：

1. 目标仓库的 `node_modules/.bin/markdownlint-cli2`——存在则用，尊重项目自带版本
2. `PATH` 上的 `markdownlint-cli2`
3. 都没有 → **询问用户**，四个选项：

| 选项 | 命令 | 适用 |
|---|---|---|
| Homebrew 安装 | `brew install markdownlint-cli2` | macOS 首选。依赖 node，但不随 node 版本切换而失效 |
| npm 全局安装 | `npm i -g markdownlint-cli2` | 跨平台。⚠️ 若 node 由 mise / nvm / asdf 管理，包装在当前 node 版本目录下，**切换 node 版本后失效** |
| 本次临时运行 | `npx --yes markdownlint-cli2` | 不想装。首次需网络、较慢 |
| 跳过 M 组 | —— | 降级为 AI 按 `references/markdown-rules.md` 扫描，只报告 |

**不得静默安装。** 安装修改用户系统环境，必须先问。

**版本处理**：不强制特定版本——本地已装什么就用什么。但**报告头部须记录实际版本**（`markdownlint-cli2 --version`），这才是"报告可复现"的实质：知道某份报告出自哪个规则集。仅在"帮用户安装"与"npx 兜底"两种情况下建议具体版本。

⚠️ **安全提示（对只读扫描同样成立）**：CLI2 会沿目标路径发现 `.markdownlint-cli2.*` 与 `.markdownlint.*` 配置，其中 `.cjs` / `.mjs` 形式**会执行代码**，且没有关闭配置发现的命令行参数。对不受信任的第三方仓库运行扫描存在代码执行风险，须在 SKILL.md 中明示。

`--config` 只是 base configuration，可被目标路径上的子目录配置覆盖，也可被文档内 `markdownlint-enable/disable/configure-file` 注释覆盖（后者可用 `noInlineConfig: true` 禁用）。因只读扫描不改文件、误报成本低，**允许项目配置生效**——目标仓库自有的 markdownlint 约定优先于本 skill 默认值是合理行为。

### 3.3 T 组规则

全部为 `report`（§4）。原方案标为自动修复的五条经审查逐条证伪。

| ID | 规则 | 出处 |
|---|---|---|
| T1 | 中文与半角英文之间加一个半角空格 | 排版指北 §1 |
| T2 | 中文与数字之间的空格风格须统一（判据：同一文档内同时出现"5 台"与"5台"） | document-style-guide text.md（2） |
| T3 | 数字与英文单位之间加空格（`°` `%` 例外） | 排版指北 §3/§4 |
| T4 | 全角标点两侧不留**行内横向**空格 | 排版指北 §5；GB/T 15834 §5.1.1（全角标点占一个字位置） |
| T6 | 问号/叹号叠用超过三个 | GB/T 15834 §4.2.3.3、§4.3.3.3 |
| T7 | 全角字母数字宜用半角 | 排版指北 §8 |
| T9 | 中文省略号须为六连点 `……` | GB/T 15834 前言、§4.11.2 |

**逐条证伪记录**：

- **T1 原含"与数字"，与 T2 直接矛盾**——T1 若含数字，`2026年7月31日`、`第3章`、`3个节点` 会被强制加空格；而 T2 正是因为日期场景不应强制统一才定为报告。同一件事两个结论。**修正：中数关系全部归 T2，T1 只管中英**
- **T3 白名单答不了"此处是不是单位"**——白名单含 `s` 时 `iPhone 5s` → `iPhone 5 s`；裸写的 CSS `margin: 2em` → `2 em` 变成无效值。白名单仅用于**降低误报**，不构成自动修复依据
- **T4 会删除 Markdown 硬换行**——行尾两个空格是 hard break，删掉改变渲染结构。故限定为"同一行内部的横向空格"，行尾空白一律不动
- **T6 改语气强度，属语意**——`危险！！！` 与 `危险！` 语气不同。国标允许叠用最多三个（§4.3.3.3 原文示例"我要揭露！我要控诉！！我要以死抗争！！！"），§4.3.3.4 允许 `？！` 连用，§5.1.2 还为二叠、三叠、问叹连用规定了占位宽度。排版指北"不要重复使用标点符号"仅为文案风格主张，与国标冲突。**故仅报告"超过三叠"这一越界情形，二至三叠不提示**
- **T7 全角字符可能是数据本身**——Unicode 与安全测试文档中，`系统必须拒绝用户名 ａｄｍｉｎ` 转半角后测试对象即改变；全角 `＠` 可能被刻意用于避免触发 mention。检出时须附带此风险提示
- **T9 与本地参考项目冲突**——document-style-guide 主张 `⋯⋯`（U+22EF），但 GB/T 15834 前言明确"省略号的形式统一为六连点"，即 `……`（U+2026 × 2）。以国标为准，`⋯⋯` 判为不合规。`...` → `……` 仅在紧邻 CJK 时报告；英文语境的 `...`、`foo(...)`、`a...b` 范围语法一律不报

**争议项落点**：排版指北标注为争议项的规则（链接两侧是否加空格、是否使用直角引号「」）为 ℹ️，仅在检出文档内写法不统一时提示，不给强制主张。

### 3.4 L 组规则

全部为 `report`。原方案将 L1/L2 定为可应用的改写建议，审查指出其仍可能删减语意。

| ID | 规则 | 判据 |
|---|---|---|
| L1 | emoji 装饰滥用 | 标题行含 emoji；或同级列表中 ≥ 3 项以 emoji 开头 |
| L2 | 加粗滥用 | 单段内 ≥ 3 处 `**`；或整段/整句被加粗包裹；或独占一行的加粗文本后紧跟正文（与 MD036 重叠时以 MD036 为准） |
| L3 | 结构滥用 | 列表嵌套 > 3 层；或列表仅含 1 项 |

**语意承载豁免**——以下 emoji 用法不计入 L1：

- 出现在表格单元格内
- 作为级别标记紧邻其说明文字（⛔ ⚠️ ℹ️ ✅）
- **承载信息的标记**：状态标记（🟢 🟡 🔴）、权限标记（🔒）等，删除即丢信息

L2 检出时须附提示：`**必须**` 这类加粗承载规范强度，删除会削弱语义；独占一行的加粗改为标题会改变目录、锚点与层级。

## 4. 分级体系

**严重级别**

| 级别 | 判据 |
|---|---|
| ⛔ 错误 | 破坏渲染 / 违反国标强制条款 / markdownlint error |
| ⚠️ 警告 | 风格不一致 / LLM 排版毛病 |
| ℹ️ 提示 | 可选项与争议项 |

**处置方式**：**全部检出一律只报告**，不存在自动修改路径。用户确认后的修改统一走 §6 事务流程。原方案的 `auto` / `assist` / `report` 三级与后来的两级均已取消——分级本身曾是"某些项可以安全自动改"这一错误假设的产物。

## 5. 执行流程

```
0  前置检查：目标文件是否在 git 版控下、工作区是否干净
   → 不满足则 ⚠️ 警告并请求确认（不硬阻塞：目标可能是刚生成的新文件）
1  语言判定：CJK 字符占比 → 中文 / 英文 / 混合
   → 英文文档跳过 T 组
2  M 组扫描（只读）：按 §3.2.2 检测顺序取得 markdownlint-cli2 → --config assets/markdownlint.jsonc
   → 未安装：询问用户（brew / npm -g / npx 临时 / 跳过），不得静默安装
   → 用户选跳过或工具不可用：降级为 AI 按 references/markdown-rules.md 扫描
   → 目标为不受信任的第三方仓库：先提示 §3.2.2 的代码执行风险
   → 报告头部记录工具实际版本
3  T 组 + L 组：AI 通读，跳过保护区，产出报告条目
4  报告输出：按组分节，每条含 行号 · 规则 ID · 严重级 · 权威出处
5  询问是否应用 → 用户确认后按 §6 事务流程修改
6  二次验证：重跑步骤 2，确认无新增问题
```

**批量与输出落点**：支持传入目录，逐文件处理并汇总。文件数 ≤ 5 时报告输出到终端；> 5 时写入临时目录 md 文件并给出路径（不入库）。

## 6. 修改的应用方式

**本节不提供结构安全保证。** 这是人工确认后的尽力修改流程；可验证的部分只有"落盘内容与已确认内容逐字节相等"这一条不变量。

第二轮审查驳回了"纪律即安全"的表述，理由成立且须记录，因为这是最容易复发的自欺：

- "一次一处 Edit"保证的是**定位唯一**，不保证**判断正确**——AI 可以精确地改错地方
- "改前确认不在保护区"仍然要求 AI 正确解析 CommonMark。跨行 code span、容器内 HTML、围栏长度、lazy continuation 不因改用逐点 Edit 而变简单
- "重跑 lint 零 error"只证明结果更符合 lint 规则，不证明没有语意、AST 或渲染变化。MD009 与 MD029 正是能修得干净却改坏含义的例子

因此不使用"fail-closed"或"安全性由本节承载"这类措辞。真正的 fail-closed 要么需要解析器提供结构 span，要么根本不在本 skill 内执行修改。

### 6.1 事务流程

原方案的不变量是"实际变更行 ⊆ 已确认条目的目标行范围"，用 `git diff --unified=0` 校验。**该不变量不成立**，第三轮审查给出四个理由：

1. 确认条目的行号属于冻结前文件，而 diff 的删除行用旧侧坐标、新增行用新侧坐标——两套坐标系
2. 前面的插入或删除会让后续合法编辑的新侧行号整体漂移
3. 纯插入发生在两行之间，没有天然的"原始目标行"
4. 即使坐标映射正确，"改动发生在批准行内"仍允许顺手改掉该行的其他字符，证明强度不足

此外 `git diff` 比较的是 HEAD/index 与工作树，而非冻结快照与事务结果，已有改动会混入，未跟踪文件也无法覆盖。

**修正后的唯一硬不变量**

> 实际落盘结果 `A` 与推导出的预期结果 `E` 逐字节相等。

**确认时机按回滚成本分两种情况。** 原方案一律先确认后改，经复核判定过重：当文件在 git 版控下且工作区干净时，"改完看 diff，不满意 `git checkout --`" 与 "先看 diff 再改" 的**安全性等价**——两者都能完整回滚、呈现的信息量相同，只是顺序不同，而前者流畅得多。

| 情况 | 确认时机 |
|---|---|
| 文件在 git 版控下且工作区干净 | **后置**：直接改，改完展示 diff，不阻塞 |
| 工作区有未提交改动，或文件不在 git 中 | **前置**：先展示 diff 并等待确认（回滚成本高） |

```
1  冻结：记录事务开始时的原始字节串 B 与 hash(B)
2  生成：所有编辑基于 B 推导出确定性候选结果 E
3  前置确认（仅回滚成本高的情况）：展示 B → E 完整 diff 并等待确认
4  防竞态：落盘前再次断言当前文件哈希仍为 hash(B)
   → 不等则中止并重新生成（文件在此期间被其他进程改动）
5  应用：写入 E
6  校验：断言 hash(A) == hash(E)
   → 不等则事务失败，恢复 B
7  展示：完整 diff（后置确认情况下这是使用者的审查点，须明确告知可用 git checkout 回滚）
8  复核：重跑 M 组只读扫描
```

哈希不变量在两种情况下都保留——它防的是并发写入，与确认时机无关。该不变量证明"落盘内容就是推导出的内容"，强于原先的行号子集断言，且插入、删除与多点编辑都不产生坐标问题。

### 6.2 修改纪律

以下纪律降低误改概率，但不构成保证：

1. **禁止正则全文替换。** 不得用 `sed` / `perl -pi` / 全局 `replace_all` 处理排版问题——这是把已排除的正则风险重新引入的捷径。候选结果 `E` 须逐点推导后整体写入，而非全文正则变换
2. 每处改动须有唯一定位的上下文依据
3. 改前确认不在保护区：围栏代码块（含 blockquote 与列表内的围栏）、缩进代码块、行内 code span（含跨行与多反引号）、YAML frontmatter、HTML 块、链接与图片的 URL 与 title、autolink
4. 行内标记外侧落点：`中文**abc**` 改为 `中文 **abc**`，空格加在标记符外侧
5. 行尾空白一律不动（硬换行）
6. 结构不确定时跳过，并在报告中标注"结构不确定，未处理"
7. 数量门：单文件待改 > 30 处时汇总确认，不逐条询问

## 7. 决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| 工作模式 | 写作约束 SSOT + 事后审查（双向） | 既约束生成、也审查已有产物 |
| M 组判定者 | 工具优先，AI 兜底 | 机械规则交确定性工具，省 token 且更准 |
| 规则权威源 | Node 版 markdownlint + 国标 + 排版指北 | 本地两个参考项目分别偏旧与二手 |
| skill 身份 | **审查策略 skill，非自动格式化 skill** | auto 塌缩后价值内核在规则知识与一致性 |
| 是否附带脚本 | **否**（原方案为是） | 保护区识别等于实现 CommonMark 子解析器；auto 塌缩后脚本失去存在理由 |
| T 组自动修复 | **全部取消** | 五条逐条证伪（§3.3） |
| **M 组自动修复** | **首版不实现**（原 27 条 → 9 → 4 → 0） | `fixable` ≠ 语意安全；收缩至 4 条罕见笔误后，收益与隔离执行的代价明显失衡（§3.2.1） |
| 分级体系 | **取消处置分级** | 分级是"某些项可安全自动改"这一错误假设的产物 |
| M 组工具获取 | **优先用已安装的（项目 node_modules → PATH），缺失则询问四选项，不得静默安装** | 避免每次走 npx 网络开销；安装修改系统环境须先问 |
| M 组版本策略 | 不强制版本，但报告须记录实际版本 | "报告可复现"的实质是知道出自哪个规则集，而非固定某版本 |
| M 组配置策略 | 只读；允许项目配置生效 | 只读不改文件，误报成本低；目标仓库自有约定应优先 |
| 修改的不变量 | **落盘内容与推导内容逐字节相等** | 行号子集断言存在坐标漂移且证明强度不足（§6.1） |
| 确认时机 | **git 干净则后置（改完看 diff），否则前置** | 可完整回滚时两种顺序安全性等价，前置确认纯属摩擦 |
| MD060 处置 | `style: "padded"` | 实测：默认 78 条噪音 → padded 归零，且仍能抓真不一致（§3.2） |
| 半角标点转全角 | 不实现 | 中英混排判定边界模糊 |
| 重复标点收敛 | 仅报告"超过三叠" | 国标允许最多三叠；叠用改语气属语意 |
| 中文省略号形式 | 六连点 `……` | 国标前言明确；本地参考项目主张的 `⋯⋯` 不合规 |
| GB/T 15835 数字用法 | 不纳入 | 管用字选择非排版；标准本身允许两种形式并存 |
| L 组处置级 | 全部 report | emoji 与加粗可承载语意 |
| **W 组（文风）** | **删除** | 属语意建议，与 §2 正面冲突；"明示越界"只是掩盖而非解决。需要时另做 `writing-review` |
| 是否接入 DevDocs | 不接入 | 独立 skill，零改动现有流程 |

## 8. 文件结构

```
skills/markdown-style/
  SKILL.md                          # 主流程 + 三组概览 + 分级 + §6 事务与纪律 + 浓缩「生成时清单」
  references/
    markdown-rules.md               # M 组全表 + 出处 + 「为何不用 --fix」盲区分类（核心知识资产）
    cjk-typography.md               # T 组，含逐条证伪记录
    llm-artifacts.md                # L 组，含语意承载豁免表
  assets/
    markdownlint.jsonc              # 只读扫描配置（单份）
  templates/
    report.md
```

**无 `scripts/` 目录**——本 skill 不含可执行代码，仓库保持纯规格库属性。

**写作约束模式**不读 references——SKILL.md 内嵌约 15 条最高频清单，供会话或其他 skill 直接引用。

**命令接口**（一个 flag）：

- `/markdown-style <file|dir>`——扫描并出报告，然后询问是否应用修改
- `--check`——只出报告，不询问、不修改

## 9. 验证方式

本仓无测试框架，验证依赖样例核对：

1. **工具检测与询问**：在未安装 markdownlint-cli2 的环境下运行，确认不静默安装、四个选项都能走通；安装后再运行，确认走"已安装"路径不再询问，且报告头部带版本号
2. **配置噪音基线（已有实测基准）**：对 `AGENTS.md` + `README.md` + `docs/workflows.md` 跑只读扫描，结果须为 22 条且构成与 §3.2 实测表一致。该数字随文档修订会变，但"出厂默认 138 / 本配置 22"的量级差须保持
3. **保护区零误伤**：应用修改时，样例须含审查给出的三个反例——blockquote 内围栏、跨行多反引号 code span、含平衡括号的链接 URL——修改后逐字节比对，保护区内容不变
4. **T 组检出准确性**：样例含 `iPhone 5s`、`margin: 2em`、`2026年7月31日`、全角 `ａｄｍｉｎ`、三叠叹号、英文语境 `...`，确认不产生错误检出
5. **事务不变量**：构造"预览期间文件被外部修改"场景，确认 §6.1 步骤 4 的哈希断言中止事务；构造"写入结果与推导结果不一致"场景，确认步骤 6 回滚。另须分别验证两种确认时机——git 干净时不阻塞、工作区脏时阻塞等待
6. **端到端冒烟**：对本仓一篇真实中文文档跑完整流程，人工核对报告与改动
