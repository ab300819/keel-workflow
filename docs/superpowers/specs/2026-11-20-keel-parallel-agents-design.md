# keel 多 agent 并行：负责人、可派任务与验证者分离（设计稿）

> 状态：待用户审阅。范围由用户 2026-11-20 定为 (a)(b)(d)，其余见 §6。

## 1. 为什么做

用户已开始用 hcom 让多个 agent 并行开发。EMSPR 的实况（2026-11-20 向其 PM 会话核实）：

- 1 个 PM 会话管台账和派单，9 个执行 agent（5 个 claude 会话、4 个经 hcom 的 codex），各在自己的 worktree 和分支上干活。
- **只有 PM 写台账、分配编号**，所以「两个 agent 抢同一张卡」「新建任务撞号」都没发生过。
- PM 现在靠手写交接文件跟踪「谁在做哪张卡、在哪个分支、在等谁」，依赖解开靠人盯，「验证者不能验自己写的卡」靠约定。

keel 3.x 已有的文件锁、原子写、每任务一个文件、合并和切分支不误拦，足够应付「单一写入者 + 多执行者」。缺的是**台账里没有「谁、在哪、谁验」这几项**，所以 PM 只能另记一份。

## 2. 目标与非目标

**目标**

- (a) 台账能回答「谁在做哪张卡、在哪个分支」，PM 不再手写交接文件。
- (b) 一条查询列出「依赖都已解开、可以派」的卡。
- (d) 验证者和实现者是同一个名字时，工具拒绝写入。

**非目标**

- 不做任务抢占、加锁领取：EMSPR 是 PM 派单，没有自领场景。
- 不做 hcom 推送通知、不让 keel 依赖 hcom。
- 不改「dev-workflow 不做任务并行」的定位：并行由 PM 或用户编排，keel 只记账、只查询。

**反目标**（做了反而坏事）

- 让执行 agent 也直接写台账：会破坏 EMSPR 现在「只有 PM 写」的单一写入者，引出抢写和冲突。
- 给用户增加要记的命令或子指令：用户面仍是自然语言，见 2026-08-26「用户面零子指令」。

## 3. 方案比较

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 只给任务加字段（**推荐**） | 任务加 3 个可选字段；`task list` 加两种筛选；`task set` 加一条校验 | 改动小，全在 keel 工具里；PM 照旧单一写入；旧任务文件不用迁移 |
| B. 另建「派单」记录 | `state/assignments/` 存每次派单，带历史 | 能看派单历史，但和任务状态是两份账，要对齐；EMSPR 没提历史需求 |
| C. 接入 hcom | keel 读 hcom 的实例列表，自动知道谁在线、自动通知 | 最省人工，但 keel 依赖一个外部工具，其他用户没装 hcom 就失效 |

选 A。B 留到真有人要派单历史时再说，C 等 A 用顺手、且第二个项目也用 hcom 再说（本仓 ROI 判据）。

## 4. 设计

### 4.1 任务新增 3 个字段（都可选，默认空）

| 字段 | 含义 | 谁写、何时写 |
|---|---|---|
| `assignee` | 实现者的名字 | PM 派单时 |
| `branch` | 实现者干活的分支 | PM 派单时，或实现者交卡时由 PM 补 |
| `verified_by` | 验证者的名字 | 验证结论回来时 |

- 名字是什么由派单方决定：用 hcom 时用 hcom 实例名，否则用会话名。工具只比较字符串，不认识 hcom。
- 上限 80 字符，禁止换行和 `<!--`，和现有文本字段同一套校验。
- schema 仍是 `keel.task.v1`：现有校验只拒绝**未知**字段，不要求字段齐全，所以旧任务文件不用迁移。
- 执行者身份与执行方式见 [精简执行路径设计稿](2026-11-22-keel-executor-lean-path-design.md) §4.1；`assignee` 即执行者名。

### 4.2 校验：验证者不能是实现者

`task set` 写入后，如果 `assignee` 和 `verified_by` 都非空且相等，拒绝写入，退出码 1，提示「验证者与实现者相同：<名字>」。放在 schema 校验里，任何写入路径都会经过。

局限：同一个会话里由子代理验证时，名字由派单方填，工具分辨不出是不是同一个会话。这条只防「填了同一个名字」，不防冒名。

### 4.3 查询

- `task list --assignee <名字>`：只列该负责人的卡。
- `task list --ready`：列出 `status` 为「待开发」、且 `depends_on` 里每一项都已解开的卡。依赖里有不存在的编号时，该卡不算可派，并在末尾提示是哪个编号。
- 「谁在做什么」不加新命令，用已有的 `--fields`：`task list --status 进行中 --fields id,assignee,branch,title`。

**待你定**：依赖解开的标准。EMSPR 的说法是「T-247 合入 → 可派 T-261」，合入发生在 PM 把台账改为「待审查」（review_pending）之前或同时。

- 建议：依赖为「已完成」「已归档」或「review_pending」都算解开。代码已经合入，等审查不该挡住后续卡。
- 代价：审查若打回，后续卡可能已经基于有问题的代码开工。

### 4.4 skill 改动

只改写台账的地方，一条规则只写一处：

- `skills/shared/constraints.md`「keel 工具」一节：登记 3 个字段与 `--ready`、`--assignee` 的含义。
- dev-workflow 领取任务那一步：有负责人和分支时，一并写入 `--assignee`、`--branch`。
- 验证结论写回那一步：写 `--verified-by`。
- 派单方（PM）如何用 `--ready` 选卡：写进 `docs/workflows.md` 一段，不新建 skill。

### 4.5 生成区

04-dev-tasks.md 的台账生成区**不加列**。表格已经很宽，查询走 `task list`。

## 5. 验收

- 新字段能经 `task add` / `task set` 写入，`task get` 能读出，旧任务文件不报错。
- `assignee` 等于 `verified_by` 时，`task set` 退出码 1，文件不变。
- `--ready`：依赖全解开的列出；有一个依赖未解开、或依赖编号不存在的不列出，后者有提示。
- `--assignee` 只列该负责人的卡。
- 测试、ruff、mypy --strict、自测（python3 ≥ 3.9）全过；版本升到 3.3.0（3.1.0、3.2.0 已被 worktree 支持与精简执行路径占用）。
