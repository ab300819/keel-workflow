# 审查/验证体系复杂度审计 —— 结论、已落地项与遗留台账

> 日期：2026-08-20 · 范围：`dev-workflow` / `verify` / `adversarial-review` / `_shared/constraints.md`
> 用途：**后续接手的入口文档**。审计结论、已改动项、未清项与封存项全在此文，不必回溯对话。

## 1. 起因与方法

用户观察：DevDocs 开发阶段每个任务都跑一次对抗审查，导致**局部最优而非全局最优，甚至对审查者过拟合**。

方法：两路**独立并行**审计（codex CLI + 独立子 Agent），同题同约束，最后做分歧对齐。给两边的四条反规则：

1. 每条结论必须给 `file:line` 证据
2. 优先找可删项，判据是"删掉之后哪条真实失败会发生"
3. **禁止用"新增机制"作答**——任何净增状态/flag/enum/概念/文件的建议须说明它删掉了什么更重的东西
4. 承重复杂度（状态机 / Recovery / flag / enum / 概念）与表述复杂度分开报

两边都要求交「最有信心的 3 条 / 最没把握的 3 条」——用于分歧对齐：**两路都高信心的直接采纳，一边高一边低的才需人工判断**。

体量基线（审计时实测）：5221 行、≈43 个 enum 值、28 个用户面 flag、10 个 commit trailer。

关键结论摘要：

- **`作用域匹配` 准则**（`constraints.md` §11）：局部最优 = 优化的作用域 < 决策的影响域。与 SSOT 对偶（SSOT 管"事实边界 ≡ 文件边界"，本条管"评审边界 ≥ 影响边界"）。含三条防滥用刹车——只约束门的设计不约束每次执行、不改交付粒度、不建检测器。
- **`doc/project-rule-boundary`**：补住 project→skill 方向的提拔缺口（此前只有 skill→shared 设闸）。起因是 mic-en 的 Java SPI/DTO 规则经一条**只存在于使用它的那份文件里**的三级阶梯被提拔为跨项目 ⛔ 强制门。
- **镜像边界**：agent 侧 references/SKILL 一律改指针；仅用户侧产物模板允许内联阈值数字（模板复制进项目后 skill 不在场）。
- **延后外审空 diff**（最值钱的一条）：`fast`/`guarded` 的外审延后到 drain，而 Phase 4 用工作区 diff / `uncommitted: true`，此时 Commit 1 早已落盘 → **默认档的延后外审等于没审**。既存缺陷，非本轮引入。已按 inline（工作区）/ drain（Commit 1 提交 diff）分离 diff 源。

## 5. 遗留：封存待数据

### 5.1 第二段：外审输入 task → batch

方案 [specs/2026-08-06-review-unit-task-to-batch-design.md](../superpowers/specs/2026-08-06-review-unit-task-to-batch-design.md) §3。触发条件（§3.1）：

| 第一段跑完后观察到 | 决策 |
|---|---|
| 跨任务问题被漏判（后续任务给早期抽象打补丁，而逐任务外审全 PASS） | **做** |
| 逐任务外审已够，未见跨任务盲区 | **不做**，接受双 diff 源分支为永久代价 |
| 外审发现数偏低或全是框内微调 | 倾向做——局部最优的特征信号 |

> **"不做"是合法结局**，不是失败分支。那样省下整个 `constraints.md` SSOT 改动，同时保住已修好的延后外审。
>
> 已知代价：第一段引入的 Phase 4 双 diff 源分支（inline / drain）若第二段不做则永久保留。

## 6. ⚠️ 审计自身的错误（勿全盘采信本报告的来源）

后续若重跑审计或引用其结论，注意这两处已证实的错误：

1. **「层级仅作风险输入」称重申 21 处、该删 20 处 —— 结论不成立。** 它按 grep 命中数计数，未判断各处用途。逐条核对后真重复只有 **7 处**（同一文件内说两三遍），其余是字段限定符（`task-template` 的 4 个层级行，删了字段就歧义）、表格列名、章节引语。这与它自己批评的「≥3 发现门槛」是同一种错误：数数量而非判质量。
2. **两路都漏了上游对镜像的显式授权。** `code-quality` / `testing-guide` 的阈值表原本写着「镜像处（如 dev-workflow verification-flow Phase 1）须标注摘录自本表」——镜像不是违规，是 SSOT 所有者的既定设计。删除镜像因此不是"修违规"而是"改上游决策"，已同步改写那两处授权说明。

反向地，本次执行也补出两路都没算到的项：

- `[D1]`/`[D2]` 带 profile 条件分支，第二段统一走 drain 后**可整个删除并折叠进 `[F]`**——是漏算的一笔额外减法，不是漏算的改动量
- 合并 diff 在 `workspace_mode: shell` 下须逐 `code_root` 拼接（Commit 1 拆成 N 个子模块 commit）——三稿之前无人提及
